Spike

Feasibility spike

The spike proved on the target machine that the chosen stack works before anything general is built: a locked Python 3.13 environment, both public datasets verified, an Inspect task where a model calls a read-only SQL tool on Chinook, and a live trace of a real model doing it. This chapter is the reference for what exists, how to run it and where it stops.

Install and run

The project is a uv project on Python 3.13 with a committed lock. The core needs the standard library and one schema validator, jsonschema; the Inspect and the machine-learning dependencies are optional extras (agent and ml).

# core only: the standard library and jsonschema
uv sync --locked
uv run python -m hypotrail --help

# everything the spike needs, then the offline test suite (no network, no model call)
uv sync --locked --all-extras
uv run --locked --all-extras pytest

# the Python version is pinned by .python-version and requires-python (3.13 only)

The default test command never calls a model, even when a model key is present: every test runs with outbound network access blocked, and an attempt fails the test. Live calls are opt-in and never part of the suite.

Data verification

The two public datasets live in the declarative Workloads examples/bike_day and examples/chinook, each with the slice of data-sources.lock.json that covers it and a data-checks.json that declares what to check. Verification works offline, in a fixed order: the bytes of every selected dataset first, then the licence notices, then the content.

The Inspect spike

The agentic side lives in src/hypotrail/agentic/; the core never imports Inspect (ADR 0001). Inspect owns the agent loop, the tool calls, its limits and its log; Hypotrail owns the scoring function and reads the log only through Inspect's public log API.

  • Task (runner.py): a system message and a user message per Case, the tools, then Inspect's own generate-and-call-tools loop. The task is now built from the Workload declaration; see the chapter on the agentic Track.
  • Tool (sql_tool.py): query_readonly(sql) opens the Chinook file read-only at a path fixed by the application, one connection per execution, execute and never executescript, extensions disabled. mode=ro covers only the main database, so three native SQLite mechanisms decide what runs, and no SQL text is inspected (no regular expression, no SELECT test): the limit on attached databases is 0; execute takes one statement; and an authorizer holds the allow-list, which is SELECT, reads of the tables the file itself declares (read from the file, never named in code, so its system tables such as sqlite_master stay refused) and the functions of the allow-list table in the chapter on the agentic Track (like and glob were added to AG-03's list by the owner's revision of 2026-11-07, #51). Everything else is denied: writes and DDL, ATTACH, DETACH, PRAGMA, transactions, VACUUM (also INTO), extension loading, recursive queries and any other function, so a statement that starts with WITH or SELECT but needs a denied action is refused. It returns columns, rows, row_count, truncated, error and a tool_call_id. A refused or failed statement sets error to a code (DENIED_ACTION, SQL_ERROR or MULTIPLE_STATEMENTS), a type and a message; the code is what to rely on. Four per-query caps bound every call (row, size, time and instruction count; see the agentic Track chapter).
  • Projection (projection.py): one record per Case x Repeat, in the order model turn, tool call, tool result, model turn, final answer. A Repeat is 0-based; Inspect's epoch is 1-based. An Episode is produced, failed (execution stopped with an error, at one of our limits before a final answer, or with its answer cut by the output cap) or missing (absent from the log).
  • Scoring (core/answer_scoring.py): compares status, reason, columns, rows and unit with the frozen Reference. An answer missing one of the six required fields (status, reason_code, columns, rows, unit, evidence) is malformed: parsed is false and every component is false, even when the Reference holds null there. No string-to-number conversion, a boolean is not an integer, NULL stays NULL, non-finite numbers are refused, and the Reference's absolute tolerance applies. agentic/rescore.py rescores a kept log without the model, the tool or the Chinook file; since ticket #45 it goes through the chinook_contract_v1 Scorer (see the agentic Track chapter).
  • Limits (limits.py): set through Inspect's own options and read back from the log.
  • Live execution (live.py): python -m hypotrail spike live --config plain --model anthropic/<model> --out DIR. Opt-in and paid. See below, and the agentic Track chapter for the two commands.

The live execution

spike live runs one named Configuration of the spike task on at most two dev Cases (D03 and D05 by default), one Repeat each, under the limits above (the token budget since revised: see the table). It scores nothing against References; it only shows that a real model calls the tool and uses its result.

  • Key: read only from HYPOTRAIL_ANTHROPIC_API_KEY and passed explicitly to the provider; ANTHROPIC_API_KEY is ignored. It is never logged or persisted, and the output directory, including the decoded Inspect log, is scanned for its value before the execution reports, and the scan also runs when a step of the execution fails (a leak is then the error reported). Each log is read back through Inspect's read_eval_log and searched, and its raw bytes are searched too; the log's storage format is never opened by hand (ADR 0001). A log that Inspect cannot read back does not stop the scan of the other files; if no leak is found anywhere and some log could not be read, the execution fails with LOG_NOT_FULLY_SCANNED and the files named, and is never reported clean. Without the key the command exits 5 with the named blocker LIVE_NOT_VALIDATED before any network call. Inspect's Anthropic provider prefers ANTHROPIC_AUTH_TOKEN to an explicit key, so the execution refuses to start when that variable is set.
  • Model: an explicit input of the form anthropic/<model>; the code holds no default, and another provider or a cloud-platform variant is refused so the key cannot travel there.
  • Bounds: non-dev Cases and more than two Episodes are refused.
  • Record: run.json holds the provider, the model identifier, the served model, the request parameters the log recorded, the engine version, the effective limits and the hardware; projection.json holds the Episodes; inspect/ holds the Inspect log.

The recorded execution used anthropic/claude-sonnet-5-5. Both Episodes ran model, tool call executed on Chinook, model, final answer, and both final answers repeat rows the tool returned. The request carried the provider's defaults for this model: adaptive thinking and a top-level ephemeral cache control, with max_tokens 1024 shared between thinking and the answer.

Choices and limits worth knowing

Tool-call IDs

Inspect gives a tool no public way to read its own call ID while it runs. The tool mints an application ID, puts it in the result the model sees, and the projection keeps the mapping to the native ID.

Scripted executions

Offline executions use Inspect's mock model, recorded as mockllm/model, so no projection of such a log can be taken for a live model.

Rehearsal

The live path is exercised in the suite against a fake endpoint on loopback, so the real Anthropic client, the key header and the key scan are tested without a real call.

Not built

The Import and Assessment contracts.

Track

Temporal regression Track

The temporal regression Track runs the daily bike-rental Workload end to end on the Partition dev: it derives the Items of each Partition, builds the References, produces the predictions of two declared Configurations, seasonal_7 and ridge_v1, scores them and writes a first Comparison with per-date paired differences and delta_mae. It is a library driven from Python; init and run ml drive it from the command line and record the result as an Attempt of a Study (chapter 04).

The Workload declaration

The Workload is declarative and holds no Python (ADR 0002). Everything the Track needs is a parameter read from examples/bike_day/workload.json, next to its data (data/day.csv) and licence notice. The Track code in src/hypotrail/ml/ fixes only two things: the Partition roles train, dev and public_check (protocol vocabulary, defined once in partitions.py) and the two kinds of Configuration it knows, with the keys each takes. Every other rule is checked against the declarations below.

The shape of workload.json is described once, as a JSON Schema (src/hypotrail/ml/workload.schema.json) checked by jsonschema, the one schema validator of the core (jsonschema is a pinned dependency of the core, not of an extra). The schema lists every key at every level, each kind of Configuration with the keys it takes, and the type of every value, leaves included: a column name is a string, a period is a whole number (7.0 and true are not), clip_min is a number, sparse_output is a boolean. It also lists the values the Track can run: ridge.solver is one of auto, svd, cholesky, lsqr, sparse_cg, sag, saga; encoder.handle_unknown is ignore or error; encoder.sparse_output is false (the Track feeds a dense matrix to scikit-learn); ridge.alpha is at least 0; the root period_k is at least 1; id_prefix, target_unit, the file and column names, the id of a Configuration and the name of a Partition are not empty (a Partition named "" would otherwise load and lose its Items from the References); the dates of a Partition are calendar dates YYYY-MM-DD; track, when present, is temporal_regression. A declaration that does not match is refused when it is loaded, with a code and the path of the faulty value, before any data is read, any model is fitted, any prediction is made or any file is written. The Track keeps no hand-written check of what the schema guarantees.

Only partitions is required by the schema, because it is the one key every public entry point reads (memberships, References, the seasonal baseline, the Ridge outputs, metrics and the Comparison). Any other key is required by the entry points that read it, which refuse its absence with DECLARATION_INCOMPLETE before they write anything: data_file, date_column, id_prefix and period_k by memberships (and so by References and by the two Configurations); target_column by References and the two Configurations; forbidden_features, allowed_target_features and configurations by the two Configurations; target_unit by metrics and the Comparison. schema_version, track and licence_notice are read by no Track code and may be absent. question, objective and limitations are read by init only, for the StudySpec (chapter 04), and may be absent from a Workload that is never given a Study. The rules that relate values to each other or to the protocol stay in Track code and run after the schema (see Refusals).

The declaration is read once. declaration.load_declaration(workload_dir) is the one loader: it reads workload.json, checks it against the schema and returns a Declaration, a tree of frozen dataclasses (tuples and read-only mappings; a key the schema leaves optional is None when the file lacks it). Every entry point calls it once and every computation starts from the typed object: memberships_of, read_table, read_target_series, validate_configuration, inputs_of and the others take a Declaration and refuse a raw dict with a TypeError. No other module indexes the raw dictionary.

A period is an object too. periods.Period holds a number of days with the key and the path where it was declared, and shifts a date itself: earlier(date) is the date one period before, and window(date) yields the dates 1 to k days before, nearest first. Memberships (the warm-up), the lags and the seasonal baseline all shift through it, and a shift that leaves the calendar is refused there (see Refusals). Two periods of the same length are equal wherever they are declared.

Memberships and References

write_memberships(workload_dir, out_dir) derives one row per date of the data into memberships.csv with the columns row_id, date, partition and exclusion_reason. A date inside a declared range gets that Partition. A date whose history is incomplete gets no Partition and the reason insufficient_history; for Bike these are the seven first days, 2011-01-01 to 2011-01-07. A declared range may not cover such a day, and a date that falls in no range is refused, so the declaration and the data are always consistent. The result does not depend on the order of the input rows.

write_references(workload_dir, out_dir) writes references.csv (row_id, y_true): the target of every Item that belongs to a Partition. Predictions never carry their own target; metrics join this file by row_id.

The two Configurations

  • seasonal_7 (kind seasonal_baseline; baselines.py, needs neither scikit-learn nor NumPy): the prediction for date t is the target 7 days earlier. Nothing is fitted. Its declaration holds period_k and post_processing.clip_min. A period must be a declared lag of allowed_target_features.
  • ridge_v1 (kind ridge_pipeline; ridge.py, needs the ml extra: it imports scikit-learn and NumPy, and nothing in the core does): the inputs are the lag features lag_1, lag_7, mean_previous_7, computed from dates in lags.py (only values strictly before t are read), and the calendar columns mnth, weekday, holiday, workingday read as they are. A scikit-learn Pipeline holds a ColumnTransformer (a OneHotEncoder on the calendar columns, handle_unknown=ignore, dense output; a StandardScaler on the lags) and a Ridge (alpha 1.0, intercept, solver svd). The pipeline is fitted once, on the train Partition, always. Predicting any other Partition fits nothing.

Both apply the same post-processing: y_pred is y_pred_raw bounded below at the declared clip_min (0), applied once when the predictions are written. Both go through the same function (configuration.load_configuration) before anything is fitted or predicted. The declared kind picks the keys a Configuration may carry; the schema refuses an unknown kind, or a key that does not belong to its kind, when the declaration is loaded. The checks that apply to every Configuration (forbidden features, target transformations that reach date t or later, target transformations the Workload does not declare) run for every kind.

Metrics

metrics.compute_metrics(predictions, references, memberships, workload_dir, partition="dev") joins predictions, References and memberships by row_id and scores y_pred. The predictions must be exactly the Items of the Partition, each with a reference; a repeated row_id, a value that is not a finite number or a missing reference is refused. Reported: mae (the primary metric), rmse, mae_by_month and clipped_count (the number of Items where y_pred differs from y_pred_raw). Each carries the declared unit and a direction (lower_is_better); the order of the files changes nothing.

The function computes metrics on dev only. Any other Partition is refused; public_check has its own code, because the function takes no Study and so has no Exposure journal to write to. Inside a Study, assess accepts public_check Items and records the Exposure (chapter 12).

Comparison on dev

comparison.compare(control_predictions, candidate_predictions, references, memberships, out_dir, workload_dir, partition="dev") pairs the two predictions files by row_id. They must cover exactly the same Items: there is no silent intersection. It reports the metrics of each side over the same scored Items and, for each Item, control_abs_error, candidate_abs_error and delta_abs_error (Candidate minus Control). delta_mae is MAE(Candidate) - MAE(Control) taken from the two reported MAEs: a positive value means the Candidate is worse. An improvement is never required. Here seasonal_7 is the Control and ridge_v1 the Candidate. The command compare (chapter 07) gives the same per-date differences and the same delta_mae (to 1e-9) from the two Assessments of a Study, after the comparability checks.

Refusals

Each refusal is an InvalidInputError (exit code 2 on the command line) with a code, a message, a stage and details. Nothing is dropped or included silently, and a declaration or Configuration is refused before anything is fitted or predicted. Every refusal raised while the declaration is loaded has the stage declaration and its details give key and path (the dotted path of the faulty value, empty at the root). A declaration file that is missing or not JSON is refused with FILE_NOT_FOUND or FILE_NOT_JSON: key is the file name, path is empty (the whole document) and file is its location. A period that no date can apply (it reaches before the first date of the calendar) passes the schema, since it depends on the dates; it is refused when a date is shifted, in memberships, lags and the seasonal baseline, with DECLARATION_VALUE_NOT_ALLOWED, stage periods, and in details the key and path of the declared period, its length in days (days, the declared number, never the offset the loop had reached) and the date being shifted. The same code at load has the stage declaration, so the two are told apart by their stage. An empty name of a Partition or of a Configuration is refused at load with key set to the empty name and path the object that holds it (partitions or configurations).

Track

Agentic Track

The agentic Track asks a model Chinook questions and scores the answer it keeps. This chapter describes the part that exists: the Workload declaration and the task built from it, and the chinook_contract_v1 Scorer, which turns one Episode's raw final answer, its Reference and its projected trace into four Criteria, exact_table, format_valid, evidence_link_valid and contract_success, and keeps failures of the instrument apart from failures of the evaluated system. The spike chapter covers the executions and the log projection.

Where the Scorer lives

The Scorer is src/hypotrail/core/chinook_contract.py. It needs the standard library and jsonschema only; the core never imports Inspect (ADR 0001). Rescoring a kept log (agentic/rescore.py) projects the log, then applies this Scorer to each Episode. It calls neither the model nor a tool and never opens the Chinook file: the frozen References are enough. The output of every Episode records the Scorer's name, chinook_contract_v1, and its version, and two rescorings of one log give the same verdicts.

The Scorer takes the raw final answer unchanged and keeps it unchanged in its output, whether or not it respects the schema.

The two Configurations

  • plain carries the system text in full. It tells the model to answer with the available tools and not to guess, to answer in the requested schema table-answer/1, and to distinguish an answer, an ambiguity and unavailable information. It states the common format rules: one JSON object and nothing else, no Markdown fence, no extra prose, the six fields, the three statuses and their reason_codes (criterion_undefined for needs_clarification, field_not_available for not_answerable), with columns and rows empty and unit null for the last two.
  • verify is plain (extends) followed by a declared added_instruction and nothing else: check the scope, the joins, the units and the result before concluding. Its resolved text is exactly plain's text plus the instruction. No Reference value is in either text.

The task

runner.build_task(workload, configuration, cases=None, partition="dev") returns the Inspect task. runner.run_episodes(cases, workload=..., configuration=..., model=..., repeats=..., log_dir=...) runs it. The task replaces the spike's single prompt and its chinook_spike task.

  • Each Case is one sample. Its input is two messages: the Configuration's system text, and a user message rendered from the question, the requested columns and the unit only (prompt.render_user_message). A Case with no unit goes through the same rendering (Unit: none), so the system text is identical for every Case of a Configuration. The Case identifier, the group, the family, the Reference rows, the oracle SQL, the expected status and the tolerance never reach the model.
  • The model gets exactly two tools, describe_schema and query_readonly, both bound to the database path of the declaration. describe_schema takes no argument and returns the eleven tables with their columns, types and foreign-key relations, read from SQLite itself (PRAGMA); it holds no row, Reference or oracle SQL.
  • Both Configurations run with the same tools, limits and generation settings; only the system text differs.
  • The log header keeps the Configuration name and its exact system text (eval.metadata), and the live run record (run.json) repeats them.
  • The References are not an input of the builder: a task built from the declaration runs when the References file is absent.
Open pointThe builder can build a task on any declared group of Cases, public_check included. The builder does not refuse it; the counting and rescoring entry points do (see the scripted_fixture section), because they take no Study. Inside a Study, assess accepts public_check Episodes and records the Exposure (chapter 12).

The read-only SQL tool

The evaluated model reaches Chinook through two tools, describe_schema (see above) and query_readonly(sql) (agentic/sql_tool.py; the connection details are in the spike chapter). No SQL text is inspected: three native SQLite mechanisms decide what runs. The limit on attached databases is 0, execute takes a single statement, and an authorizer holds the allow-list.

  • Allowed: SELECT, reads of the tables the Chinook file itself declares, and the functions of the table below. AG-03 did not list like and glob; the owner added them by an explicit revision of AG-03 on 2026-11-07 (#51). SQLite reports the operators LIKE (also NOT LIKE and LIKE … ESCAPE) and GLOB to the authorizer under these two names; both only compare text, and the per-query caps still bound any pattern. LIKE keeps SQLite's default matching (case-insensitive for ASCII; GLOB is case-sensitive) because PRAGMA case_sensitive_like stays refused.
  • Tables read from the file: the table names are never written in the code, so a table the file does not declare is not readable, and the system tables such as sqlite_master stay refused.
  • Denied: writes and DDL, ATTACH, DETACH, PRAGMA, transactions, VACUUM (also INTO), extension loading, recursive queries and any other function. A statement that starts with WITH or SELECT but needs a denied action is refused.

Wrapped answers

The prompt asks for a single JSON object and nothing else, and a model sometimes puts a sentence before it or a Markdown fence around it. By owner decision of 2026-11-07 (#58, option E) the Scorer keeps the format as its own Criterion and stops letting the wrapping hide the content. The answer is scanned left to right; at each { the standard JSON decoder tries to read one value (NaN and the infinities are refused, and so is a number that decodes to a non-finite float), a read that gives an object is a candidate and the scan resumes after it, and a failed read (a stray brace in prose, a truncated object, a non-finite number) skips only its own {, so an object that decodes further on, even inside the text of a failed read, is still a candidate. find_embedded_object in core/answer_scoring.py returns the decoded candidate with its text only when there is exactly one, wherever it sits; the table below says what each outcome means. parse_answer is unchanged and still decides format_valid. The raw answer is never altered, and the record says what was scored in its top-level field answer_read_from. The Scorer's version was 2 when that decision was taken (#58), since the same raw answer then scored differently; its name stays chinook_contract_v1.

The evidence link and contract success

A successful tool call is one with no Inspect-level tool error and no structured error in its result body (the shape {code, type, message} that the read-only SQL tool returns, for example when its authorizer refuses a statement). The Scorer reads the Episode's projected steps, plain records, and never an Inspect object; the projection itself still reads the log only through Inspect's public log API. The link is a check that a cited ID points to a real, earlier, successful call. It is not a proof that every claim in the answer follows from the trace.

An exact table with no valid evidence is exact but not a success of the tool-based path: exact_table true, evidence_link_valid false, contract success false. Contract success is scored false as soon as one dependency is false, whatever the state of the others. Only when none is false and one is unscored or errored does it take that state and Reason: a well-formed answer with valid evidence and a missing Reference gives unscored with reference_missing. Without a trace, evidence_link_valid is unscored (trace_missing), and so is the contract success of an answered answer; for an answer whose evidence cannot be read (nothing is read from it, or the object read is not valid against the schema), evidence_link_valid is scored false with invalid_response_format, trace or not.

Study and Attempts

A Study is a folder that holds one Protocol and the Attempts run under it. init creates the Study of the bike Workload; run ml runs one Configuration on one Partition and records it as an Attempt: a manifest, an Observation set and the predictions, every artifact referenced by its digest and published atomically before the terminal manifest. A repeated --request-id returns the recorded Attempt or is refused. A Study admits one writer at a time (init, run ml, import ml, recover, assess and compare take its lock); status shows its local state and recover records an Attempt left behind by a dead writer as interrupted. This chapter describes what exists; importing outputs produced elsewhere is chapter 06; scoring an Attempt is chapter 05; comparing two Assessments is chapter 07.

Commands

The four commands are in src/hypotrail/cli.py. With --json, stdout holds exactly one JSON object ({"ok": true, ...} or {"ok": false, "error": {"code", "message", "stage", "details"}}) and the human diagnostic goes to stderr; no error carries a secret (an unexpected exception is reported by its type only, and so is an OS error of run agent; the other commands report an OS error by its type and message). Without --json, stdout holds one line.

  • init verifies the Workload's data against its lock, then creates the Study: the StudySpec (study.json), a copy of the dataset, and the population (memberships) and the References set as Study artifacts, each with an ID. The Workload must be of the temporal regression Track or of the tool-using agent Track; a Study of the latter (Chinook) holds the database, the Case memberships, the References set and the answer schema, and its primary metric is the Criterion the Workload declares (chapter 08). A Study folder that already holds a study.json is refused. init --study DIR --new-revision adds a revision to an existing Study when its Protocol changes, for example a corrected References set (chapter 10); it takes no --workload. A changed Case text changes the Protocol too: a Study created before the change takes it with init --study DIR --new-revision.
  • run ml runs one declared Configuration (seasonal_7, ridge_v1) on one declared Partition and records one Attempt. --request-id is required. Its output is {"ok": true, "replayed": false, "attempt": MANIFEST}; replayed is true when the request was already recorded and nothing was computed. It needs the ml extra only to run ridge_v1.
  • status only reads. It lists every Attempt of the Study with its technical_status and the artifacts found in its folder, the partial ones of an Attempt that never reached its terminal manifest included, and the Study's write sequence (see The write sequence below). It takes no lock and writes nothing.
  • recover is the explicit command that writes. It records as interrupted, with finished_at and a Reason, an Attempt that is running while no writer is alive, and keeps its artifacts. It resubmits nothing.

The Workload stays where it is declared (examples/<name> of a checkout, or the folder given by --examples-dir: see below): a Configuration can change after the Study exists, and an Attempt records the Configuration it ran. The Study freezes the Protocol, not the Configurations.

The records

Every record is canonical JSON (core/canonical.py): UTF-8, keys sorted, separators , and :, no whitespace, strict types. NaN and Infinity are refused, never written (NON_CANONICAL_VALUE), and an integer and a float of the same value stay distinct. A configuration declared with its keys in another order has the same digest; the source files are hashed on their bytes, separately. Each record is validated against the contract schema (src/hypotrail/core/contracts.schema.json, by jsonschema) before it is written and after it is read; a fault is CONTRACT_VIOLATION.

The schema is derived from the kit's contracts.schema.json and owned here; the kit's copy is not changed. It keeps every field of the kit's envelopes, names the Criterion states scored / unscored / errored and their counters unscored / errored, and defines the fields and the two further record kinds (freeze, exposure) that the next tickets of the slice name. Only the records below are written today.

Attempt manifest. attempt_id is a UUID, never a hash of the inputs: two requests of identical inputs under two request_ids are two Attempts with the same effective_config_digest. effective_config holds the Command, the Workload, the Mode, the Partition, the Configuration (its id and its declared content), the Protocol (id and digest), the input digests (dataset, population, References), the effective parameters (null while running), and the applicable bounds. code_environment holds the Python version, the dependency lock (uv.lock, by digest) and the code revision: the commit, whether the code is dirty and, when it is, a fingerprint of the local code. "The code" is src/, pyproject.toml and uv.lock. No provider secret is written: the process environment is never read into a record. A manifest that is running has no finished_at; a completed one has it, the counts of its Items by execution status (item_counts) and its output_refs.

Observation set. One per Attempt. Its Items are exactly the Items of the Partition (read from the Study's memberships), each produced, failed or missing. population_ref is the memberships artifact, raw_refs the library's own files, normalized_ref observations.csv.

Artifacts and integrity

An ArtifactRef is {path, sha256, size_bytes, media_type, role}: the path is relative to the Study and the digest is of the bytes. A path that leaves the Study (.., an absolute path) or goes through a symlink pointing outside it is refused (ARTIFACT_PATH_OUTSIDE_STUDY), for writing and for reading; a symlink that stays inside is not a traversal.

Publication is atomic (core/artifacts.py): the bytes go to a temporary file in the destination's folder, inside the Study, are flushed and fsynced, then renamed onto the final path; nothing appears under the final path before the rename. A published artifact is immutable: other bytes under the same path are refused (ARTIFACT_IMMUTABLE). When a referenced artifact's bytes no longer match its digest, or the file is gone, reading it back is an integrity refusal (ARTIFACT_INTEGRITY, ARTIFACT_MISSING; exit 3), raised before any computation: run ml reads back the dataset, the memberships and the References of the Study before it computes, and an Attempt it replays.

The canonical JSON and the atomic write were copied from hypotrail/hypotrail at commit 4ef4925 (framework/mlkit/study/understanding/canonical.py, framework/mlkit/study/store.py) and are owned here; nothing is imported from that project.

The Protocol

The StudySpec's protocol_digest is the canonical digest of what binds every Attempt: the Partitions and their ranges, the population and the References by their bytes, the data file by its bytes, the columns, the rules on when information is available (period_k, the forbidden and the allowed target features) and the primary metric. It changes when a Partition range or the References change. It does not change when a Configuration changes, nor with the key order of the declaration. run ml recomputes it from the Workload for a new request and refuses a Workload whose Protocol is no longer the Study's (PROTOCOL_CHANGED, exit 3); a Protocol that changed on purpose is a new revision of the Study (chapter 10).

The question, the objective and the limitations of the StudySpec are declared by the Workload (question, objective, limitations in workload.json, read by init only). The primary metric is mae, lower_is_better, in the unit the Workload declares. study_id is a UUID; revision is the digest of the StudySpec without its study_id and itself. An artifact ID is its kind and the first 16 hex digits of its digest (references-<digest>), so a corrected References set has another ID.

Request identity

--request-id is required for run, for import (chapter 06) and for decide (chapter 17), and must not be empty. A request is identified by the elements below, read from the Attempt manifest itself. The same request_id with the same request returns the recorded Attempt, whatever its status, after reading its artifacts back against their digests: no fit and no prediction happens, and nothing is written. With any element different it is REQUEST_CONFLICT (exit 6), naming the elements that differ, and nothing is written. A wanted rerun uses a new request_id and --retry-of ATTEMPT_ID; the earlier Attempt and its artifacts keep their digests.

A Study has one request_id namespace, for its Attempts and its decisions. A request_id that names a decision is REQUEST_CONFLICT for run and import, and one that names an Attempt is REQUEST_CONFLICT for decide: in both, differs is ["command"] and details carry both attempt_id and decision_id, the one that does not apply set to null. Two decisions under one request_id that differ name, in differs, the fields of the decision record that differ (chapter 17).

Changing ridge.alpha from 1.0 to 10.0 under the name ridge_v1, or changing the dataset, or running another commit, is therefore a conflict under the same request_id; under a new one it is a new Attempt (a changed dataset is then refused as a Protocol change). A different dirty state or fingerprint of the local code with the same commit is a conflict too.

One writer, interruption and retry

The lock. init, run ml, import ml, recover, assess and compare hold an exclusive, non-blocking lock on writer.lock (core/lock.py) for the whole command. A second writer does not wait: it is refused at once with STUDY_LOCKED, exit 6, and writes nothing. The operating system drops the lock when its holder ends, killed or not, so a dead writer never blocks the Study. status takes no lock; it probes whether one is held. The lock needs fcntl (Linux, macOS); elsewhere the writers are refused with LOCKING_UNAVAILABLE (exit 5). The lock mechanism was adapted from framework/mlkit/study/lock.py of hypotrail/hypotrail at commit 4ef4925 and is owned here.

What an interruption leaves. The manifest is written running before anything else, each artifact is published before the terminal manifest, and the terminal manifest replaces the running one atomically, last. A process killed in between leaves the artifacts it had published, no artifact under a final path it had not reached, and a manifest that is still running, without finished_at. No complete state is invented. An error that is raised inside a live process instead leaves the Attempt failed, with a Reason and finished_at, its artifacts kept, and the command exits 4.

Looking and recovering. status shows such an Attempt as it is: running, with recoverable: true when no writer is alive. recover --attempt ID records it as interrupted. It refuses an Attempt that is already terminal (ATTEMPT_TERMINAL, exit 3) and, while a writer is alive, the whole command (STUDY_LOCKED). An Attempt whose Mode calls a provider (llm_live) is recorded with outcome_unknown: true: a lock that is gone is never read as the cancellation of a remote call.

Retry. A retry is never implicit and nothing is resubmitted. The same request_id with the same request returns the recorded Attempt, whether it is running, interrupted or failed, with neither a fit nor a prediction. To run it again, use a new --request-id and --retry-of ATTEMPT_ID: it is a new Attempt, and the earlier one and its artifacts keep their digests.

Immutability. Once an Attempt is no longer running, a write that would change its manifest or its outputs, or add a file to its folder, is refused with ATTEMPT_TERMINAL.

The write sequence

A Study keeps a write sequence: a value that every write to the Study advances and that nothing else changes. It is the number of entries of an append-only journal, write_journal/SEQ.json (core/write_journal.py); an entry is never rewritten. status --json shows it as the top-level key write_sequence, and no other command's output shows it, but the details of the two refusals of --read-sequence (below). It is not a revision of the Study (chapter 10): a revision changes the Protocol, a write only advances the sequence.

Two entries per writing command. A command that writes appends a begin entry just before its first write and an end entry after its last, so a command advances the sequence by 2 and a new Study, created by init, shows 2. A writer killed between its first write and its last has still written: it leaves its begin entry only (a run ml killed after its running manifest leaves the sequence one higher), and the recover that follows adds two. A command that writes and then stops appends its end entry too: a run ml that leaves a failed Attempt, and a compare refused for its coverage after it appended its Exposure entry (chapter 12).

What a command that writes nothing leaves. status, a replay (the same request_id with the same request), a refusal before the first write (STUDY_LOCKED, REQUEST_CONFLICT, PROTOCOL_CHANGED, STUDY_CHANGED, WRITE_SEQUENCE_AHEAD, INVALID_ARGUMENTS, DECISION_FIELD_EMPTY, CITED_ID_NOT_FOUND) and a report whose page shows dev Items only leave the sequence as it was, and append no entry.

The entries. A begin entry holds phase, command and request_id (null for a command without one: init, assess, compare, recover, report). An end entry holds the same three keys, an outcome and written, the ids the command wrote as a list of {"kind", "id"}. The outcome is completed (the command wrote what it set out to write), failed or refused. For run and import, any error after the running manifest is failed, whatever its exit code, since it leaves a failed Attempt. For a command with no Attempt, an error after its first write is failed when it exits 4 and refused when it is a coded error with another exit. outcome may gain values: a reader does not treat that list as closed.

Reading the sequence before a write: --read-sequence N. Every command that writes to a Study takes, as an option, the write sequence its author read (the write_sequence of status --json): init --new-revision, run ml, run agent, import ml, import agent, assess, compare, recover, report and decide, which requires it: without it decide is INVALID_ARGUMENTS (chapter 17). init that creates a Study has no sequence to read and takes no value: --read-sequence with --workload is INVALID_ARGUMENTS. Given and equal to the Study's, the command does what it does without the option. Given and lower, it is refused with STUDY_CHANGED, which names the value read, the current value and writes_since, the journal entries after the value read; given and higher, with WRITE_SEQUENCE_AHEAD; a value that is negative or not an integer is INVALID_ARGUMENTS. Nothing is written in any of these cases. Not given, any other command is not checked at all: direct use stays what it was. report compares the value only when its page records an Exposure; a page of dev Items only is written as without the option.

The value is compared under the writer lock, so a write made by another process between the author's read and the command is caught. The refusals come in this order: the arguments (REQUEST_ID_EMPTY included), STUDY_NOT_FOUND, the lock (STUDY_LOCKED), the request identity (a replay of the same request_id with the same request returns the recorded Attempt, or the recorded decision for decide, and writes nothing, whatever value was read; another request is REQUEST_CONFLICT), then STUDY_CHANGED or WRITE_SEQUENCE_AHEAD, then the command's other refusals (PROTOCOL_CHANGED among them). In run ml, import ml and import agent the refusals that guard the reads the identity needs (UNSUPPORTED_CAPABILITY, DATA_INTEGRITY, ARTIFACT_*, the declaration's codes, RETRY_OF_UNKNOWN) keep their place before it; in run agent, whose identity reads its input bytes directly, DATA_INTEGRITY and ARTIFACT_* come after the check. An older value with corrupt data is therefore STUDY_CHANGED in run agent and DATA_INTEGRITY in run ml; neither writes anything.

A Study written before this version holds no journal and shows write_sequence 0 until its first write. Its files are never rewritten.

Limits

No resume engine, POSIX locking

An interrupted or failed Attempt is never continued: a retry is a new Attempt (a generic resume engine is out of scope). The lock needs fcntl; on Windows the writers are refused. A status probe holds a shared lock for an instant, so a writer that starts at that very moment is refused (it writes nothing) and can simply be run again. recover leaves the unpublished scratch files of a dead writer in .scratch/.

No scoring, no Comparison

run ml does not score: assess does, in a separate step (chapter 05), and compare compares two Assessments in another (chapter 07). An import is a separate command (chapter 06).

No freeze at run time

A run ml on public_check is recorded like any other and is not an Exposure: it scores nothing, so it writes no freeze record and no journal entry. The Exposure is the Assessment or the Comparison (chapter 12). After the Study's first Exposure, a run ml of a Configuration the freeze record does not hold is not refused: its Attempt is marked check_informed.

Two Tracks, one native each

run ml serves the temporal regression Track only. A Chinook Study (init) takes answers produced elsewhere with import agent (chapter 08) and records its own native Attempts with run agent (chapter 13), which follows the order, the request identity, the lock and the manifest described here.

The Scorer registry

The registry is a static, closed table in the code. A --scorer value is a key of that table and nothing else: it is never imported, evaluated or looked up by name, so a string such as package.module:function loads no Python and is refused as a Scorer that is not registered. A Scorer belongs to one Track (its domain); one applied to an Observation set of another Track is refused. chinook_contract_v1 is the Scorer of the agent Track (version 3); it has four Criteria and no Metric of its own, and its Assessment is described in chapter 08.

Both Scorers have the same Criterion, the absolute error of the day, and differ in the Metric they aggregate from it: mae, the mean of the absolute errors, and rmse, the square root of the mean of their squares. The Metric's unit is the one the StudySpec declares for the primary metric; its direction is lower_is_better. The config_digest is the digest of the Scorer's configuration (the Criterion, the Metric and the direction): another Metric is another digest.

What is checked, in order

  1. The Study exists; the Scorer is in the registry.
  2. The Observation set and the References set exist in the Study (the References set of the current revision: an earlier revision's set is refused with REFERENCES_NOT_FOUND), and the Scorer belongs to the Observation set's Track.
  3. Every artifact read is read back against its digest: the Observation set record, the normalized outputs, the raw predictions it was made from, the population and the References. One that no longer matches is an integrity refusal (chapter 04, ARTIFACT_INTEGRITY, exit 3) and nothing is written.
  4. The Partition of the Items is dev or public_check; any other Partition (train) is refused.   5. The Items of the Observation set must be Items of that Partition, each once.

The execution status of the Item (produced, failed, missing) stays separate, in its own column. An expected Item that the outputs do not hold at all is missing.

The mapping is a JSON object of strings. A key that is not in the table is refused, and so is a missing required key. What is checked, in order

  1. The Study exists and the writer lock is free; the Workload's data is verified against its lock and the Study's artifacts are read back against their digests (chapter 04).
  2. The three files are read and their sha256 taken. The request is identified (below). The same request_id with the same request ends here with the recorded Import: the source is not validated again, and nothing is written or scored.
  3. The Protocol of the Workload is still the Study's (PROTOCOL_CHANGED, chapter 04).
  4. The mapping, then the source file (data and not a serialized object, valid UTF-8, a readable CSV that holds the mapped columns), then the population are checked. The dataset digest of the mapping is compared with the lock's.
  5. Every row of the source is joined to the population by ID: no empty ID, no repeated ID, no ID outside the population, a finite number in y_pred; every Item of the population must be present. A population smaller than its Partition is allowed: assess counts the Items of the Partition that the file does not hold as missing.
  6. Only then is anything written: the running manifest, the original files, the validation report, the normalized Observations and the Observation set, and the terminal manifest last. A refusal at steps 4 or 5 writes nothing at all. An error inside the process after the manifest is written leaves a failed Attempt with a Reason, as in chapter 04.

Nothing in an import is executed or deserialised as code. A source with the extension of a pickle, joblib or array dump, or whose first byte is the pickle marker, is refused as SOURCE_SERIALIZED before it is read as text.

What the Import keeps

Comparison

compare takes two Assessments of a Study, one named the Control and one the Candidate, and writes a Comparison record into the Study. It reads what the Study keeps (the Assessments, their per-Item files, the Observation sets and Attempt manifests they point to) and nothing else: it fits nothing, predicts nothing and calls no model. A Comparison is strict when everything that makes two Assessments comparable holds, and descriptive when one side is an Import. Items are aligned by row_id, and a Comparison never rests on a hidden intersection: if the Items differ by one, it is refused. This chapter describes the temporal regression Track, on dev; the Comparison of two agent Assessments, which aligns Episodes by Case and Repeat, is chapter 11, and the report and the Exposure journal are later work (see Limits).

The command

compare is in src/hypotrail/cli.py; the work is in src/hypotrail/core/comparison.py, a core module (ADR 0001): it imports neither a Track, scikit-learn, NumPy nor Inspect, and runs where Inspect is not importable. It follows the rules of chapter 04: with --json, stdout holds one JSON object, {"ok": true, "comparison": RECORD} or {"ok": false, "error": {"code", "message", "stage", "details"}}, and the diagnostics (the scope warning of a descriptive Comparison, the refusal) go to stderr; without it, stdout holds one line. Agent answers: Study, import and Assessment

init --workload chinook creates a Study of the tool-using agent Track. import agent adopts answers produced elsewhere, as JSON Lines, as an Import Attempt of that Study: one line for every expected Case and Repeat, a failed or missing line included. assess --scorer chinook_contract_v1 scores the kept Observation set with the Scorer of chapter 03 and writes an Assessment: four Criteria per Episode, each with a state and a Reason for every non-score, the counters of CMP-03 and the two named rates of CMP-04. Nothing here runs a model or a tool, opens the Chinook database or imports Inspect. This chapter describes what exists for JSONL answers, on dev; an Inspect log, which needs Inspect, is chapter 09.

A Chinook Study

init reads the Workload's track: tool_using_agent goes to src/hypotrail/agentic/study.py, temporal_regression to the code of chapter 04. The data is verified against its lock first (this one check opens the database and counts its tables); nothing is created before it passes. The Study then keeps a copy of the database and three Study artifacts, each with an ID: the memberships (which Partition each Case belongs to), the References set exactly as the Workload declares it, and the answer schema (table-answer/1) the Scorer checks answers against. The References set is therefore frozen in the Study: assess reads no Workload file.

The Study's primary metric is the primary Criterion of its Assessments. The Workload declares it as data (primary_criterion in examples/chinook/workload.json, closed to the four Criteria of the Scorer by workload.schema.json) and init copies it into the StudySpec, so it is frozen with the Protocol. The log is read with read_eval_log and nothing else: there is no hand-written parser (ADR 0001). Revisions and corrected References

A Study holds one frozen Protocol per revision, and a Protocol change is a new revision inside the same Study. A corrected References set changes the Protocol, so it is added with init --study DIR --new-revision. So is a changed Case text, which is part of the Protocol too: a Study created before the change refuses a new request with PROTOCOL_CHANGED until init --study DIR --new-revision adds the revision that holds the new text. For a corrected References set, the corrected set is published beside the old one, the StudySpec of the earlier revision is kept as it was, and nothing an earlier revision references changes by a byte. An Assessment of a corrected set scores the same Observation set again, and says which earlier Assessment it differs from and why, so a corrected Reference is never read as a change of the evaluated system.

The command

init --new-revision is in src/hypotrail/cli.py; the work is in src/hypotrail/core/revisions.py and, for each Track, in the new_revision function beside init_study (src/hypotrail/ml/study.py, src/hypotrail/agentic/study.py). The Study names its Workload, so the command takes no --workload (giving one is INVALID_ARGUMENTS, as is init with neither). It reads the Workload again, from --examples-dir or the checkout's examples/ (chapter 04), verifies its data against the lock before anything is written, and derives the Protocol it declares now: the population, the Partitions, the References, the rules on when information is available. With --json, stdout holds {"ok": true, "study": SPEC} with the new revision's StudySpec, or the error object of chapter 04; without it, one line.

The command holds the Study's writer lock for its whole execution, as every command that writes to a Study does: a second writer is refused at once with STUDY_LOCKED (exit 6) and writes nothing.

# the new References ID is in `artifacts` of study.json and in `status --json`
uv run python -m hypotrail status --study runs/chinook --json

What a revision keeps and what it adds

Every artifact the Protocol freezes (the dataset, the population, the References, the answer schema) is compared by its bytes with the one the current revision holds. One whose bytes did not change is carried over as it is: same path, same digest, same ID, same version. One whose bytes changed is published beside the earlier one, under a path that names its first sixteen digest digits, with the next version number and an ID that names its digest; the earlier file is never replaced. A References set is versioned as a whole: version 1 is the set init froze, version 2 the first corrected set.

study.json always holds the current revision, so every other command keeps reading one file. When a revision is added, the StudySpec of the one before is copied byte for byte to revisions/N/study.json, the new StudySpec is published as revisions/N+1/study.json, and study.json is replaced last, atomically. A writer killed between two of these steps leaves the earlier revision current; running the command again completes it. study_id stays the same for the life of the Study; revision is the digest of the StudySpec without its revision and study_id, so it differs from one revision to the next, and previous_revision chains each revision to the one before.

A Workload whose Protocol is the one the current revision already freezes is refused with PROTOCOL_UNCHANGED, and nothing is written. A Configuration is not part of the Protocol: changing one needs no revision (chapter 04).

Comparing two agent Assessments

compare on two Assessments of a Chinook Study works as it does on the bike (chapter 07), with what an agent adds: the Items are Episodes, aligned by Case and Repeat; the two sides must share their planned Repeats, tools, model and budgets, except for the factor the request declares as intentional; each side keeps its Case × Repeat matrix; and, when every Episode is scored on both sides, each Criterion is aggregated per Case first and every Case weighs the same. The main delta is that of the primary Criterion, contract_success. With one Episode missing, the Comparison shows the coverage and gives no main delta. A Chinook side is an Import (chapter 08, chapter 09) or a native llm_live Attempt recorded by run agent (chapter 13). A Comparison with an Import on either side is descriptive; the strict path is two native llm_live Attempts, witnessed offline by two Attempts recorded with Inspect's mock model in place of the provider, which only a test can do. An Attempt of the scripted_fixture Mode is never assessed, so it is never compared.

The command

The command is the one of chapter 07, with one more flag. The work is in src/hypotrail/core/agent_comparison.py, a core module (ADR 0001): it imports no Track, no scikit-learn, no NumPy and no Inspect, and hypotrail.core.comparison loads it for an Assessment of an agentic Observation set. --factor names the factor that is intentionally different between the two sides; it defaults to configuration, the factor of plain against verify (the verify Configuration adds one explicit instruction to plain and changes nothing else). On a Study of another Track it is refused with UNSUPPORTED_CAPABILITY (exit 2). The command holds the Study's writer lock for the whole command and follows the --json rules of chapter 04.

What is checked, in order

The checks run in this order, and the first one that fails refuses the Comparison with its own code and exit 3; nothing is written. A Partition other than dev and public_check is refused right after the population (COMPARISON_PARTITION_NOT_DEV, exit 2), as in chapter 07; a public_check Comparison is journaled once every check has passed (chapter 12). The population of an agent Comparison is the Partition and the Cases; the Repeats have their own check, so that a difference in Repeats can be declared. The References, Scorer and unit checks are those of chapter 07, with the same codes. The refusal's details carry the check, its Reason, the values of both sides and the checks evaluated so far.

For tools, model and budgets, each side establishes what it can: a native Attempt's manifest records them; an Import declares its model and tools in the lines of its file, and its budgets in the header of an Inspect log, or leaves them unknown (chapter 06). A check compares what both sides establish. When a side does not establish it, the check is recorded as failed with the Reason not_established, nothing is refused, and the Comparison is descriptive. Strict against descriptive

A Comparison is compatible (strict) only when every check passed and both sides were produced by Hypotrail. It is descriptive_only when a side is an Import, whatever the origin of the fields the Import declares, or when a native side does not record a factor. Episodes, the matrix and the Case weight

Episodes are aligned by (case_id, repeat), never by position. The Comparison takes the union of the two sides' Episodes and drops none: an Episode on one side only (possible only when repeats is declared) and an Episode not scored for the primary Criterion on a side both show in coverage, as counts and as rates of the expected Episodes. matrix.json keeps each side's Cases × Repeats matrix: for each Case and Repeat, the execution status and, for each of the four Criteria, the state, the score and the Reason.

With full coverage, every Episode scored for the primary Criterion on both sides, the Criterion is aggregated per Case first: a Case's share is the share of its Repeats scored true. The value of a side is the mean of the shares of its Cases, so every Case has the same weight and the three Repeats of a Case are never counted as three Cases (they are not independent). The delta is the value of the Candidate minus the value of the Control; a positive value means the Candidate is better, since the Criterion is higher-is-better. paired_deltas.csv holds one row per Case. The main delta, delta, is that of the primary Criterion (contract_success, declared by the Workload and frozen by the Study); secondary_deltas holds the other three Criteria, each with its own coverage rule.

Without full coverage, delta.value is null and delta.reason is coverage_incomplete; paired_deltas_ref is null, so no per-Case table hides the gap. No binomial or other interval is computed over Episodes, and the limitations say so. A correct answer without a trace leaves contract_success unscored (trace_missing, chapter 05), so an import without traces gives no main delta unless every answer is wrong or needs no tool call.

The rates, and what is only described

rates repeats, for each side, the two named rates of its Assessment with the unknowns beside them: quality_among_scored (correct among scored) and confirmed_share_of_expected (correct among expected), the Episodes unscored or errored and their Reasons, and the failed and missing Episodes. A rate whose denominator is zero is null with a Reason, never 0. descriptive reports, for each side, latency, the numbers of model and tool calls, tokens and cost. These are descriptive only: no Criterion and no delta rests on them, and no cost is compared. Calls are counted from the kept traces and are null unless every Episode that ran has one; latency and tokens are the sums of what an Inspect log import kept for each Episode (chapter 09), and are null unless every Episode that ran has them, so a JSONL import or a partial log gives null; cost is always null, because no Observation set keeps it. None of them is ever filled with 0.

Freeze, Exposure and check_informed

A Study may use its public_check Partition, and it records every use. Before the first use in a Study revision, the revision holds a freeze record: the digests of its Protocol, of every Configuration the Workload declares, of the environment and of the code. Every Assessment or Comparison that touches public_check Items, native or imported, for either Track, is an Exposure and is appended to the Study's journal. What the first Exposure may have informed is marked check_informed. A Study with no journal entry says that it recorded no Exposure and that any earlier exposure is unknown; nothing here claims that public_check was never seen.

What the commands do

assess, compare and report (chapter 14) record Exposures; a report that shows public_check Items records one even with no Assessment. assess and compare do the work, in src/hypotrail/ml/assess.py, src/hypotrail/agentic/assess.py, src/hypotrail/core/comparison.py and src/hypotrail/core/agent_comparison.py; the freeze record, the journal and the marks are in src/hypotrail/core/exposure.py, a core module (ADR 0001). The three commands take an optional --examples-dir, read only when the Items are public_check ones, to digest the Workload as it is declared now (default: the checkout's examples/, as chapter 04 says).

  1. The usual checks run first (chapters 05, 07, 08 and 11). A refusal there writes nothing.
  2. For public_check Items, the Workload's Protocol is digested again and compared with the one the current revision froze. A difference is refused with PROTOCOL_CHANGED (exit 3) and nothing is written: a Protocol change is made with init --study DIR --new-revision (chapter 10).
  3. If the revision has no freeze record, it is written now, before anything is computed on public_check Items. It is never rewritten, and a revision gets its own at its own first use.
  4. One journal entry is appended, pointing to that freeze record, and only then are the Items scored or paired. The entry is published atomically under the writer lock and never rewritten. An Assessment lists its Attempt and its own ID; a Comparison lists the Attempts and the Assessments of both sides and its own ID.
  5. The Workload's current digests are read through a function the entry point passes in (the Track's freeze_basis), so the core imports no Track. A Configuration's digest itself is computed by one function of the core, exposure.configuration_digest, which freeze_basis of each Track calls and which check_informed calls on an Attempt's manifest, so the two cannot drift. A library call that records an Exposure without passing that function (a Comparison of public_check Items through core.comparison.compare with no live_basis) is refused with WORKLOAD_BASIS_REQUIRED (exit 2) and nothing is written. The basis function is called with the StudySpec the command read under the writer lock, so the digests and the revision they are compared with come from the same read. For a Chinook Study the database part of the Protocol digest is the digest of the Study's own copy: neither import agent nor assess opens or hashes the live file, so a replaced database goes unnoticed by them; init, init --new-revision and data verify are what catch it. The freeze record says so in dataset_source.

An entry written for a Comparison that is then refused at its coverage check stays: the Items were read, and the journal is not rewritten. Its Comparison ID names no Comparison. run ml on public_check is not an Exposure: it produces predictions and scores nothing.

# an Attempt on public_check, then its Assessment: the first Exposure of the Study

Running the agent into a Study

run agent records a native Attempt of the tool-using agent Track in a Chinook Study, from the Inspect log of the Attempt, the way run ml records a Bike Attempt (chapter 04): the same order of checks, the same request identity and replay, the same running-then-terminal manifest, the same atomic artifacts, the same writer lock, status and recover. It has two Modes. scripted_fixture runs the Workload's seven technical scenarios with Inspect's mock model and the real tools, and records the scenario Attempt: a test of the instrument, with a labelled self-check, that is neither assessed nor compared. llm_live runs one Configuration on one Partition (dev or public_check), optionally on some of its Cases, for one to three Repeats, against an explicit Anthropic model; it is opt-in, bounded and paid, and it is never part of the tests.

The command

The order

Nothing is run before the checks that precede it, and the first refusal ends the command. The order is the one of the decision on chadlis/hypotrail#74:

  1. The flag checks (exit 2), against the Workload's declaration only: the flags of the other Mode, the Configuration, the Partition (dev or public_check), the Repeats (1 to 3), the model (anthropic/<model>), the Cases (each a Case of the Partition, none repeated). They come before the key is read and before Inspect is imported. Together with the Repeats bound they make the bound of the Attempt: at most the Partition's Cases times three Repeats, that is 24 Episodes on dev. spike live keeps its own bound of two Episodes on dev.
  2. The writer lock (STUDY_LOCKED, exit 6): a second writer is refused at once. Then --retry-of must name an Attempt of the Study (RETRY_OF_UNKNOWN, exit 2).
  3. The request is identified (below). The same request_id with the same request returns the recorded Attempt here: no key, no Inspect, no provider call, no scan. With another request it is REQUEST_CONFLICT. The identity is taken before the data is verified, so a database changed on disk is a changed request (the file's digest differs), and a References set changed by a new Study revision is too.
  4. The Workload's data is verified against its lock (DATA_INTEGRITY, exit 3), and every Study artifact read is read back against its digest (ARTIFACT_INTEGRITY, exit 3).
  5. For a new request, the Workload's Protocol must still be the Study's (PROTOCOL_CHANGED, exit 3).
  6. Inspect must be importable (INSPECT_UNAVAILABLE, exit 5), in either Mode; then, for llm_live, HYPOTRAIL_ANTHROPIC_API_KEY must be set and no variable that would override it (LIVE_UNAVAILABLE, exit 5). Nothing is sent without the key. scripted_fixture never reads the key.
  7. The manifest is written running, the Episodes are run, the artifacts are published atomically and the terminal manifest is written last.

An Attempt stopped between its running manifest and its terminal one keeps what it published and is never shown as completed. status shows it as recoverable and recover records it interrupted, with outcome_unknown: true for llm_live, since a vanished lock does not prove that the provider call was cancelled. Nothing is resubmitted. A recorded Attempt may hold failed Episodes (an error of the provider, a limit): it is completed, exit 0, and the failed Episode has a Reason and no invented answer.

The files of an Attempt

Inspect owns the agent loop and its log. The log is written outside the Study, into a folder that is removed at the end; it is scanned for the key, then read through Inspect's public log API (never parsed by hand, ADR 0001) and kept in the Attempt as a raw artifact. The key is read from HYPOTRAIL_ANTHROPIC_API_KEY and nowhere else, and is given to the provider explicitly. For an llm_live Attempt, every file the Attempt writes, the running and the terminal manifests included, is scanned for the key before it is written. The scan is made whether or not the Attempt failed: after a failed Attempt the same warnings are on stderr and in error.details.warnings of the --json object, and the exit is the error's. A replay runs no scan.

The scenario Attempt

scripted_fixture runs every scenario of the Workload once (SCN-01 to SCN-07, SCN-07 never run, so missing), through the real tools and the same task, projection and Scorer code as a live Attempt, with the model mockllm/model. Limits

Tool calls are not capped

Inspect has no limit on the number of tool calls; the manifest says so in limit_notes. The turn limit bounds them indirectly.

The Campaign ran once

The 72-Episode Campaign on public_check is two invocations of this command, run on 2026-11-21 and kept as they were recorded; its order of Configurations is not alternated (chapter 16).

One provider

Only anthropic/<model> is accepted, with the key sent to that provider alone. The model licence line of the specification does not apply to a remote provider, and no field records one.

A scan is not a proof

The scan finds the key as written, in a file or decoded from a log; it does not find the key in an altered form.

Report

The Study report

report renders one HTML page for a Study of either Track, the temporal regression Track (Bike) or the tool-using agent Track (Chinook), from the Study's records alone: the Attempts, Observation sets, Assessments, Comparisons, the freeze record and the Exposure journal. The page holds its text, styles and tables inline, loads nothing, has no script and computes nothing when it is opened. A page that shows public_check Items is an Exposure and is recorded as one.

The command

python -m hypotrail report --study DIR --out FILE, with --json, --examples-dir DIR and --read-sequence N (the flags are in the commands table of chapter 04). The code is src/hypotrail/report/: gather.py reads and verifies the records (gather_agent.py adds what a Chinook Study holds), render.py writes the page and its sections (render_agent.py writes the sections that differ for a Chinook Study, markup.py holds the escaping building blocks), command.py is the command. It imports neither Inspect nor scikit-learn nor NumPy (ADR 0001), and it calls no fit, no prediction, no model and no tool, so it works with the network cut. An Inspect log is never opened: the page links to it.

  1. The Study is read, whichever Track it is of. --out must not be inside the Study, nor a directory, and its folder must exist.
  2. Every artifact the page shows is read back against its digest: a changed byte is ARTIFACT_INTEGRITY (exit 3) and no page is written.
  3. If the page shows public_check Items, the Study's writer lock is taken (a second writer is STUDY_LOCKED, exit 6), --read-sequence, when given, is compared with the Study's write sequence (STUDY_CHANGED, exit 6, or WRITE_SEQUENCE_AHEAD, exit 2; nothing is written, no Exposure and no page), the Workload is found through the one resolver of chapter 04 and its Protocol is checked against the revision's (PROTOCOL_CHANGED, exit 3), the freeze record is written first if the revision has none, then one journal entry names the Attempts, Assessments and Comparisons the page shows of those Items (chapter 12). A Study whose Items are all dev records nothing, takes no lock, reads no Workload and does not compare --read-sequence.
  4. The page is written to a temporary file beside --out and renamed onto it: an existing file is replaced.

The page is rebuilt from the Study each time it is asked for; it is never stored as a record. Two reports of the same public_check Study record two Exposures.

Data

Acquiring the data: data fetch

data fetch acquires a Workload's public sources from the URLs of its data-sources.lock.json. Each file is downloaded to a temporary file, bounded while it arrives, checked against the lock's SHA-256 and published by an atomic rename. It never chooses a mirror or another URL, never replaces a file that is there, and the files it publishes pass data verify like the committed bundle.

The command

python -m hypotrail data fetch --lock LOCK --dest DIR, with --json. With --json, stdout holds exactly one JSON object and the human diagnostic goes to stderr; every error has code, message, stage and details. The code is src/hypotrail/core/fetch.py (standard library only).

FlagRequiredMeaning
--lock LOCKyesThe data-sources.lock.json to acquire. Its sources and their URLs are the only input; no URL is ever taken from anywhere else.
--dest DIRyesThe Workload directory the files are published in: each source lands at its lock's local_path under it, and each licence notice at its notice path.
--jsonnoPrint one JSON object on stdout.
# acquire a checkout's data in place: only a missing file is downloaded
uv run python -m hypotrail data fetch --lock examples/bike_day/data-sources.lock.json --dest examples/bike_day
uv run python -m hypotrail data verify
# a clean install into a directory of its own, then verified there
uv run python -m hypotrail data fetch --lock examples/chinook/data-sources.lock.json --dest my-examples/chinook
uv run python -m hypotrail data verify --examples-dir my-examples --workload chinook

What it does, in order

  1. The lock is read. Not valid JSON, an unknown schema_version (only data-sources/1 is read), or a key the fetch needs that is missing is a refusal with exit 2, before any download. The keys a source needs are dataset_id, download_url (an http or https address), local_path, sha256 and size_bytes; an archive source adds archive_sha256 and member; a source with a notice_url adds notice and notice_sha256.
  2. Every path that is written stays inside --dest. A local_path, a notice or a member that is absolute or holds .., and a destination whose path to the published file passes through a link that leads outside --dest, are refused with exit 2 before any download and with nothing written.
  3. The files already there are compared with the lock, before any connection. A file that matches (SHA-256 and, for a data file, size) is left as it is, is not downloaded again and is reported present. A file that differs is refused with exit 3 and is left unchanged byte for byte: a fetch never replaces a file. To acquire a file again, remove it first. A missing file is downloaded.
  4. Each missing file is downloaded from its lock's download_url and from no other address, to a temporary file in the directory it will be published in. The redirects that URL answers with are followed, at most 5 hops and https only; a redirect to an address that is not https (a downgrade) or a sixth hop is a failed transfer, with no fallback. The command holds no list of allowed hosts: the lock's SHA-256 is the only gate on what arrives, and the timeout and the bounds below apply to the file that finally arrives. The download stops as soon as it passes its bound. Then the SHA-256 (and the size, for a data file) is checked against the lock, and only then is the file published by an atomic rename; the temporary file never outlives the command.
  5. The Bike source is an archive. The archive is checked against archive_sha256 before it is opened; only the lock's member (day.csv) is read from it, and only as a stream into a second temporary file: no archive path is ever joined to the destination. An entry that is a link, or not a regular file, is refused. The extracted file is checked against the lock's sha256 and size_bytes before it is published.
  6. The Chinook licence notice is downloaded from the lock's notice_url and checked against notice_sha256, under the rules above. The Bike lock has no notice_url: its notice is not fetched and is reported absent (the committed notice stays where it is).

The files are published one at a time, each only after its own check. If a later file is refused, the files already published stay, and each of them matches the lock.

Bounds

A data file downloaded directly is bounded by its lock's size_bytes, and the member extracted from an archive by the same size_bytes, whatever the archive says of it. Any download whose lock gives no size (an archive, a notice) is bounded by one generic cap: 67108864 bytes (64 MiB). The cap names no Workload and is the same for every lock. A body that announces a length past its bound is refused before it is read, and one that does not is stopped as soon as the bytes read pass the bound.

The result

With --json: {"ok": true, "sources": [...]}, one entry per source in the lock's order, each with dataset_id, file (the local_path), status (fetched or present), sha256, size_bytes and notice (file and status: fetched, present or absent). data verify then checks the published files with the same checks as the committed bundle: the bytes, the licence notice and the content. A byte altered after a fetch is refused by data verify with exit 3.

There is no automatic mirror. When a transfer fails, the message names the explicit alternative: the already verified bundle, checked with data verify on the committed data of a checkout. A failure reports the final host (the one the request had reached) and never a URL, a path or a query string, so a signed address is never printed.

The command takes the framing of a response from the framing http.client computed for it, and parses no Content-Length or Transfer-Encoding header itself; the framing http.client computed is read before the first read. It reads a body as chunked, or as framed by a length (a Content-Length that is an integer and not negative; a signed +12 is read as 12), or as unframed, with no length, so that the close ends it. It ignores a Content-Length on a chunked body, one that is not a number, and a negative one: such a response is chunked or unframed. A connection cut in the middle of a transfer then ends in one of these ways. A body framed by a length that closed before it arrived, and a chunked body that closed before its last chunk (the client reports an incomplete read), are DOWNLOAD_FAILED with reason interrupted, exit 4. So is an unframed body that delivered fewer bytes than the lock's size_bytes: only fewer bytes than size_bytes triggers it. In all three nothing is published, the temporary file is removed, and the message names the already verified bundle. An unframed body of an equal size (the lock's) with a wrong hash, and a framed body that arrived whole but differs, are DOWNLOAD_INTEGRITY, exit 3. The limit: where the lock gives no size (an archive, a notice), an unframed short body cannot be told from a differing one by HTTP; it stays DOWNLOAD_INTEGRITY, exit 3, and its message says so and names the already verified bundle (data verify on the committed data) as the explicit alternative. Only that case carries the note that a server may have cut the body short; a framed body that differs does not.

Where the tests stand

No test reaches the network. A stand-in server on the loopback interface serves every download, a replaced opener serves the one that must be stopped early, and the network guard of tests/conftest.py stays on. The committed locks name the UCI and GitHub hosts; no test opens them, and the lock's landing_url is never opened by the code. The stand-in speaks http, so the https-only rule is witnessed without TLS: a redirect to the stand-in is refused as a downgrade, a test that follows hops widens the allowed schemes for its own duration, and the redirect handler is also tested directly with https and http targets. The first fetch against a real host is therefore a step an installer does, not one the suite has done.

Decisions

Decisions

decide records one decision in a Study: the question it answers, the option chosen, who decided (a human or a proxy, with a declared source if any), the ids of the Study's records it concerns, and the write sequence its author read. The Study is the only decision authority: a decision is a record of the Study, kept in a file of its own and never rewritten, and nowhere else. decide calls no model; it records what its caller says, after it has checked the ids and the sequence.

The command

decide holds the Study's writer lock for the whole command, as every command that writes does: a second writer is refused at once with STUDY_LOCKED and nothing is written. It requires --request-id and --read-sequence (chapter 04): a decision is made on the write sequence its author read, and a decision made on an older sequence is refused with STUDY_CHANGED, which names what was written since. Given the current sequence, decide records the decision and advances the write sequence by 2, like every command that writes. It creates or changes no file outside the folder given by --study.

The question and the option are free text, and neither may be empty. The author is human or proxy, recorded by its kind only: a human has no name field. --source is a declared source, a text, optional for either author; it is recorded as given, or as null. --artifact ID is repeated for each id the decision concerns, and at least one is required. A duplicate is recorded once and the ids are sorted, so the same ids in another order are the same decision.

The ids a decision may cite

An id is citable when the Study holds a record with that id, of one of these kinds: an Attempt, an Observation set, an Assessment, a Comparison, a Study artifact (references-<digest>, for example), a revision, a freeze record, an Exposure entry or a decision, whose id is its decision_id. decide looks the id up in the Study's records. A revision is cited by its revision value, the id check_informed gives it; its revision_number is not citable, so that one revision never appears under two ids and "the same decision" stays one thing. A request_id, the study_id, a path and a file's content digest (sha256, protocol_digest) are not citable either: they name no record. An id the Study does not hold is refused with CITED_ID_NOT_FOUND, which lists every unknown id, sorted, and nothing is written.

status --json lists no Observation set, Assessment or Comparison: a caller finds those ids in the Study's records, and the listing of them in status --json waits for a later change. It does not list decisions yet either.

The request identity

A Study has one request_id namespace, for its Attempts and its decisions (chapter 04). "The same decision" is the same question, option, author, source and cited ids, the ids de-duplicated and sorted; the read sequence is not part of it. The same request_id with the same decision is a replay: it is found before the stale-sequence check, so a client whose answer was lost can repeat its decide after its own write moved the sequence on. It returns the recorded decision with replayed true and writes nothing.

The same request_id with another decision is REQUEST_CONFLICT (exit 6). Its differs lists, in this order, the fields among question, option, author, source and cited_ids that differ, under the decision record's own field names, and decision_id names the recorded decision. A request_id that names an Attempt is a conflict too, with differs ["command"], attempt_id set and decision_id null; and a request_id that names a decision is a conflict for run and import, with decision_id set and attempt_id null.

The checks come in the order of every writer: the arguments (REQUEST_ID_EMPTY, DECISION_FIELD_EMPTY, the author), STUDY_NOT_FOUND, the lock, the request identity, STUDY_CHANGED or WRITE_SEQUENCE_AHEAD, then CITED_ID_NOT_FOUND. A refusal appends nothing to the write journal.

The decision record

The record is canonical JSON, of the record kind decision of the contract schema (DecisionRecord): validated before it is written and after it is read, with a fault reported as CONTRACT_VIOLATION. revision is the revision of the Study's current StudySpec, read under the lock after the stale-sequence check, so a decision made after init --new-revision holds the new one. write_sequence is the position, in the write journal, of the begin entry of the decide that recorded it; read_sequence is the value its author read, and for a recorded decision it is always write_sequence minus 1.

Limits

No history, no outdated mark

decide only records. status --json does not list the decisions, and nothing says whether a decision still applies after the Study changed: that is read from the records later and is not part of this command.

Free text, no declared question

The question and the option are the caller's words. The Study declares no question with options yet, so nothing checks that an option is one of a list.

A decision is not an Exposure

Recording a decision reads no public_check Item and writes no freeze record or journal entry of the Exposure journal. It cites ids; it does not show what they hold.
