Spike

Feasibility spike

The spike proved on the target machine that the chosen stack works before anything general is built: a locked Python 3.13 environment, both public datasets verified, an Inspect task where a model calls a read-only SQL tool on Chinook, and a live trace of a real model doing it. This chapter is the reference for what exists, how to run it and where it stops.

Install and run

The project is a uv project on Python 3.13 with a committed lock. The core needs the standard library and one schema validator, jsonschema; the Inspect and the machine-learning dependencies are optional extras (agent and ml).

# core only: the standard library and jsonschema
uv sync --locked
uv run python -m hypotrail --help

# everything the spike needs, then the offline test suite (no network, no model call)
uv sync --locked --all-extras
uv run --locked --all-extras pytest

# the Python version is pinned by .python-version and requires-python (3.13 only)

The default test command never calls a model, even when a model key is present: every test runs with outbound network access blocked, and an attempt fails the test. Live calls are opt-in and never part of the suite.

Data verification

The two public datasets live in the declarative Workloads examples/bike_day and examples/chinook, each with the slice of data-sources.lock.json that covers it and a data-checks.json that declares what to check. Verification works offline, in a fixed order: the bytes of every selected dataset first, then the licence notices, then the content.

uv run python -m hypotrail data verify                  # both datasets

The Inspect spike

The agentic side lives in src/hypotrail/agentic/; the core never imports Inspect (ADR 0001). Inspect owns the agent loop, the tool calls, its limits and its log; Hypotrail owns the scoring function and reads the log only through Inspect's public log API.

  • Task (runner.py): a system message and a user message per Case, the tools, then Inspect's own generate-and-call-tools loop. The task is now built from the Workload declaration; see the chapter on the agentic Track.
  • Tool (sql_tool.py): query_readonly(sql) opens the Chinook file read-only at a path fixed by the application, one connection per execution, execute and never executescript, extensions disabled. mode=ro covers only the main database, so three native SQLite mechanisms decide what runs, and no SQL text is inspected (no regular expression, no SELECT test): the limit on attached databases is 0; execute takes one statement; and an authorizer holds the allow-list, which is SELECT, reads of the tables the file itself declares (read from the file, never named in code, so its system tables such as sqlite_master stay refused) and the functions count, sum, avg, min, max, round, lower, upper, coalesce, ifnull and strftime. Everything else is denied: writes and DDL, ATTACH, DETACH, PRAGMA, transactions, VACUUM (also INTO), extension loading, recursive queries and any other function, so a statement that starts with WITH or SELECT but needs a denied action is refused. It returns columns, rows, row_count, truncated, error and a tool_call_id. A refused or failed statement sets error to a code (DENIED_ACTION, SQL_ERROR or MULTIPLE_STATEMENTS), a type and a message; the code is what to rely on. Four per-query caps bound every call (row, size, time and instruction count; see the agentic Track chapter).
  • Projection (projection.py): one record per Case x Repeat, in the order model turn, tool call, tool result, model turn, final answer. A Repeat is 0-based; Inspect's epoch is 1-based. An Episode is produced, failed (execution stopped with an error, at one of our limits before a final answer, or with its answer cut by the output cap) or missing (absent from the log).
  • Scoring (core/answer_scoring.py): compares status, reason, columns, rows and unit with the frozen Reference. An answer missing one of the six required fields (status, reason_code, columns, rows, unit, evidence) is malformed: parsed is false and every component is false, even when the Reference holds null there. No string-to-number conversion, a boolean is not an integer, NULL stays NULL, non-finite numbers are refused, and the Reference's absolute tolerance applies. agentic/rescore.py rescores a kept log without the model, the tool or the Chinook file; since ticket #45 it goes through the chinook_contract_v1 Scorer (see the agentic Track chapter).
  • Limits (limits.py): set through Inspect's own options and read back from the log.
  • Live run (live.py): python -m hypotrail spike live --config plain --model anthropic/<model> --out DIR. Opt-in and paid. See below, and the agentic Track chapter for the two commands.

Effective limits

The proposals are 6 model turns, 8 tool calls, 60 s, 12 000 tokens, 1 024 output tokens per call, concurrency 1, response cache off and no retries. The column "Effective" is what the live run's Inspect log recorded, read back through the public log API. A limit is either shown enforced (a named offline test makes a scripted model exceed it), configured, not witnessed, or not enforceable.

The live run

spike live runs one named Configuration of the spike task on at most two dev Cases (D03 and D05 by default), one Repeat each, under the limits above. It scores nothing against References; it only shows that a real model calls the tool and uses its result.

  • Key: read only from HYPOTRAIL_ANTHROPIC_API_KEY and passed explicitly to the provider; ANTHROPIC_API_KEY is ignored. It is never logged or persisted, and the output directory, including the decoded Inspect log, is scanned for its value before the run reports, and the scan also runs when a step of the run fails (a leak is then the error reported). Each log is read back through Inspect's read_eval_log and searched, and its raw bytes are searched too; the log's storage format is never opened by hand (ADR 0001). A log that Inspect cannot read back does not stop the scan of the other files; if no leak is found anywhere and some log could not be read, the run fails with LOG_NOT_FULLY_SCANNED and the files named, and is never reported clean. Without the key the command exits 5 with the named blocker LIVE_NOT_VALIDATED before any network call. Inspect's Anthropic provider prefers ANTHROPIC_AUTH_TOKEN to an explicit key, so the run refuses to start when that variable is set.
  • Model: an explicit input of the form anthropic/<model>; the code holds no default, and another provider or a cloud-platform variant is refused so the key cannot travel there.
  • Bounds: non-dev Cases and more than two Episodes are refused.
  • Record: run.json holds the provider, the model identifier, the served model, the request parameters the log recorded, the engine version, the effective limits and the hardware; projection.json holds the Episodes; inspect/ holds the Inspect log.

The recorded run used anthropic/claude-sonnet-5-5. Both Episodes ran model, tool call executed on Chinook, model, final answer, and both final answers repeat rows the tool returned. The request carried the provider's defaults for this model: adaptive thinking and a top-level ephemeral cache control, with max_tokens 1024 shared between thinking and the answer.

Trace: run.json, projection.json and the Inspect log under traces/live-spike/inspect/.

Choices and limits worth knowing

Tool-call IDs

Inspect gives a tool no public way to read its own call ID while it runs. The tool mints an application ID, puts it in the result the model sees, and the projection keeps the mapping to the native ID.

Scripted runs

Offline runs use Inspect's mock model, recorded as mockllm/model, so no projection of such a log can be taken for a live model.

Rehearsal

The live path is exercised in the suite against a fake endpoint on loopback, so the real Anthropic client, the key header and the key scan are tested without a real call.

Not built

The Import and Assessment contracts.

Track

Temporal regression Track

The temporal regression Track runs the daily bike-rental Workload end to end on the Partition dev: it derives the Items of each Partition, builds the References, produces the predictions of two declared Configurations, seasonal_7 and ridge_v1, scores them and writes a first Comparison with per-date paired differences and delta_mae. It is a library driven from Python: there is no command line for it yet.

The Workload declaration

The Workload is declarative and holds no Python (ADR 0002). Everything the Track needs is a parameter read from examples/bike_day/workload.json, next to its data (data/day.csv) and licence notice. The Track code in src/hypotrail/ml/ fixes only two things: the Partition roles train, dev and public_check (protocol vocabulary, defined once in partitions.py) and the two kinds of Configuration it knows, with the keys each takes. Every other rule is checked against the declarations below.

The shape of workload.json is described once, as a JSON Schema (src/hypotrail/ml/workload.schema.json) checked by jsonschema, the one schema validator of the core (jsonschema is a pinned dependency of the core, not of an extra). The schema lists every key at every level, each kind of Configuration with the keys it takes, and the type of every value, leaves included: a column name is a string, a period is a whole number (7.0 and true are not), clip_min is a number, sparse_output is a boolean. It also lists the values the Track can run: ridge.solver is one of auto, svd, cholesky, lsqr, sparse_cg, sag, saga; encoder.handle_unknown is ignore or error; encoder.sparse_output is false (the Track feeds a dense matrix to scikit-learn); ridge.alpha is at least 0; the root period_k is at least 1; id_prefix and the file and column names are not empty; the dates of a Partition are calendar dates YYYY-MM-DD; track, when present, is temporal_regression. A declaration that does not match is refused when it is loaded, with a code and the path of the faulty value, before any data is read, any model is fitted, any prediction is made or any file is written. The Track keeps no hand-written check of what the schema guarantees.

Only partitions is required by the schema, because it is the one key every public entry point reads (memberships, References, the seasonal baseline, the Ridge outputs, metrics and the Comparison). Any other key is required by the entry points that read it, which refuse its absence with DECLARATION_INCOMPLETE before they write anything: data_file, date_column, id_prefix and period_k by memberships (and so by References and by the two Configurations); target_column by References and the two Configurations; forbidden_features, allowed_target_features and configurations by the two Configurations; target_unit by metrics and the Comparison. schema_version, track and licence_notice are read by no Track code and may be absent. The rules that relate values to each other or to the protocol stay in Track code and run after the schema (see Refusals).

Memberships and References

write_memberships(workload_dir, out_dir) derives one row per date of the data into memberships.csv with the columns row_id, date, partition and exclusion_reason. A date inside a declared range gets that Partition. A date whose history is incomplete gets no Partition and the reason insufficient_history; for Bike these are the seven first days, 2011-01-01 to 2011-01-07. A declared range may not cover such a day, and a date that falls in no range is refused, so the declaration and the data are always consistent. The result does not depend on the order of the input rows.

write_references(workload_dir, out_dir) writes references.csv (row_id, y_true): the target of every Item that belongs to a Partition. Predictions never carry their own target; metrics join this file by row_id.

The two Configurations

  • seasonal_7 (kind seasonal_baseline; baselines.py, needs neither scikit-learn nor NumPy): the prediction for date t is the target 7 days earlier. Nothing is fitted. Its declaration holds period_k and post_processing.clip_min. A period must be a declared lag of allowed_target_features.
  • ridge_v1 (kind ridge_pipeline; ridge.py, needs the ml extra: it imports scikit-learn and NumPy, and nothing in the core does): the inputs are the lag features lag_1, lag_7, mean_previous_7, computed from dates in lags.py (only values strictly before t are read), and the calendar columns mnth, weekday, holiday, workingday read as they are. A scikit-learn Pipeline holds a ColumnTransformer (a OneHotEncoder on the calendar columns, handle_unknown=ignore, dense output; a StandardScaler on the lags) and a Ridge (alpha 1.0, intercept, solver svd). The pipeline is fitted once, on the train Partition, always. Predicting any other Partition fits nothing.

Both apply the same post-processing: y_pred is y_pred_raw bounded below at the declared clip_min (0), applied once when the predictions are written. Both go through the same function (configuration.load_configuration) before anything is fitted or predicted. The declared kind picks the keys a Configuration may carry; the schema refuses an unknown kind, or a key that does not belong to its kind, when the declaration is loaded. The checks that apply to every Configuration (forbidden features, target transformations that reach date t or later, target transformations the Workload does not declare) run for every kind.

Metrics

metrics.compute_metrics(predictions, references, memberships, workload_dir, partition="dev") joins predictions, References and memberships by row_id and scores y_pred. The predictions must be exactly the Items of the Partition, each with a reference; a repeated row_id, a value that is not a finite number or a missing reference is refused. Reported: mae (the primary metric), rmse, mae_by_month and clipped_count (the number of Items where y_pred differs from y_pred_raw). Each carries the declared unit and a direction (lower_is_better); the order of the files changes nothing.

Metrics are computed on dev only. Any other Partition is refused; public_check has its own code.

Comparison on dev

comparison.compare(control_predictions, candidate_predictions, references, memberships, out_dir, workload_dir, partition="dev") pairs the two predictions files by row_id. They must cover exactly the same Items: there is no silent intersection. It reports the metrics of each side over the same scored Items and, for each Item, control_abs_error, candidate_abs_error and delta_abs_error (Candidate minus Control). delta_mae is MAE(Candidate) - MAE(Control) taken from the two reported MAEs: a positive value means the Candidate is worse. An improvement is never required. Here seasonal_7 is the Control and ridge_v1 the Candidate.

Refusals

Each refusal is an InvalidInputError (exit code 2 once a command line exists) with a code, a message, a stage and details. Nothing is dropped or included silently, and a declaration or Configuration is refused before anything is fitted or predicted. Every refusal raised while the declaration is loaded has the stage declaration and its details give key and path (the dotted path of the faulty value, empty at the root). A declaration file that is missing or not JSON is refused with FILE_NOT_FOUND or FILE_NOT_JSON: key is the file name, path is empty (the whole document) and file is its location. A period that no date can apply (it reaches before the first date of the calendar) passes the schema, since it depends on the dates; it is refused when a date is shifted, in memberships, lags and the seasonal baseline, with DECLARATION_VALUE_NOT_ALLOWED, stage declaration, and the key and path of the period.

How to run it

There is no command for this Track yet. The functions are called from Python, after the data has been checked against its lock with uv run python -m hypotrail data verify --workload bike_day; the Track functions themselves do not verify the data. ridge_v1 needs the ml extra (uv sync --locked --all-extras).

# from the repository root
from pathlib import Path
from hypotrail.ml.memberships import write_memberships
from hypotrail.ml.references import write_references
from hypotrail.ml.baselines import write_seasonal_baseline
from hypotrail.ml.ridge import write_outputs
from hypotrail.ml.comparison import compare

workload, out = Path("examples/bike_day"), Path("out")
write_memberships(workload, out)
write_references(workload, out)
write_seasonal_baseline(workload, out / "control", "seasonal_7", "dev")
write_outputs(workload, out / "candidate", "ridge_v1", "dev")   # also writes sklearn_params.json
result = compare(
    out / "control" / "predictions.csv", out / "candidate" / "predictions.csv",
    out / "references.csv", out / "memberships.csv", out / "comparison", workload,
)
print(result["delta_mae"]["value"])

The tests that run the real Workload through both Configurations are tests/test_ml_bike_end_to_end.py; the causality, refusal and Comparison tests are in the other tests/test_ml_*.py files. Like the rest of the suite they run offline and call no model.

Limits

No Study

No Study, run manifest, request_id or command line. These contracts belong to issue #9.

No freeze, no Exposure

No protocol freeze and no Exposure journal. Because no use of public_check can be recorded, every metric and Comparison on it is refused. Both belong to issue #30.

Data lock

The Track does not verify the data against its lock; the caller does (data verify, later the command of issue #9).

Comparison contract

mode is a constant, native_ml. The strict comparability checks of the Comparison are a later contract. The code sits in hypotrail/ml/, not in the core (ADR 0001 names the Comparison as a core concept).

Agentic Track

The agentic Track asks a model Chinook questions and scores the answer it keeps. This chapter describes the part that exists: the Workload declaration and the task built from it, and the chinook_contract_v1 Scorer, which turns one Episode's raw final answer, its Reference and its projected trace into four Criteria, exact_table, format_valid, evidence_link_valid and contract_success, and keeps failures of the instrument apart from failures of the evaluated system. The spike chapter covers the runs and the log projection.

Where the Scorer lives

The Scorer is src/hypotrail/core/chinook_contract.py. It needs the standard library and jsonschema only; the core never imports Inspect (ADR 0001). Rescoring a kept log (agentic/rescore.py) projects the log, then applies this Scorer to each Episode. It calls neither the model nor a tool and never opens the Chinook file: the frozen References are enough. The output of every Episode records the Scorer's name, chinook_contract_v1, and its version, and two rescorings of one log give the same verdicts.

The Scorer takes the raw final answer unchanged and keeps it unchanged in its output, whether or not it respects the schema.

The Workload declaration

The Workload is declarative and holds no Python (ADR 0002). examples/chinook/workload.json is checked as a whole against one JSON Schema, src/hypotrail/agentic/workload.schema.json, by jsonschema. declaration.load_workload(directory) reads and checks it and returns a Workload; it imports neither Inspect nor any Reference, so a refusal comes before Inspect runs. Every key is required except scenarios. Every object is closed, except configurations, whose keys are the Workload's own Configuration names; the Partition names under cases are closed to the Track's two roles.

The two Configurations

  • plain carries the system text in full. It tells the model to answer with the available tools and not to guess, to answer in the requested schema table-answer/1, and to distinguish an answer, an ambiguity and unavailable information. It states the common format rules: one JSON object and nothing else, no Markdown fence, no extra prose, the six fields, the three statuses and their reason_codes (criterion_undefined for needs_clarification, field_not_available for not_answerable), with columns and rows empty and unit null for the last two.
  • verify is plain (extends) followed by a declared added_instruction and nothing else: check the scope, the joins, the units and the result before concluding. Its resolved text is exactly plain's text plus the instruction. No Reference value is in either text.

The task

runner.build_task(workload, configuration, cases=None, partition="dev") returns the Inspect task. runner.run_episodes(cases, workload=..., configuration=..., model=..., repeats=..., log_dir=...) runs it. The task replaces the spike's single prompt and its chinook_spike task.

  • Each Case is one sample. Its input is two messages: the Configuration's system text, and a user message rendered from the question, the requested columns and the unit only (prompt.render_user_message). A Case with no unit goes through the same rendering (Unit: none), so the system text is identical for every Case of a Configuration. The Case identifier, the group, the family, the Reference rows, the oracle SQL, the expected status and the tolerance never reach the model.
  • The model gets exactly two tools, describe_schema and query_readonly, both bound to the database path of the declaration. describe_schema takes no argument and returns the eleven tables with their columns, types and foreign-key relations, read from SQLite itself (PRAGMA); it holds no row, Reference or oracle SQL.
  • Both Configurations run with the same tools, limits and generation settings; only the system text differs.
  • The log header keeps the Configuration name and its exact system text (eval.metadata), and the live run record (run.json) repeats them.
  • The References are not an input of the builder: a task built from the declaration runs when the References file is absent.
Open pointThe builder can build a task on any declared group of Cases, public_check included. The builder does not refuse it; the counting and rescoring entry points do (see the scripted_fixture section), until #9's Exposure journal exists.

The read-only SQL tool

The evaluated model reaches Chinook through two tools, describe_schema (see above) and query_readonly(sql) (agentic/sql_tool.py; the connection details are in the spike chapter). No SQL text is inspected: three native SQLite mechanisms decide what runs. The limit on attached databases is 0, execute takes a single statement, and an authorizer holds the allow-list.

  • Allowed: SELECT, reads of the tables the Chinook file itself declares, and eleven functions: count, sum, avg, min, max, round, lower, upper, coalesce, ifnull and strftime.
  • Tables read from the file: the table names are never written in the code, so a table the file does not declare is not readable, and the system tables such as sqlite_master stay refused.
  • Denied: writes and DDL, ATTACH, DETACH, PRAGMA, transactions, VACUUM (also INTO), extension loading, recursive queries and any other function. A statement that starts with WITH or SELECT but needs a denied action is refused.

A refused or failed statement sets error to a code, a type and a message; the code is what to rely on.

CodeMeaning
DENIED_ACTIONThe authorizer refused an action outside the allow-list.
SQL_ERRORSQLite failed the statement for another reason (syntax, unknown table or column).
MULTIPLE_STATEMENTSThe text holds more than one statement.

Four caps per query

Every call is also bounded by four caps (QueryCaps in agentic/sql_tool.py, AG-04). A cap that is reached is never turned into a complete result: it shows as truncated: true, or as an error that names the limit and comes with no rows.

CapDefaultWhen reached
Watched time1 s of wall clockError code TIME_LIMIT, no rows.
Instruction ceiling100,000,000 SQLite VM instructionsError code INSTRUCTION_LIMIT, no rows.
Rows200 returned, 201 fetchedThe first 200 rows in the query's order, truncated: true.
Serialized size64 KiB (the JSON of columns and rows)The longest prefix of rows that fits, truncated: true, and a row_count that matches the rows returned.

SQLite's progress handler, called every 1000 instructions, watches the first two caps. The fetch stops at 201 rows through fetchmany, so the extra row only tells that more exist. AG-04 gives no number for the instruction ceiling, so 100,000,000 is a declared default: the 1 s time stays the primary cap, and the ceiling is a machine-independent backstop set near it (about 0.7 s at the roughly 138 million instructions per second measured on the development machine). It is about 3,000 times the heaviest of the 16 oracle statements (about 32,000), so it does not refuse a read the time cap would allow on this machine. It changes only by a new value in the record. The two time mechanisms are witnessed apart: each test puts the other cap out of reach.

The query runs in a worker thread (anyio.to_thread), not on Inspect's event loop. A slow query therefore does not stop the Episode time limit from taking control: when that limit cancels the call, a stop flag read by the progress handler interrupts the statement. The four caps are recorded in the task metadata and read back with the Episode limits, under query_caps (read_back in agentic/limits.py).

The comparison rules are the spike's: no string is converted to a number, a boolean is not an integer, NULL stays NULL, non-finite numbers are refused, and no number is picked out of prose. The evidence link and contract success

A successful tool call is one with no Inspect-level tool error and no structured error in its result body (the shape {code, type, message} that the read-only SQL tool returns, for example when its authorizer refuses a statement). The Scorer reads the Episode's projected steps, plain records, and never an Inspect object; the projection itself still reads the log only through Inspect's public log API. The link is a check that a cited ID points to a real, earlier, successful call. It is not a proof that every claim in the answer follows from the trace.

An exact table with no valid evidence is exact but not a success of the tool-based path: exact_table true, evidence_link_valid false, contract success false. Contract success is scored false as soon as one dependency is false, whatever the state of the others. Only when none is false and one is unscored or errored does it take that state and Reason: a well-formed answer with valid evidence and a missing Reference gives unscored with reference_missing. Without a trace, evidence_link_valid is unscored (trace_missing), and so is the contract success of an answered answer; for a malformed answer, whose evidence cannot be read, it is unscored with invalid_response_format.

The scripted_fixture Mode

fixture.run_fixture(workload_dir=..., out_dir=..., configuration=...) runs the Chinook task under a Configuration the Workload declares (the Track names none as a default), and runs the Chinook task with Inspect's own mock model, which plays scripted responses. The tools are the real local tools on the Chinook file; the task (runner.run_episodes), the projection and the Scorer are the code a live run uses. Only the model differs. It needs no network and no provider key.

The scripts are data in examples/chinook/fixtures/scenarios.json, not Python. Each entry is one model turn: a tool call (with repeat on the last turn, it repeats), an answer built from the last tool result and citing its own tool_call_id, or a raw answer kept verbatim. The scenario Cases (SCN-01 to SCN-07) are technical: none is one of the 20 business Cases, and the run records business_case_outputs: 0.

Public_check Items are refused. rescore.rescore_episodes, rescore.rescore_log and counts.tally take the Workload and refuse a public_check Item before any computation, with PUBLIC_CHECK_RESCORING_REFUSED or PUBLIC_CHECK_COUNTS_REFUSED. The Partition of an Item is the one the Workload declares for its Case, not a label the caller passes; a Case the declaration does not list (a scenario) has none and is not refused. #9 lifts the refusal with the Exposure journal. Scoring one answer against one Reference (score_episode) stays allowed. The scenarios are not public_check Items.

What is written names the Mode and carries the banner "simulation, no LLM evaluated": run.json, projection.json, verdicts.json and the Inspect log header. The recorded model is mockllm/model. run.json also holds the effective limits read back from the log (the per-query caps included), the tool-call limit named as not enforceable (Inspect has none), the note that a 6-turn limit allows 7 provider calls, and the SHA-256 of the Chinook file before and after the run, which must be equal. The banner as a report renders it is #10's.

Choices and limits worth knowing

Malformed means not exact

An answer that is not one JSON object with the six fields is scored false on exact_table and evidence_link_valid as well, each with invalid_response_format: it is the system's failure, not the instrument's. A valid JSON object with an extra field makes format_valid and contract_success false and leaves exact_table to the comparison with the Reference.

Failed and missing Episodes

Every expected Episode has a state for every Criterion, with a Reason for each non-score (rescore.rescore_episodes). An Episode failed by an execution error has every Criterion unscored with execution_failed; an Episode absent from the log is missing, every Criterion unscored with observation_missing. Neither is scored false, and neither has an empty list. An Episode stopped by one of our limits is failed too (see the scripted_fixture section), with Criteria that depend on who stopped it.

The schema is an input

The Scorer is given the Workload's table-answer/1 schema; it does not read it from disk, so rescoring opens no Workload file.

Not built

Scoring answers imported without a trace, the shares of the Assessment contract, the Assessment contract and a closed Scorer registry, and an Inspect adapter (ADR 0001's parity test applies if one is built).

The live command

spike live runs one declared Configuration of the Chinook task against a real Anthropic model. It is opt-in, paid and bounded, and it is never part of the tests or CI. This book only prepares it: it was rehearsed offline against a local fake endpoint and has not been run. Per the owner, the References review of D07, D08, E11 and E12 comes before any live run. The two live runs below, and the 72-Episode campaign, happen outside the ticket that built the command (#49).

export HYPOTRAIL_ANTHROPIC_API_KEY=...   # the only variable read for the key
uv run python -m hypotrail spike live --config plain  --model anthropic/<model> --out DIR_PLAIN
uv run python -m hypotrail spike live --config verify --model anthropic/<model> --out DIR_VERIFY

Each output directory must be empty. With no --case, the run takes the two dev join Cases, D03 and D05, one Repeat each, so two Episodes; the record names them. The command refuses, before the key is read and before Inspect is imported, a Configuration the Workload does not declare, a model that is not an explicit anthropic/<model> (there is no default), a Case outside dev, and more than two Episodes. With no key it exits 5 and sends nothing. The output is scanned for the key before the run reports.

Reasoning is disabled, identically for plain and verify, and the 1,024-token output cap is kept (owner decision 1 on #8). A reasoning level would draw its thinking from the same 1,024 tokens as the answer, so an answer could be cut by our own setting; disabled leaves the whole cap to the answer. A test captures the request bodies of both Configurations at the fake endpoint and checks that each carries the same thinking field and max_tokens: 1024. Which thinking value a model gets is Inspect's to decide: {"type": "disabled"}, or {"type": "between_tools"} for Sonnet 5.5, which rejects disabled. Inspect's source describes between_tools as no up-front thinking and the model's lowest setting; it does not say whether thinking may still happen between tool calls, so that is not claimed here. Before any provider call, the run asks Inspect's own request building (completion_config, no network) what the request would carry; if it would not state the reasoning setting (for example Opus 5.5 cannot disable thinking, and models before 4.7 get no thinking field), the run is refused with REASONING_NOT_EXPLICIT and nothing is sent. The record keeps the field as it was sent, with this note.

The projection records why each model call stopped. A live Episode whose final call stopped on the output cap is failed with the Reason output_cap, never produced; one stopped by the turn, token or time limit carries turn_limit, token_limit or time_limit. How they are scored is described above; live Episodes are still not scored against References here.

run.json holds: the Mode llm_live and the provider; the requested and served model; the Configuration name and its exact system text; the reasoning setting (requested and as sent) and the output cap (requested and as sent); the engine version, Python and hardware; the effective limits read back from the log, including the per-query caps; the statements that Inspect has no tool-call limit and that 6 turns allow 7 provider calls; the Cases run; the SHA-256 of the Chinook file before and after the run; and, per Episode, the number of model calls, the latency, and the tokens and cost when the log gives them (null otherwise, never zero). projection.json gives each model turn a stop_reason (stop, tool_calls, max_tokens, ...), so an answer cut by the output cap is told apart from a complete one. That is a record only: live Episodes are not scored against References here. The record also reports whether the tool loop was observed: a produced Episode with at least one successful query_readonly call between model turns, then a final answer. describe_schema calls and further queries may come anywhere in it.
