Spike

Feasibility spike

The spike proved on the target machine that the chosen stack works before anything general is built: a locked Python 3.13 environment, both public datasets verified, an Inspect task where a model calls a read-only SQL tool on Chinook, and a live trace of a real model doing it. This chapter is the reference for what exists, how to run it and where it stops.

Install and run

The project is a uv project on Python 3.13 with a committed lock. The core needs the standard library and one schema validator, jsonschema; the Inspect and the machine-learning dependencies are optional extras (agent and ml).

# core only: the standard library and jsonschema
uv sync --locked
uv run python -m hypotrail --help

# everything the spike needs, then the offline test suite (no network, no model call)
uv sync --locked --all-extras
uv run --locked --all-extras pytest

# the Python version is pinned by .python-version and requires-python (3.13 only)

The default test command never calls a model, even when a model key is present: every test runs with outbound network access blocked, and an attempt fails the test. Live calls are opt-in and never part of the suite.

Data verification

The two public datasets live in the declarative Workloads examples/bike_day and examples/chinook, each with the slice of data-sources.lock.json that covers it and a data-checks.json that declares what to check. Verification works offline, in a fixed order: the bytes of every selected dataset first, then the licence notices, then the content.

The Inspect spike

The agentic side lives in src/hypotrail/agentic/; the core never imports Inspect (ADR 0001). Inspect owns the agent loop, the tool calls, its limits and its log; Hypotrail owns the scoring function and reads the log only through Inspect's public log API.

  • Task (runner.py): a system message and a user message per Case, the tools, then Inspect's own generate-and-call-tools loop. The task is now built from the Workload declaration; see the chapter on the agentic Track.
  • Tool (sql_tool.py): query_readonly(sql) opens the Chinook file read-only at a path fixed by the application, one connection per execution, execute and never executescript, extensions disabled. mode=ro covers only the main database, so three native SQLite mechanisms decide what runs, and no SQL text is inspected (no regular expression, no SELECT test): the limit on attached databases is 0; execute takes one statement; and an authorizer holds the allow-list, which is SELECT, reads of the tables the file itself declares (read from the file, never named in code, so its system tables such as sqlite_master stay refused) and the functions of the allow-list table in the chapter on the agentic Track (like and glob were added to AG-03's list by the owner's revision of 2026-11-07, #51). Everything else is denied: writes and DDL, ATTACH, DETACH, PRAGMA, transactions, VACUUM (also INTO), extension loading, recursive queries and any other function, so a statement that starts with WITH or SELECT but needs a denied action is refused. It returns columns, rows, row_count, truncated, error and a tool_call_id. A refused or failed statement sets error to a code (DENIED_ACTION, SQL_ERROR or MULTIPLE_STATEMENTS), a type and a message; the code is what to rely on. Four per-query caps bound every call (row, size, time and instruction count; see the agentic Track chapter).
  • Projection (projection.py): one record per Case x Repeat, in the order model turn, tool call, tool result, model turn, final answer. A Repeat is 0-based; Inspect's epoch is 1-based. An Episode is produced, failed (execution stopped with an error, at one of our limits before a final answer, or with its answer cut by the output cap) or missing (absent from the log).
  • Scoring (core/answer_scoring.py): compares status, reason, columns, rows and unit with the frozen Reference. An answer missing one of the six required fields (status, reason_code, columns, rows, unit, evidence) is malformed: parsed is false and every component is false, even when the Reference holds null there. No string-to-number conversion, a boolean is not an integer, NULL stays NULL, non-finite numbers are refused, and the Reference's absolute tolerance applies. agentic/rescore.py rescores a kept log without the model, the tool or the Chinook file; since ticket #45 it goes through the chinook_contract_v1 Scorer (see the agentic Track chapter).
  • Limits (limits.py): set through Inspect's own options and read back from the log.
  • Live run (live.py): python -m hypotrail spike live --config plain --model anthropic/<model> --out DIR. Opt-in and paid. See below, and the agentic Track chapter for the two commands.

The live run

spike live runs one named Configuration of the spike task on at most two dev Cases (D03 and D05 by default), one Repeat each, under the limits above (the token budget since revised: see the table). It scores nothing against References; it only shows that a real model calls the tool and uses its result.

  • Key: read only from HYPOTRAIL_ANTHROPIC_API_KEY and passed explicitly to the provider; ANTHROPIC_API_KEY is ignored. It is never logged or persisted, and the output directory, including the decoded Inspect log, is scanned for its value before the run reports, and the scan also runs when a step of the run fails (a leak is then the error reported). Each log is read back through Inspect's read_eval_log and searched, and its raw bytes are searched too; the log's storage format is never opened by hand (ADR 0001). A log that Inspect cannot read back does not stop the scan of the other files; if no leak is found anywhere and some log could not be read, the run fails with LOG_NOT_FULLY_SCANNED and the files named, and is never reported clean. Without the key the command exits 5 with the named blocker LIVE_NOT_VALIDATED before any network call. Inspect's Anthropic provider prefers ANTHROPIC_AUTH_TOKEN to an explicit key, so the run refuses to start when that variable is set.
  • Model: an explicit input of the form anthropic/<model>; the code holds no default, and another provider or a cloud-platform variant is refused so the key cannot travel there.
  • Bounds: non-dev Cases and more than two Episodes are refused.
  • Record: run.json holds the provider, the model identifier, the served model, the request parameters the log recorded, the engine version, the effective limits and the hardware; projection.json holds the Episodes; inspect/ holds the Inspect log.

The recorded run used anthropic/claude-sonnet-5-5. Both Episodes ran model, tool call executed on Chinook, model, final answer, and both final answers repeat rows the tool returned. The request carried the provider's defaults for this model: adaptive thinking and a top-level ephemeral cache control, with max_tokens 1024 shared between thinking and the answer.

Choices and limits worth knowing

Tool-call IDs

Inspect gives a tool no public way to read its own call ID while it runs. The tool mints an application ID, puts it in the result the model sees, and the projection keeps the mapping to the native ID.

Scripted runs

Offline runs use Inspect's mock model, recorded as mockllm/model, so no projection of such a log can be taken for a live model.

Rehearsal

The live path is exercised in the suite against a fake endpoint on loopback, so the real Anthropic client, the key header and the key scan are tested without a real call.

Not built

The Import and Assessment contracts.

Track

Temporal regression Track

The temporal regression Track runs the daily bike-rental Workload end to end on the Partition dev: it derives the Items of each Partition, builds the References, produces the predictions of two declared Configurations, seasonal_7 and ridge_v1, scores them and writes a first Comparison with per-date paired differences and delta_mae. It is a library driven from Python; init and run ml drive it from the command line and record the result as an Attempt of a Study (chapter 04).

The Workload declaration

The Workload is declarative and holds no Python (ADR 0002). Everything the Track needs is a parameter read from examples/bike_day/workload.json, next to its data (data/day.csv) and licence notice. The Track code in src/hypotrail/ml/ fixes only two things: the Partition roles train, dev and public_check (protocol vocabulary, defined once in partitions.py) and the two kinds of Configuration it knows, with the keys each takes. Every other rule is checked against the declarations below.

The shape of workload.json is described once, as a JSON Schema (src/hypotrail/ml/workload.schema.json) checked by jsonschema, the one schema validator of the core (jsonschema is a pinned dependency of the core, not of an extra). The schema lists every key at every level, each kind of Configuration with the keys it takes, and the type of every value, leaves included: a column name is a string, a period is a whole number (7.0 and true are not), clip_min is a number, sparse_output is a boolean. It also lists the values the Track can run: ridge.solver is one of auto, svd, cholesky, lsqr, sparse_cg, sag, saga; encoder.handle_unknown is ignore or error; encoder.sparse_output is false (the Track feeds a dense matrix to scikit-learn); ridge.alpha is at least 0; the root period_k is at least 1; id_prefix, target_unit, the file and column names, the id of a Configuration and the name of a Partition are not empty (a Partition named "" would otherwise load and lose its Items from the References); the dates of a Partition are calendar dates YYYY-MM-DD; track, when present, is temporal_regression. A declaration that does not match is refused when it is loaded, with a code and the path of the faulty value, before any data is read, any model is fitted, any prediction is made or any file is written. The Track keeps no hand-written check of what the schema guarantees.

Only partitions is required by the schema, because it is the one key every public entry point reads (memberships, References, the seasonal baseline, the Ridge outputs, metrics and the Comparison). Any other key is required by the entry points that read it, which refuse its absence with DECLARATION_INCOMPLETE before they write anything: data_file, date_column, id_prefix and period_k by memberships (and so by References and by the two Configurations); target_column by References and the two Configurations; forbidden_features, allowed_target_features and configurations by the two Configurations; target_unit by metrics and the Comparison. schema_version, track and licence_notice are read by no Track code and may be absent. question, objective and limitations are read by init only, for the StudySpec (chapter 04), and may be absent from a Workload that is never given a Study. The rules that relate values to each other or to the protocol stay in Track code and run after the schema (see Refusals).

The declaration is read once. declaration.load_declaration(workload_dir) is the one loader: it reads workload.json, checks it against the schema and returns a Declaration, a tree of frozen dataclasses (tuples and read-only mappings; a key the schema leaves optional is None when the file lacks it). Every entry point calls it once and every computation starts from the typed object: memberships_of, read_table, read_target_series, validate_configuration, inputs_of and the others take a Declaration and refuse a raw dict with a TypeError. No other module indexes the raw dictionary.

A period is an object too. periods.Period holds a number of days with the key and the path where it was declared, and shifts a date itself: earlier(date) is the date one period before, and window(date) yields the dates 1 to k days before, nearest first. Memberships (the warm-up), the lags and the seasonal baseline all shift through it, and a shift that leaves the calendar is refused there (see Refusals). Two periods of the same length are equal wherever they are declared.

Memberships and References

write_memberships(workload_dir, out_dir) derives one row per date of the data into memberships.csv with the columns row_id, date, partition and exclusion_reason. A date inside a declared range gets that Partition. A date whose history is incomplete gets no Partition and the reason insufficient_history; for Bike these are the seven first days, 2011-01-01 to 2011-01-07. A declared range may not cover such a day, and a date that falls in no range is refused, so the declaration and the data are always consistent. The result does not depend on the order of the input rows.

write_references(workload_dir, out_dir) writes references.csv (row_id, y_true): the target of every Item that belongs to a Partition. Predictions never carry their own target; metrics join this file by row_id.

The two Configurations

  • seasonal_7 (kind seasonal_baseline; baselines.py, needs neither scikit-learn nor NumPy): the prediction for date t is the target 7 days earlier. Nothing is fitted. Its declaration holds period_k and post_processing.clip_min. A period must be a declared lag of allowed_target_features.
  • ridge_v1 (kind ridge_pipeline; ridge.py, needs the ml extra: it imports scikit-learn and NumPy, and nothing in the core does): the inputs are the lag features lag_1, lag_7, mean_previous_7, computed from dates in lags.py (only values strictly before t are read), and the calendar columns mnth, weekday, holiday, workingday read as they are. A scikit-learn Pipeline holds a ColumnTransformer (a OneHotEncoder on the calendar columns, handle_unknown=ignore, dense output; a StandardScaler on the lags) and a Ridge (alpha 1.0, intercept, solver svd). The pipeline is fitted once, on the train Partition, always. Predicting any other Partition fits nothing.

Both apply the same post-processing: y_pred is y_pred_raw bounded below at the declared clip_min (0), applied once when the predictions are written. Both go through the same function (configuration.load_configuration) before anything is fitted or predicted. The declared kind picks the keys a Configuration may carry; the schema refuses an unknown kind, or a key that does not belong to its kind, when the declaration is loaded. The checks that apply to every Configuration (forbidden features, target transformations that reach date t or later, target transformations the Workload does not declare) run for every kind.

Metrics

metrics.compute_metrics(predictions, references, memberships, workload_dir, partition="dev") joins predictions, References and memberships by row_id and scores y_pred. The predictions must be exactly the Items of the Partition, each with a reference; a repeated row_id, a value that is not a finite number or a missing reference is refused. Reported: mae (the primary metric), rmse, mae_by_month and clipped_count (the number of Items where y_pred differs from y_pred_raw). Each carries the declared unit and a direction (lower_is_better); the order of the files changes nothing.

Metrics are computed on dev only. Any other Partition is refused; public_check has its own code.

Comparison on dev

comparison.compare(control_predictions, candidate_predictions, references, memberships, out_dir, workload_dir, partition="dev") pairs the two predictions files by row_id. They must cover exactly the same Items: there is no silent intersection. It reports the metrics of each side over the same scored Items and, for each Item, control_abs_error, candidate_abs_error and delta_abs_error (Candidate minus Control). delta_mae is MAE(Candidate) - MAE(Control) taken from the two reported MAEs: a positive value means the Candidate is worse. An improvement is never required. Here seasonal_7 is the Control and ridge_v1 the Candidate.

Refusals

Each refusal is an InvalidInputError (exit code 2 on the command line) with a code, a message, a stage and details. Nothing is dropped or included silently, and a declaration or Configuration is refused before anything is fitted or predicted. Every refusal raised while the declaration is loaded has the stage declaration and its details give key and path (the dotted path of the faulty value, empty at the root). A declaration file that is missing or not JSON is refused with FILE_NOT_FOUND or FILE_NOT_JSON: key is the file name, path is empty (the whole document) and file is its location. A period that no date can apply (it reaches before the first date of the calendar) passes the schema, since it depends on the dates; it is refused when a date is shifted, in memberships, lags and the seasonal baseline, with DECLARATION_VALUE_NOT_ALLOWED, stage periods, and in details the key and path of the declared period, its length in days (days, the declared number, never the offset the loop had reached) and the date being shifted. The same code at load has the stage declaration, so the two are told apart by their stage. An empty name of a Partition or of a Configuration is refused at load with key set to the empty name and path the object that holds it (partitions or configurations).

Track

Agentic Track

The agentic Track asks a model Chinook questions and scores the answer it keeps. This chapter describes the part that exists: the Workload declaration and the task built from it, and the chinook_contract_v1 Scorer, which turns one Episode's raw final answer, its Reference and its projected trace into four Criteria, exact_table, format_valid, evidence_link_valid and contract_success, and keeps failures of the instrument apart from failures of the evaluated system. The spike chapter covers the runs and the log projection.

Where the Scorer lives

The Scorer is src/hypotrail/core/chinook_contract.py. It needs the standard library and jsonschema only; the core never imports Inspect (ADR 0001). Rescoring a kept log (agentic/rescore.py) projects the log, then applies this Scorer to each Episode. It calls neither the model nor a tool and never opens the Chinook file: the frozen References are enough. The output of every Episode records the Scorer's name, chinook_contract_v1, and its version, and two rescorings of one log give the same verdicts.

The Scorer takes the raw final answer unchanged and keeps it unchanged in its output, whether or not it respects the schema.

The two Configurations

  • plain carries the system text in full. It tells the model to answer with the available tools and not to guess, to answer in the requested schema table-answer/1, and to distinguish an answer, an ambiguity and unavailable information. It states the common format rules: one JSON object and nothing else, no Markdown fence, no extra prose, the six fields, the three statuses and their reason_codes (criterion_undefined for needs_clarification, field_not_available for not_answerable), with columns and rows empty and unit null for the last two.
  • verify is plain (extends) followed by a declared added_instruction and nothing else: check the scope, the joins, the units and the result before concluding. Its resolved text is exactly plain's text plus the instruction. No Reference value is in either text.

The task

runner.build_task(workload, configuration, cases=None, partition="dev") returns the Inspect task. runner.run_episodes(cases, workload=..., configuration=..., model=..., repeats=..., log_dir=...) runs it. The task replaces the spike's single prompt and its chinook_spike task.

  • Each Case is one sample. Its input is two messages: the Configuration's system text, and a user message rendered from the question, the requested columns and the unit only (prompt.render_user_message). A Case with no unit goes through the same rendering (Unit: none), so the system text is identical for every Case of a Configuration. The Case identifier, the group, the family, the Reference rows, the oracle SQL, the expected status and the tolerance never reach the model.
  • The model gets exactly two tools, describe_schema and query_readonly, both bound to the database path of the declaration. describe_schema takes no argument and returns the eleven tables with their columns, types and foreign-key relations, read from SQLite itself (PRAGMA); it holds no row, Reference or oracle SQL.
  • Both Configurations run with the same tools, limits and generation settings; only the system text differs.
  • The log header keeps the Configuration name and its exact system text (eval.metadata), and the live run record (run.json) repeats them.
  • The References are not an input of the builder: a task built from the declaration runs when the References file is absent.
Open pointThe builder can build a task on any declared group of Cases, public_check included. The builder does not refuse it; the counting and rescoring entry points do (see the scripted_fixture section), until #9's Exposure journal exists.

The read-only SQL tool

The evaluated model reaches Chinook through two tools, describe_schema (see above) and query_readonly(sql) (agentic/sql_tool.py; the connection details are in the spike chapter). No SQL text is inspected: three native SQLite mechanisms decide what runs. The limit on attached databases is 0, execute takes a single statement, and an authorizer holds the allow-list.

  • Allowed: SELECT, reads of the tables the Chinook file itself declares, and the functions of the table below. AG-03 did not list like and glob; the owner added them by an explicit revision of AG-03 on 2026-11-07 (#51). SQLite reports the operators LIKE (also NOT LIKE and LIKE … ESCAPE) and GLOB to the authorizer under these two names; both only compare text, and the per-query caps still bound any pattern. LIKE keeps SQLite's default matching (case-insensitive for ASCII; GLOB is case-sensitive) because PRAGMA case_sensitive_like stays refused.
  • Tables read from the file: the table names are never written in the code, so a table the file does not declare is not readable, and the system tables such as sqlite_master stay refused.
  • Denied: writes and DDL, ATTACH, DETACH, PRAGMA, transactions, VACUUM (also INTO), extension loading, recursive queries and any other function. A statement that starts with WITH or SELECT but needs a denied action is refused.

A refused or failed statement sets error to a code, a type and a message; the code is what to rely on.

Four caps per query

Every call is also bounded by four caps (QueryCaps in agentic/sql_tool.py, AG-04). A cap that is reached is never turned into a complete result: it shows as truncated: true, or as an error that names the limit and comes with no rows.

SQLite's progress handler, called every 1000 instructions, watches the first two caps. The fetch stops at 201 rows through fetchmany, so the extra row only tells that more exist. AG-04 gives no number for the instruction ceiling, so 100,000,000 is a declared default: the 1 s time stays the primary cap, and the ceiling is a machine-independent backstop set near it (about 0.7 s at the roughly 138 million instructions per second measured on the development machine). It is about 3,000 times the heaviest of the 16 oracle statements (about 32,000), so it does not refuse a read the time cap would allow on this machine. It changes only by a new value in the record. The two time mechanisms are witnessed apart: each test puts the other cap out of reach.

The query runs in a worker thread (anyio.to_thread), not on Inspect's event loop. A slow query therefore does not stop the Episode time limit from taking control: when that limit cancels the call, a stop flag read by the progress handler interrupts the statement. The four caps are recorded in the task metadata and read back with the Episode limits, under query_caps (read_back in agentic/limits.py).

Wrapped answers

The raw answer is never altered, and the record says what was scored in its top-level field answer_read_from. The evidence link and contract success

A successful tool call is one with no Inspect-level tool error and no structured error in its result body (the shape {code, type, message} that the read-only SQL tool returns, for example when its authorizer refuses a statement). The Scorer reads the Episode's projected steps, plain records, and never an Inspect object; the projection itself still reads the log only through Inspect's public log API. The link is a check that a cited ID points to a real, earlier, successful call. It is not a proof that every claim in the answer follows from the trace.

An exact table with no valid evidence is exact but not a success of the tool-based path: exact_table true, evidence_link_valid false, contract success false. Contract success is scored false as soon as one dependency is false, whatever the state of the others. Only when none is false and one is unscored or errored does it take that state and Reason: a well-formed answer with valid evidence and a missing Reference gives unscored with reference_missing. Without a trace, evidence_link_valid is unscored (trace_missing), and so is the contract success of an answered answer; for an answer whose evidence cannot be read (nothing is read from it, or the object read is not valid against the schema), evidence_link_valid is scored false with invalid_response_format, trace or not.

Choices and limits worth knowing

Malformed means not exact, unless it only wears a wrapper

What the other two Criteria read is set out in the table of wrapped answers; a failure to read is the system's failure, not the instrument's.

Failed and missing Episodes

Every expected Episode has a state for every Criterion, with a Reason for each non-score (rescore.rescore_episodes). An Episode failed by an execution error has every Criterion unscored with execution_failed; an Episode absent from the log is missing, every Criterion unscored with observation_missing. Neither is scored false, and neither has an empty list. An Episode stopped by one of our limits is failed too (see the scripted_fixture section), with Criteria that depend on who stopped it.

The schema is an input

The Scorer is given the Workload's table-answer/1 schema; it does not read it from disk, so rescoring opens no Workload file.

Not built

Scoring answers imported without a trace, the shares of the Assessment contract, the Assessment contract and a closed Scorer registry, and an Inspect adapter (ADR 0001's parity test applies if one is built).

Study and Attempts

A Study is a folder that holds one Protocol and the Attempts run under it. init creates the Study of the bike Workload; run ml runs one Configuration on one Partition and records it as an Attempt: a manifest, an Observation set and the predictions, every artifact referenced by its digest and published atomically before the terminal manifest. A repeated --request-id returns the recorded Attempt or is refused. This chapter describes what exists; one writer per Study, interruption recovery, status and imports are later work (see Limits); scoring an Attempt is chapter 05.

Commands

Both commands are in src/hypotrail/cli.py. With --json, stdout holds exactly one JSON object ({"ok": true, ...} or {"ok": false, "error": {"code", "message", "stage", "details"}}) and the human diagnostic goes to stderr; no error carries a secret (an unexpected exception is reported by its type only). Without --json, stdout holds one line.

  • init verifies the Workload's data against its lock, then creates the Study: the StudySpec (study.json), a copy of the dataset, and the population (memberships) and the References set as Study artifacts, each with an ID. The Workload must be of the temporal regression Track. A Study folder that already holds a study.json is refused.
  • run ml runs one declared Configuration (seasonal_7, ridge_v1) on one declared Partition and records one Attempt. --request-id is required. Its output is {"ok": true, "replayed": false, "attempt": MANIFEST}; replayed is true when the request was already recorded and nothing was computed. It needs the ml extra only to run ridge_v1.

The Workload stays where it is declared (examples/<name>, or the folder given by --examples-dir): a Configuration can change after the Study exists, and an Attempt records the Configuration it ran. The Study freezes the Protocol, not the Configurations.

The records

Every record is canonical JSON (core/canonical.py): UTF-8, keys sorted, separators , and :, no whitespace, strict types. NaN and Infinity are refused, never written (NON_CANONICAL_VALUE), and an integer and a float of the same value stay distinct. A configuration declared with its keys in another order has the same digest; the source files are hashed on their bytes, separately. Each record is validated against the contract schema (src/hypotrail/core/contracts.schema.json, by jsonschema) before it is written and after it is read; a fault is CONTRACT_VIOLATION.

The schema is derived from the kit's contracts.schema.json and owned here; the kit's copy is not changed. It keeps every field of the kit's envelopes, names the Criterion states scored / unscored / errored and their counters unscored / errored, and defines the fields and the two further record kinds (freeze, exposure) that the next tickets of the slice name. Only the records below are written today.

Attempt manifest. attempt_id is a UUID, never a hash of the inputs: two requests of identical inputs under two request_ids are two Attempts with the same effective_config_digest. effective_config holds the Command, the Workload, the Mode, the Partition, the Configuration (its id and its declared content), the Protocol (id and digest), the input digests (dataset, population, References), the effective parameters (null while running), and the applicable bounds. code_environment holds the Python version, the dependency lock (uv.lock, by digest) and the code revision: the commit, whether the code is dirty and, when it is, a fingerprint of the local code. "The code" is src/, pyproject.toml and uv.lock. No provider secret is written: the process environment is never read into a record. A manifest that is running has no finished_at; a completed one has it, the counts of its Items by execution status (item_counts) and its output_refs.

Artifacts and integrity

An ArtifactRef is {path, sha256, size_bytes, media_type, role}: the path is relative to the Study and the digest is of the bytes. A path that leaves the Study (.., an absolute path) or goes through a symlink pointing outside it is refused (ARTIFACT_PATH_OUTSIDE_STUDY), for writing and for reading; a symlink that stays inside is not a traversal.

Publication is atomic (core/artifacts.py): the bytes go to a temporary file in the destination's folder, inside the Study, are flushed and fsynced, then renamed onto the final path; nothing appears under the final path before the rename. A published artifact is immutable: other bytes under the same path are refused (ARTIFACT_IMMUTABLE). When a referenced artifact's bytes no longer match its digest, or the file is gone, reading it back is an integrity refusal (ARTIFACT_INTEGRITY, ARTIFACT_MISSING; exit 3), raised before any computation: run ml reads back the dataset, the memberships and the References of the Study before it computes, and an Attempt it replays.

The canonical JSON and the atomic write were copied from hypotrail/hypotrail at commit 4ef4925 (framework/mlkit/study/understanding/canonical.py, framework/mlkit/study/store.py) and are owned here; nothing is imported from that project.

The Protocol

The StudySpec's protocol_digest is the canonical digest of what binds every Attempt: the Partitions and their ranges, the population and the References by their bytes, the data file by its bytes, the columns, the rules on when information is available (period_k, the forbidden and the allowed target features) and the primary metric. It changes when a Partition range or the References change. It does not change when a Configuration changes, nor with the key order of the declaration. run ml recomputes it from the Workload for a new request and refuses a Workload whose Protocol is no longer the Study's (PROTOCOL_CHANGED, exit 3).

The question, the objective and the limitations of the StudySpec are declared by the Workload (question, objective, limitations in workload.json, read by init only). The primary metric is mae, lower_is_better, in the unit the Workload declares. study_id is a UUID; revision is the digest of the StudySpec without its study_id and itself. An artifact ID is its kind and the first 16 hex digits of its digest (references-<digest>), so a corrected References set has another ID.

The same request_id with the same request returns the recorded Attempt, whatever its status, after reading its artifacts back against their digests: no fit and no prediction happens, and nothing is written. With any element different it is REQUEST_CONFLICT (exit 6), naming the elements that differ, and nothing is written. An interrupted write

The manifest is written running before anything else, each artifact is published before the terminal manifest, and the terminal manifest replaces the running one atomically, last. The Scorer registry

The registry is a static, closed table in the code. A --scorer value is a key of that table and nothing else: it is never imported, evaluated or looked up by name, so a string such as package.module:function loads no Python and is refused as a Scorer that is not registered. A Scorer belongs to one Track (its domain); one applied to an Observation set of another Track is refused. chinook_contract_v1 is not registered yet (Chinook ticket).

Both Scorers have the same Criterion, the absolute error of the day, and differ in the Metric they aggregate from it: mae, the mean of the absolute errors, and rmse, the square root of the mean of their squares. The Metric's unit is the one the StudySpec declares for the primary metric; its direction is lower_is_better. The config_digest is the digest of the Scorer's configuration (the Criterion, the Metric and the direction): another Metric is another digest.

What is checked, in order

  1. The Study exists; the Scorer is in the registry.
  2. The Observation set and the References set exist in the Study, and the Scorer belongs to the Observation set's Track.
  3. Every artifact read is read back against its digest: the Observation set record, the normalized outputs, the raw predictions it was made from, the population and the References. One that no longer matches is an integrity refusal (chapter 04, ARTIFACT_INTEGRITY, exit 3) and nothing is written.
  4. The Partition of the Items is dev. An Assessment on public_check is refused with its own code until the Exposure journal exists; on any other Partition (train) with another. Running predictions on public_check with run ml is not an Exposure and stays allowed.
  5. The Items of the Observation set must be Items of that Partition, each once.
  6. Each expected Item (every Item the population holds for the Partition, whatever the outputs hold) gets its Criterion; the Metric is aggregated from the scored ones. per_item.csv is published, then assessment.json, last.

The Assessment record

assessments/ASSESSMENT_ID/assessment.json is canonical JSON, validated against the contract schema before it is written and when it is read. assessment_id is a UUID, new each time. counts holds one counter per key of the schema, named for the key (the specification's N_expected is expected). attempted is the Items that were produced or failed (a missing Item was never attempted). For a numeric loss, correct and incorrect are null: an absolute error is not a binary verdict; the other counters are filled. scored + unscored + errored = expected. The Metric has the number of scored Items as its denominator; with none, its value is null with the Reason no_scored_item.

Limits

No lock yet

assess writes into the Study like run ml does: the writer lock is a separate ticket of issue #9, and until it lands nothing stops two commands from writing at once.

No Comparison, no report

Two Assessments are not compared yet, and nothing summarises them: the Comparison and the report come later in issue #9. The record's rescoring field (the earlier Assessment and the cause) is defined by the schema but not written.

Dev only

Items of public_check cannot be assessed until the Exposure journal exists; Items of train never can.

Regression only

The agentic Scorer chinook_contract_v1 joins the registry with the Chinook ticket; its Observation sets cannot be assessed before.
