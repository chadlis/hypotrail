init --workload chinook creates a Study of the tool-using agent Track. import agent adopts answers produced elsewhere, as JSON Lines, as an Import Attempt of that Study: one line for every expected Case and Repeat, a failed or missing line included. assess --scorer chinook_contract_v1 scores the kept Observation set with the Scorer of chapter 03 and writes an Assessment: four Criteria per Episode, each with a state and a Reason for every non-score, the counters of CMP-03 and the two named rates of CMP-04. Nothing here runs a model or a tool, opens the Chinook database or imports Inspect. This chapter describes what exists for JSONL answers, on dev; an Inspect log, which needs Inspect, is chapter 09.

A Chinook Study

init reads the Workload's track: tool_using_agent goes to src/hypotrail/agentic/study.py, temporal_regression to the code of chapter 04. The data is verified against its lock first (this one check opens the database and counts its tables); nothing is created before it passes. The Study then keeps a copy of the database and three Study artifacts, each with an ID: the memberships (which Partition each Case belongs to), the References set exactly as the Workload declares it, and the answer schema (table-answer/1) the Scorer checks answers against. The References set is therefore frozen in the Study: assess reads no Workload file.

The Study's primary metric is the primary Criterion of its Assessments. The Workload declares it as data (primary_criterion in examples/chinook/workload.json, closed to the four Criteria of the Scorer by workload.schema.json) and init copies it into the StudySpec, so it is frozen with the Protocol. Chinook declares contract_success (owner decision 1A on issue #9). The Workload also declares the question, the objective and the limitations the StudySpec needs; init refuses a declaration without one of them or without the primary Criterion (DECLARATION_INCOMPLETE). The Protocol digest covers the Cases of each Partition, the memberships, the References, the answer schema and the database by their bytes, and the primary Criterion; it holds no Configuration. A command of the other Track on a Study is refused with UNSUPPORTED_CAPABILITY (chapter 04).

The command: import agent

import agent is in src/hypotrail/cli.py; the work is in src/hypotrail/agentic/imports.py. The lines and the population

The population is {"episodes": [{"case_id", "repeat"}, ...]}: the Episodes the file must hold, every Case taken from one Partition of the Study's Protocol, each Episode once. The expected keys come from this file checked against the Protocol, never from the answers: a line cannot add an Episode to it. The source holds exactly one line for each, whatever its order; a Case or a Repeat the population does not list is refused (an unknown Case, a Case of another Partition, a Case the population does not list and a Repeat out of range each have their problem value). A line is a JSON object with the keys below. A key the table does not list is ignored: the original file is kept as it is.

A produced line carries one answer: raw_answer (the text the system returned) or final_answer (an already-parsed JSON object, as the kit's fixture has it). Both is refused. Each Observation records answer_given_as, and a final_answer is scored as its canonical JSON text. The answer of a failed or a missing line is not scored: it stays in the original file only. A trace, when present, is a list of the projected steps the Scorer reads (plain records, each with a kind, as hypotrail.agentic.projection produces them); it is kept as data and nothing in it is executed.

Usage, metadata and settings

A line's usage and metadata reach its normalized entry, and a line without them gives an entry without them, so the normalized bytes of a line that holds neither are those of an earlier import. The normalized usage has one shape for every import (an Inspect log keeps cost_usd and by_model null):

Key of the normalized usageHolds
latency_secondsThe sum over the line's models, or null when a model's is null.
tokensThe sum over the line's models, or null when a model's is null.
cost_usdThe sum over the line's models, or null when a model's is null.
by_modelThe line's usage object as given.

settings is declared on each line, as producer is (D-155 on chadlis/hypotrail#75, item 1). When every line holds the same map, compared whole, the Observation set's provenance records it as settings with origin: declared; when a line has none or two lines differ, settings is unknown and listed in unknown_fields. An Inspect log import records it unknown. The request identity covers it through the source's digest.

The descriptive measures of an agent Comparison (chapter 11) sum usage.latency_seconds, usage.tokens and usage.cost_usd over the Episodes that ran, each only when it is known for every one of them, and give null otherwise: the cost of a side comes from its lines' cost_usd. No Criterion and no Comparison check reads usage, metadata or settings (D-154 on chadlis/hypotrail#75, item 3).

What is checked, in order

  1. The Study exists and the writer lock is free; the Study is of the agent Track (UNSUPPORTED_CAPABILITY); the bytes of the Workload's other files and licence notices are checked against its lock, the database is neither opened nor hashed (the Study's copy of it, read back against its digest, stands for it), and the Study's artifacts are read back against their digests.
  2. The two files are read and their sha256 taken. The request is identified (below). The same request_id with the same request ends here with the recorded Import: nothing is validated again, written or scored.
  3. The Protocol of the Workload is still the Study's (PROTOCOL_CHANGED): the Cases, the References, the answer schema and the primary Criterion are compared by their bytes, and the database by the digest of the Study's copy.
  4. The population is checked, then every line of the source in file order: JSON, an object, its fields, its status, its answer, its place in the population, its uniqueness; then every Episode of the population must be present.
  5. Only then is anything written: the running manifest, the original files, the validation report, the normalized Observations and the Observation set, and the terminal manifest last. A refusal at step 4 writes nothing at all.

An Import whose file holds failed or missing lines is completed: its manifest holds item_counts by execution status. The Import is an Attempt of the same Study as any other: operation: import, Mode external_unknown, and its Observation set has origin: imported. Nothing in the file is executed or deserialised as code; a source with the extension of a pickle, joblib or array dump, or whose first byte is the pickle marker, is refused as SOURCE_SERIALIZED before it is read as text.

What is known about the producer

Each field is {"value": ..., "origin": ...} in effective_config.producer and in the Observation set's provenance. A field is declared when every line of the file states the same non-null value, and unknown otherwise (a line that says nothing, or two lines that disagree, make it unknown; the original file keeps what each said). No field is verified: a claim in an external file is not checked by importing it. The model, the date of generation, the historical protocol and the tool use stay unknown unless the file establishes them; the kit's fixture states none of them. Whether the producer saw public_check values is always unknown. The import time (import_time, also the manifest's started_at) is a separate field from generation_time. No record states that the producer worked independently, and the origin the file declares is kept as a declared field, never as the Import's own: the fixture's Observation set says file_origin: authored_fixture (declared), and nothing names it llm_live or a provider's model. unknown_fields of the Observation set lists the fields whose origin is unknown.

The request

The identity of an import holds every element of chapter 04's list: the command (import agent), the Workload, the Configuration (unknown), the Partition of the population, the Mode (external_unknown), the model (the declared one, or unknown), the repeats (the largest Repeat of the population plus one), the digests of the database, the source and the population, and the code revision. The same request_id with the same request returns the recorded Import; with any element different it is REQUEST_CONFLICT (exit 6).

The command: assess with chinook_contract_v1

assess keeps the flags of chapter 05. A Scorer of the agent Track is routed to src/hypotrail/agentic/assess.py; the registry (src/hypotrail/core/scorers.py) holds chinook_contract_v1 at version 3 and its config_digest, and the one scoring function stays in src/hypotrail/core/chinook_contract.py (ADR 0001: one function per Scorer, never duplicated). It reads the Observation set, the frozen References and the kept answer schema, and nothing else: with the model, the tools and the database made to fail if used and Inspect not importable, import agent and assess succeed (a test runs both in a subprocess). An Assessment of public_check Episodes is refused until the Exposure journal of issue #9 exists, as rescoring and counting refuse them.

Every expected Episode gets a state for each of the four Criteria. An answer is scored by the Scorer exactly as chapter 03 describes, a final_answer object as its canonical JSON text; every scoring record states answer_read_from (raw_answer, embedded_object or none). An answer without a trace has exact_table and format_valid scored and evidence_link_valid unscored with the Reason trace_missing. contract_success keeps the Scorer's rule: it is scored false as soon as one dependency is false, even without a trace (a wrong table, a malformed or wrapped answer); only an answered Episode with no dependency false has it unscored with trace_missing. The kit's fixture is the example: D01 and D03 are answered, exact and well-formed, so their primary Criterion is unscored; D07 and D08 (not_answerable, needs_clarification) need no tool call and are true. An Episode without an answer is never scored false:

Execution statusState of every CriterionReason
failedunscoredexecution_failed
missingunscoredobservation_missing

An Episode that the Observation set does not hold at all is handled as missing. A crash of the scoring machinery errors the Criteria of that one Episode (errored, Reason scoring_failed, the exception's type only); the others are scored.

The counters and the two rates

The primary Criterion is the one the Study names (contract_success for Chinook). The envelope, assessment.json, holds primary_criterion, the counters of that Criterion as counts, and its two named rates as metrics. The other three Criteria are secondary: each keeps its counters and its two rates in metrics.json, referenced by detailed_metrics_ref, and none of them is in the envelope's counters. The counters are those of CMP-03 under the contract schema's keys (the ticket's N_x is the key x); scored = correct + incorrect.

Choices and limits worth knowing

The primary Criterion is data

Which Criterion is primary is declared by the Workload and frozen by the Study, not chosen by the code. An import without a trace therefore leaves the primary unscored for an answered Episode whose dependencies are not false, and the rate that counts confirmed successes stays low until traces exist.

Claims are not checked

The model, the date, the protocol, the tool use and the origin are only what the file says, and only when every line says it. The authored fixture is a hand-written file: it does not satisfy a live recipe.

The trace format is the Scorer's

A trace is a list of the projected steps the Scorer reads, not an Inspect log. An Inspect log is imported by the same command and read through its public API: see chapter 09.

Not built

A command that runs the agent into a Study. Corrected References are chapter 10, the Comparison of two agent Assessments and its matrix chapter 11, and the Exposure journal that lets assess take public_check Episodes chapter 12.

The tests are tests/test_agent_study.py, tests/test_import_agent.py and tests/test_assess_agent.py (every criterion of the ticket), tests/test_study_lock.py (the second writer) and tests/test_handbook.py (the tables of this chapter against the code). They run offline and call no model.
