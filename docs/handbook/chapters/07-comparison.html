compare takes two Assessments of a Study, one named the Control and one the Candidate, and writes a Comparison record into the Study. It reads what the Study keeps (the Assessments, their per-Item files, the Observation sets and Attempt manifests they point to) and nothing else: it fits nothing, predicts nothing and calls no model. A Comparison is strict when everything that makes two Assessments comparable holds, and descriptive when one side is an Import. Items are aligned by row_id, and a Comparison never rests on a hidden intersection: if the Items differ by one, it is refused. This chapter describes the temporal regression Track, on dev; the Comparison of two agent Assessments, which aligns Episodes by Case and Repeat, is chapter 11, and the report and the Exposure journal are later work (see Limits).

The command

compare is in src/hypotrail/cli.py; the work is in src/hypotrail/core/comparison.py, a core module (ADR 0001): it imports neither a Track, scikit-learn, NumPy nor Inspect, and runs where Inspect is not importable. It follows the rules of chapter 04: with --json, stdout holds one JSON object, {"ok": true, "comparison": RECORD} or {"ok": false, "error": {"code", "message", "stage", "details"}}, and the diagnostics (each warning of the Comparison, the refusal) go to stderr; without it, stdout holds one line, which names beside the status the code of a warning a compatible Comparison can hold (the warning codes below). The two ids are assessment_id values of Assessments the Study keeps (chapter 05). Each call writes a new Comparison with a new comparison_id; another Comparison of the same Assessments never changes an earlier one.

compare writes to the Study, so it holds the Study's writer lock for its whole execution, as init, run ml, import ml, recover and assess do: while another writer holds it, compare is refused at once with STUDY_LOCKED (exit 6) and writes nothing (chapter 04).

What is checked, in order

Both Assessments must exist in the Study (ASSESSMENT_NOT_FOUND, exit 2), and every artifact read (the Observation set, its Attempt manifest, the per-Item files) is read back against its digest (chapter 04, exit 3). Then the checks below run in this order, and the first one that fails refuses the Comparison with its own code and exit 3. The refusal's details carry the check, its Reason code (reason), the values of both sides (control, candidate) and the checks evaluated so far (checks). Nothing is written when a check fails.

One guard on the Partition comes with the population check. Once the populations are known to be the same, a Partition other than dev and public_check is refused with COMPARISON_PARTITION_NOT_DEV (exit 2). A Comparison of public_check Items is an Exposure: once the Items and the Mode have been checked, and before the differences are paired, the Study's freeze record is written if the revision has none and one journal entry names the Comparison and both sides (chapter 12). A dev side against a public_check side is two populations and is refused as such.

Strict against descriptive

A Comparison is compatible (strict) when every check passes. A Comparison where a side is an Import is descriptive_only, never strict: what an Import records about its producer (model, generation time, whether it saw public_check) is declared or unknown, never verified (chapter 06), so the Comparison supports no claim that the two sides were produced under the same conditions. Its record carries a warning on that scope (code COMPARISON_DESCRIPTIVE_IMPORT) in warnings and in limitations, and the command prints it on stderr. The population, References, Scorer, unit and Items checks still apply to it. The status incompatible exists in the schema but is never recorded: an incompatible pair is refused, and no record is written for it.

The Comparison record

comparisons/COMPARISON_ID/comparison.json is canonical JSON, validated against the contract schema before it is written. roles names the Control and the Candidate; left_assessment_id is the Control and right_assessment_id the Candidate. delta is the Metric of the Candidate minus the Metric of the Control, taken from the two Assessments: for regression_mae_v1, delta_mae = MAE(Candidate) - MAE(Control), and a positive value means the Candidate is worse. An improvement is never required. paired_deltas_ref is the per-Item file: the absolute error of each side and their difference, per row_id. coverage counts the expected Items, those scored on each side and those paired. population_ref is the population identity: the Partition, the digest of the population artifact and the row_ids. code_environment compares the two Attempts' code environments (Python, dependency lock, code revision): when they differ the record says so, naming what differs, and its limitations state that the two executions are not identical. When a side is an Import, its recorded environment is the importer's, so same is null, and the limitations say that a shared environment is not established. When they are the same it still does not claim that the executions were identical. The record holds no confidence interval: daily observations are dependent.

Limits

Regression here

This chapter's checks and record are those of the temporal regression Track. Two agent Assessments are aligned by Case and Repeat, with more checks and a matrix, in chapter 11. The bike Comparison records no latency or cost. The report comes later.

Exposure and marks

A Comparison of public_check Items is recorded as an Exposure (chapter 12). The record's check_informed field is written when a Configuration the first freeze record does not hold marks a side; declared_factor is written for an agent Comparison only.

Population identity

The identity of the population is the Partition and the digest of its expected Item IDs, read from the Study's memberships (native Attempt) or from the population file of the Import. The Items are then compared through the per-Item files.

Import

The code environment recorded for an Import is that of the process that imported it, not of its producer, which is unknown. A Comparison with an Import is descriptive for that reason too.
