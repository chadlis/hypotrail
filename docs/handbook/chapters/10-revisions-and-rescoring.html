A Study holds one frozen Protocol per revision, and a Protocol change is a new revision inside the same Study. A corrected References set changes the Protocol, so it is added with init --study DIR --new-revision. So is a changed Case text, which is part of the Protocol too: a Study created before the change refuses a new request with PROTOCOL_CHANGED until init --study DIR --new-revision adds the revision that holds the new text. For a corrected References set, the corrected set is published beside the old one, the StudySpec of the earlier revision is kept as it was, and nothing an earlier revision references changes by a byte. An Assessment of a corrected set scores the same Observation set again, and says which earlier Assessment it differs from and why, so a corrected Reference is never read as a change of the evaluated system.

The command

init --new-revision is in src/hypotrail/cli.py; the work is in src/hypotrail/core/revisions.py and, for each Track, in the new_revision function beside init_study (src/hypotrail/ml/study.py, src/hypotrail/agentic/study.py). The Study names its Workload, so the command takes no --workload (giving one is INVALID_ARGUMENTS, as is init with neither). It reads the Workload again, from --examples-dir or the checkout's examples/ (chapter 04), verifies its data against the lock before anything is written, and derives the Protocol it declares now: the population, the Partitions, the References, the rules on when information is available. With --json, stdout holds {"ok": true, "study": SPEC} with the new revision's StudySpec, or the error object of chapter 04; without it, one line.

The command holds the Study's writer lock for its whole execution, as every command that writes to a Study does: a second writer is refused at once with STUDY_LOCKED (exit 6) and writes nothing.

# a corrected References file in the Workload; the Study keeps the old set and adds the new one
uv run python -m hypotrail init --study runs/chinook --new-revision
# the new References ID is in `artifacts` of study.json and in `status --json`
uv run python -m hypotrail status --study runs/chinook --json

What a revision keeps and what it adds

Every artifact the Protocol freezes (the dataset, the population, the References, the answer schema) is compared by its bytes with the one the current revision holds. One whose bytes did not change is carried over as it is: same path, same digest, same ID, same version. One whose bytes changed is published beside the earlier one, under a path that names its first sixteen digest digits, with the next version number and an ID that names its digest; the earlier file is never replaced. A References set is versioned as a whole: version 1 is the set init froze, version 2 the first corrected set.

study.json always holds the current revision, so every other command keeps reading one file. When a revision is added, the StudySpec of the one before is copied byte for byte to revisions/N/study.json, the new StudySpec is published as revisions/N+1/study.json, and study.json is replaced last, atomically. A writer killed between two of these steps leaves the earlier revision current; running the command again completes it. study_id stays the same for the life of the Study; revision is the digest of the StudySpec without its revision and study_id, so it differs from one revision to the next, and previous_revision chains each revision to the one before.

A Workload whose Protocol is the one the current revision already freezes is refused with PROTOCOL_UNCHANGED, and nothing is written. A Configuration is not part of the Protocol: changing one needs no revision (chapter 04).

Rescoring: the new Assessment names the earlier one

After init --new-revision, assess takes the new References ID (the one in the current StudySpec; the earlier revision's set is no longer the Protocol and is refused with REFERENCES_NOT_FOUND) and an Observation set recorded under any revision. It writes a new Assessment, as ever: a new assessment_id, the same observation_set_id, the new references_ref, and every earlier file, Assessments included, untouched. It runs no model and no tool and opens neither the database nor the Workload: the frozen References, the answer schema and the kept answers are enough. The Assessment records the revision whose Protocol it applied (study_revision) and the time (recorded_at).

Its rescoring field is null when no earlier Assessment of the same Observation set and the same Scorer differs from it. Otherwise it names the latest one that does, in the order of the later Assessment (earlier_assessment_id), the cause and the Items whose verdict changed, each with both verdicts. The cause is the first of the differences below, in this order; any other that also differs is listed in other_changes, so nothing that changed is hidden. A numeric tolerance is held by the Reference (numeric_absolute_tolerance), so a changed tolerance is a changed References set and its cause is references_version.

The later Assessment has one order, used by status (whether a Decision still applies), by assess (the earlier Assessment its rescoring names) and by report (the order in which the page lists Assessments): the position in the write journal first, then (recorded_at, id). An Assessment's position is that of the first end entry of the write journal that names it among the records it wrote, from 1; an Assessment that no entry names is at position 0, before every journaled one, as is one written before the write journal existed.

The Items are listed one per Item and Criterion, sorted. An Episode's Item ID is CASE_ID#REPEAT (D03#0); a bike Item's is its row_id. A verdict is the Criterion's state, its score (a boolean for an agent Criterion, the absolute error for a bike Item) and its reason. Because a numeric loss has no correct or incorrect, a corrected bike Reference lists the Item whose absolute error moved, and the Metric moves with it; an agent Criterion can flip from true to false, or become unscored when the Reference no longer settles a dependency. Either way the delta is the Reference's, not the system's. The human line adds rescoring of Assessment ID: cause C, N Criteria changed.

Refusals

The refusals of chapter 04 apply as they are: STUDY_NOT_FOUND for a folder that is no Study (no lock file is created in it), DATA_INTEGRITY when the Workload's data no longer matches its lock (checked before anything is written), STUDY_LOCKED and the integrity refusals. Limits

Freeze and check_informed

A revision takes its own freeze record, revisions/N/freeze.json, at its first use of public_check, not when it is created. A revision created after the Study's first Exposure is marked check_informed by check_informed_mark in core/revisions.py; one created before is not. After an Exposure, an assess or compare on public_check Items that finds a Protocol other than the current revision's is refused with PROTOCOL_CHANGED (exit 3) and writes nothing (chapter 12).

The population is not compared

An Assessment applies the Protocol of its own revision to an Observation set recorded under an earlier one. assess reads the Items from the Observation set's own population and does not compare it with the new revision's population: a revision that changed the population is the author's to read.
