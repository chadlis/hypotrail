decide records one decision in a Study: the question it answers, the option chosen, who decided (a human or a proxy, with a declared source if any), the ids of the Study's records it concerns, and the write sequence its author read. The Study is the only decision authority: a decision is a record of the Study, kept in a file of its own and never rewritten, and nowhere else. decide calls no model; it records what its caller says, after it has checked the ids and the sequence.

The command

decide holds the Study's writer lock for the whole command, as every command that writes does: a second writer is refused at once with STUDY_LOCKED and nothing is written. It requires --request-id and --read-sequence (chapter 04): a decision is made on the write sequence its author read, and a decision made on an older sequence is refused with STUDY_CHANGED, which names what was written since. Given the current sequence, decide records the decision and advances the write sequence by 2, like every command that writes. It creates or changes no file outside the folder given by --study.

The question and the option are free text, and neither may be empty. The author is human or proxy, recorded by its kind only: a human has no name field. --source is a declared source, a text, optional for either author; it is recorded as given, or as null. --artifact ID is repeated for each id the decision concerns, and at least one is required. A duplicate is recorded once and the ids are sorted, so the same ids in another order are the same decision.

With --json, stdout holds one object, {"ok", "replayed", "decision"}, the same shape as run's with the decision in place of the Attempt.

The ids a decision may cite

An id is citable when the Study holds a record with that id, of one of these kinds: an Attempt, an Observation set, an Assessment, a Comparison, a Study artifact (references-<digest>, for example), a revision, a freeze record, an Exposure entry or a decision, whose id is its decision_id. decide looks the id up in the Study's records. A revision is cited by its revision value, the id check_informed gives it; its revision_number is not citable, so that one revision never appears under two ids and "the same decision" stays one thing. A request_id, the study_id, a path and a file's content digest (sha256, protocol_digest) are not citable either: they name no record. An id the Study does not hold is refused with CITED_ID_NOT_FOUND, which lists every unknown id, sorted, and nothing is written.

status --json lists no Observation set, Assessment or Comparison: a caller finds those ids in the Study's records, and the listing of them in status --json waits for a later change. It lists the decisions the Study holds, with whether each still applies (the history below).

The request identity

A Study has one request_id namespace, for its Attempts and its decisions (chapter 04). "The same decision" is the same question, option, author, source and cited ids, the ids de-duplicated and sorted; the read sequence is not part of it. The same request_id with the same decision is a replay: it is found before the stale-sequence check, so a client whose answer was lost can repeat its decide after its own write moved the sequence on. It returns the recorded decision with replayed true and writes nothing.

The same request_id with another decision is REQUEST_CONFLICT (exit 6). Its differs lists, in this order, the fields among question, option, author, source and cited_ids that differ, under the decision record's own field names, and decision_id names the recorded decision. A request_id that names an Attempt is a conflict too, with differs ["command"], attempt_id set and decision_id null; and a request_id that names a decision is a conflict for run and import, with decision_id set and attempt_id null.

The checks come in the order of every writer: the arguments (REQUEST_ID_EMPTY, DECISION_FIELD_EMPTY, the author), STUDY_NOT_FOUND, the lock, the request identity, STUDY_CHANGED or WRITE_SEQUENCE_AHEAD, then CITED_ID_NOT_FOUND. A refusal appends nothing to the write journal.

The decision record

The record is canonical JSON, of the record kind decision of the contract schema (DecisionRecord): validated before it is written and after it is read, with a fault reported as CONTRACT_VIOLATION. revision is the revision of the Study's current StudySpec, read under the lock after the stale-sequence check, so a decision made after init --new-revision holds the new one. write_sequence is the position, in the write journal, of the begin entry of the decide that recorded it; read_sequence is the value its author read, and for a recorded decision it is always write_sequence minus 1.

The decision history

status --json lists the Study's decisions under the top-level key decisions, in the order they were recorded; a Study with no decision lists none ([]). Each entry holds every field of the decision record, as decide recorded it, and two keys that are not in the record: applies, whether the decision still applies, and reasons, why it does not. reasons is always present, and is [] when applies is true. Each reason is {"reason", "id"}, id being the id that caused it.

The human output of status gains one line when the Study holds decisions, for example Decisions: 4 recorded, 1 no longer applies; a Study with no decision prints no such line.

When a decision still applies

A decision no longer applies when any of these is true. The rule is computed when status reads the Study, from the ids the decision cites and the records of the Study. It is never stored: nothing is written when a decision stops applying, the decision's own file is byte for byte the same, and status takes no lock, advances no write sequence and writes nothing. No record marks a decision outdated, and the rule is no general invalidation engine: it reads these three things and nothing else.

  • cited_id_not_held: a cited id is no longer held by the Study, that is, the Study holds no record with that id any more. The reason's id is that cited id.
  • revision_changed: the Study's current revision differs from the revision its record stores, for example after init --new-revision. The reason's id is the current revision's revision value, the id check_informed gives it. A cited record made under an earlier revision does not by itself make a decision outdated: an Assessment may apply its revision's Protocol also to outputs recorded under an earlier revision.
  • assessment_superseded: a cited Assessment has a later Assessment of the same Observation set and the same Scorer id, with the Scorer at any version, so a rescore under a new version supersedes the earlier one. An Assessment of the same Observation set by another Scorer does not. The reason's id is the later Assessment's id (the latest, when there are several).

"Later" is the position in the write journal (chapter 04): an Assessment's position is that of the first end entry that names it in its written list. A record that no end entry names counts as position 0, before every journaled record: so does an Assessment written before the write journal existed. Ties are broken by (recorded_at, id), the order rescoring.describe uses. A later decision on the same question changes nothing: it does not make an earlier one outdated.

Limits

Read at view time, never stored

Whether a decision still applies is computed each time status reads the Study. No record is written when it changes, and the Workloads and the panel do not show an outdated decision yet.

Free text, no declared question

The question and the option are the caller's words. The Study declares no question with options yet, so nothing checks that an option is one of a list.

A decision is not an Exposure

Recording a decision reads no public_check Item and writes no freeze record or journal entry of the Exposure journal. It cites ids; it does not show what they hold.
