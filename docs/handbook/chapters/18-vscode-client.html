The VS Code client is a TypeScript extension that talks to the CLI through one module, the bridge. It reads a Study and records a Decision only through the CLI, and holds no Decision, no record and no path of its own: the Study is the only decision authority (ADR 0004). It ships the bridge, the way to find a Study, and a panel that shows a Study's pending decisions with their evidence. Of the chat channels, Claude Code's is the UserPromptSubmit hook template below, and Copilot's is the two tools of the extension with the template of Copilot's instructions file, both below.

Where it lives, and its tooling

The choice of the client's location and tooling, which ADR 0004 leaves to L2.4, is recorded here. The extension is written in TypeScript, with the compiler as the only build step: no bundler, and the compiler's output folder is generated and not tracked. Its development dependencies are the compiler and the type definitions of VS Code and of Node; it has no runtime dependency. Its tests are TypeScript under its test/ folder and run under Node's own runner (node:test), with the vscode module replaced with a stub of that folder: no test runs inside VS Code. The second job of .github/workflows/tests.yml installs the locked development dependencies and runs them on every pull request; the job pytest runs the checks that read the client's files with no Node.

The literal lists the client uses (the CLI's program and arguments, the limits, the outcomes, the walk) are kept in the extension's contract.json, which the extension imports and the handbook's tests read: the tables of this chapter are compared with it.

The bridge

The bridge (src/bridge.ts) is the only part of the client that starts a process. It starts the CLI with execFile and a list of arguments, never through a command interpreter, from the checkout root: two folders above the extension's own folder. It has no setting. A Study path is given to the CLI joined to its flag with =, as one argument, so a path that holds spaces, quotation marks or a leading dash reaches the CLI unchanged. A second read starts the CLI again: the bridge keeps nothing between two calls.

The bridge has two reads. The first gives the object the panel shows; the second gives, for each Comparison of the Study, its paired deltas and the bins and the five numbers of a box computed from them (chapter 17 holds that read and its definitions). The second read starts the same program with the same first arguments, from the same folder and with the same limits as the first, and gives back one of the three outcomes of a read in the table below, under the same rules, with the same causes. Like the first, it never gives back the outcome of a call the bridge did not start, which only a write gives, and when the CLI answers with ok true every key it printed is kept, a key the client does not know included.

Writing a Decision

The client starts three commands of the CLI, two to read and one to write, and no other: the bridge's list is closed, and a test compares it with the functions that start a process, both ways. The commands that write to a Study and are not in it keep no request id of their own (the dated line of 2026-11-23 in ADR 0004).

A caller gives the bridge a Decision to record and the Write sequence it read, which it takes from the object of its last read. Each flag goes to the CLI joined to its value with =, as one argument, so a text that begins with a dash or holds a quotation mark reaches the CLI unchanged. The bridge exports a function that makes a new request id, and never makes, changes or repeats one of itself: one call starts at most one process, whatever the outcome. A repeat is the caller's explicit second call with the same id, on whatever Write sequence it gives; the CLI finds it before the stale-sequence check and gives back the recorded Decision (chapter 17).

The bridge checks the inputs of a write before it starts anything. When one fails it starts no process and gives back the client's own outcome, which lists every failing input in the order of the table below and holds no code and no message. What the CLI refuses itself, such as an empty list of cited ids or a kind of decider it does not know, reaches the CLI and comes back as the CLI printed it. When a write gets no answer, its outcome holds the phrase of the table below, since the write may have happened: a killed writer has still advanced the Write sequence, and the next read shows what was written. A read with no answer does not hold them.

Finding the Study

A Study is a folder that holds a study.json. The client finds the Studies of the workspace through a walk, breadth first from each workspace folder, which follows no symbolic link and looks for the file's name without reading the file. It gives the Studies as absolute paths, in the order of their paths. With one Study the client takes it; with several it asks with one pick; with none it shows the message below, opens no dialog and remembers nothing. The owner opens the checkout, or the Study's folder, as the workspace.

The panel and its content security policy

The extension contributes one command. It finds the Studies of the workspace as above and opens one webview panel on the Study found or picked; with no Study it creates no panel. A second run while the panel is open reveals that panel and creates none; once the panel is closed, the command creates one again. The panel holds what it was opened on in memory only, for as long as it is open. Its document shows what the Study holds, as the section below says.

The panel is created in one place, with the options below, and every document the client gives to a webview is built in one function. The document holds exactly one content security policy, in a meta element, whose directives are those below, in this order, joined with a semicolon and a space, with one nonce made for each document of letters and digits. It holds exactly one script and one style element, each with that nonce, no style attribute and no inline event handler. No element or attribute of the document holds a remote address, and a text of a Study is shown as text, whatever it holds. The colours come from VS Code's own theme variables, and the script sets no style, as the section on the panel's style says.

What the panel shows

The panel reads its Study through the bridge when it is opened, through the command or through a link, after each write the CLI answered, and when the reviewer presses Read again; each of these reads, when it succeeds, is followed with the bridge's second read, and it reads at no other time: no watcher, no timer, and no read when the panel is hidden or shown again. After a first read that fails, no second read follows. While a read is in flight, the second read included, the document says so, a press of Read again starts nothing, and an opening only reveals the panel; no document is built between the answer of the first read and that of the second. The extension builds each document whole from the objects it read, and keeps in memory, besides the target, only the object of the first read, whether a call is in flight, from a write with no usable answer to the answer of its repeat, that call's request id and arguments, and the last second read: the object of that read, kept only when it can stand beside the first.

The object of the second read can stand beside the first when the second read succeeds, carries the same Write sequence, and holds one entry with all its keys for each Comparison the first read lists. Otherwise the second read counts as failed: the document holds what the first read gives, the decision included, and nothing of the second. In the part of each Comparison, under the heading of its paired deltas and where its histogram and box plot would stand, a fixed sentence says that no figure is drawn: it follows the fixed word of a failure, in the style of the panel's other failures, as a link to the top of the document, where Read again stands; the same sentence stands for an entry that gives no reason but whose bins, numbers or paired deltas cannot be drawn. A Comparison whose delta is withheld keeps the word of a withheld delta alone. A later failed second read drops the object an earlier one gave.

The document opens with its heading: the Study's path, as the string the panel was opened with, so that with several Studies the reviewer sees which one is open. Beside Read again stands a link to the choices of the first pending decision, when one is pending. The document then shows the Study's id whole and its Write sequence, then the count of pending decisions under their heading and each pending decision in the order the CLI lists them, the second and later ones each after a rule. A pending decision opens with the core's wording of the decision; then comes the Comparison it names, with its delta, its coverage and, where the delta record carries them, the Control's and the Candidate's values; then a chart of the two values the delta compares; then the histogram and the box plot of its paired deltas, after the dots of its Items or Cases when there are fewer than ten; then a line with the count of the Comparison's warnings and of its limitations, each a link to its list; then its choices, as one group the wording names, each choice in bold with its consequence on a muted line under it, its radio input named after the choice alone and described with the consequence, and the control that records, which the wording also describes; then the core's own sentence on what the delta's sign means, a chart of the coverage, the warnings and limitations the Comparison recorded, and, from ten Items or Cases, their dots; and last the two Assessments it depends on, each under its role with every Metric. When nothing is pending, a fixed sentence stands where the first decision would. The recorded Decisions follow, as the next section says, then the Declared deviations, each with whether it is withdrawn; a fixed word stands under either heading when the Study holds none. A number that is not an integer is written with six significant digits and an integer as held; a null number is written with a fixed word.

The first chart draws the Control's and the Candidate's values of the Metric the delta names, from the delta record where it carries them and otherwise from that Metric in each role's Assessment, under the delta's own line; when the delta is withheld, or neither the delta record nor the Assessments hold the Metric, it is not drawn. The second draws one bar per role: its scored part over what was expected, the rest of the bar outlined and dashed, so that the two parts differ in more than a colour; it is not drawn when the coverage lacks those keys. Each bar is a name, a track and its value as a link, as every number is, and the bars of one chart share one grid, so that equal values draw tracks of equal length. The client computes the lengths of its bars and the places of the marks of its histograms, box plots and dots, and nothing else: a bar's length is its value over the largest value of its chart, from zero, clamped to the track; what is pending, the delta, the roles and every value shown are those the object read holds, and a key it does not know is ignored.

Each figure of a Comparison is drawn from its entry of the second read, from its paired deltas: the difference of each Item on the Regression Track and of each Case on the Agent Track. The histogram and the box plot stand in the Comparison's part under the first chart, so that in a pending decision they stand above the line of its warnings and limitations and above its choices, under a heading that ends with the delta's unit; the delta's definition follows the heading as their caption. First a histogram: one column per bin, in the order of the bins, each column's height its count over the top of the axis, which is the first of one, two, two and a half, five and ten times a power of ten at or above the largest count; each bin's count stands above its column, under a caption that names what a bin counts; one bin whose low equals its high is one column across the width. Under the histogram's baseline stand the two ends of the axis, one when they are equal, with the unit between them; the box plot under them shares that axis: a whisker from the minimum to the first quartile and one from the third quartile to the maximum, each ended with a short stroke, the box between the two quartiles, the median across the box, and a mark at the Comparison's own delta, which is the delta shown above and is not computed again; the delta's mark runs the whole height of the box plot and is twice as wide as the median's, so that the two differ in more than a colour. When zero lies on the axis, a thin mark stands at zero through the histogram and the box plot. A key under the box plot names the five numbers, the delta with its value and the zero mark, in the order they stand on the axis. When the five numbers are equal, every mark of the box plot stands at the middle of the axis, and no place is divided through a range of zero.

The dots come under a heading that names what they place, the absolute error per Item on the Regression Track and the shares of the two sides on the Agent Track, then the unit when they stand at the end of the part, and a key that names the Control and the Candidate, then a fixed sentence that says the rows run from the Candidate's worst and the joining bar takes the colour of the better side: one row for each element of the paired deltas, each holding the id of its Item or Case as a marked text, not a link, beside the marks of its two sides on one scale that all the rows of the Comparison share. The rows run from the Item or Case where the Candidate is worst to the one where it is best, in the order of its paired delta as the second read gives it, rows of equal paired deltas in the order the second read gives them. The Control's mark is a tall narrow bar and the Candidate's a shorter one across its middle, so that the two differ in more than a colour, and a thin bar joins them in the colour of the side the row favours: the lower absolute error on the Regression Track, the higher share on the Agent Track; it keeps the colour of a neutral line when the two are equal. The scale runs from the smallest to the largest of those values, not from zero, and its two ends stand above the first row, one when they are equal; no value is printed beside its marks. The id column is as wide as the longest id, up to a limit. From ten elements, where the panel is wide enough, the rows run on in further columns of one width, under the heading, the key and the sentence, which span them all; no row is hidden. With fewer than ten elements, the dots stand first, above the histogram; from ten, they stand at the end of the Comparison's part, after its limitations, and a link under the box plot leads to them. When every value is equal, every mark stands at the middle of the scale, and each number is halved before a difference is taken, so that no place is divided through a range of zero or through one too large to be a number. Each number a figure prints is a bin's count, a bin's edge, one of the five numbers, the Comparison's delta or an end of the scale of the dots, written as every number is and as a link to the Comparison's part; the client prints no number of its own, and the height of a column, the top of the axis, the place of a mark and the order of the rows stand only in the drawing. An entry that gives a reason instead of its bins and numbers shows a fixed sentence, then that reason, in the neutral style of the panel's notices, and no dot, under the heading of its paired deltas, unless the reason is that the delta is withheld, as the next section but one says.

A read that the CLI refuses shows the CLI's code and message unchanged; a read with no usable answer shows its cause after a fixed text; either failure opens with a fixed word that says it failed. Either way nothing of an earlier read stays: the document holds the failure and Read again. Every word the panel prints is an entry of clients/vscode/contract.json.

What the panel shows of a recorded Decision

After the pending decisions, the panel shows each recorded Decision in the order the CLI lists them. Its part opens with its outcome: what was chosen, whole as recorded, beside the phrase of whether it applies; then its id, the wording of the decision it answers, and, when its evidence changed since, the state of the whole, with the reason revision_changed beside it when the Decision holds that reason, and each line of its evidence with its state, its count of changed Items and, for each Metric, a chart of the cited value and the latest one, as two bars on one scale; a latest value that is null shows no bar; then each reason and its id. Then come who recorded it and each id it cites, with the Comparisons it cites as said below; whether it still applies, as the key and the value the CLI gives; and the Assessments each line names. Each Comparison the Decision cites is shown whole, as a pending one is, with the two Assessments that its roles name, unless the document already shows it whole, in a pending decision or in an earlier Decision; the Decision then shows a summary of it: its id as a link to its whole part, its delta with the definition of the delta's sign, and the chart of the two values. Recording a Decision from the panel

The reviewer records a Decision in two actions: selecting one of the choices of a pending decision, then pressing the control that records it, which stays inert until a choice is selected. The selected choice lives only in the document: the script sends the place of the pending decision and of the choice, and the extension finds both in the object it read. One write follows, through the bridge, with the wording of the decision and of the choice as that object holds them, the Comparison alone as the cited id, no origin, a new request id and the Write sequence of that object. Opening the panel, scrolling, following a link and Read again are not actions of a Decision.

While a read or a write is in flight the document says so, every control is inert and the document is marked busy for assistive technology; the notice is a live region, which a screen reader announces. When the CLI answers, the panel reads the Study once, the first read then the second, and builds one document: a notice above the first pending decision, then what the read gives. A write the CLI accepted shows its Decision among the others, with whether it applies as the object read says, and the notice names what was chosen in a link to that Decision, and that Decision's part is marked; the document's script moves the focus to the notice and leaves the view at the top. When the read holds no Decision of the answer's id, the notice is a fixed sentence with that id. A write it turned down shows the CLI's code and message unchanged in the notice, after the word that says it failed, then a fixed sentence that the Study was read again and the choice is to be made again, and for a Study written to since the read this is the backstop of a stale Write sequence. If that read fails, the document shows the write's answer and the read's failure, both: after an accepted write the answer is a fixed sentence with the id of the recorded Decision, and nothing of an earlier read stays.

A write that gets no usable answer may still have happened, so the panel reads nothing on its own. The extension keeps that call's request id and arguments in memory; every document then names the choice sent, whose radio input stands checked, as it does while the write is in flight, and says that the write's outcome is not known, in the phrase of the bridge's table above, that the Decision may have been recorded and that sending again does not write it twice, and holds Send again beside Read again, and the controls that record are inert; the first of these documents also gives the cause after a fixed text. Send again sends the same call again: the same id, the same values and the same Write sequence as the first. A read keeps the id; it is dropped on the answer to the second sending and when the panel closes, so the next write has a new one. While a write is in flight or an id is held, opening the panel, through the command or a link, only reveals it. A write the bridge itself turns down starts nothing: the notice names the missing inputs after a fixed text, no id is kept, and no read follows.

Links inside the panel

A link of the panel moves the view to another part of the same document and does nothing else: it posts no message to the extension, starts no process, opens no file and writes nothing. Each record the document shows, the Study, a Comparison, an Assessment, a recorded Decision and a Declared deviation, stands in a part of its own with its id; the part of an Assessment or a Comparison also gives the path of each output that record names, as the CLI prints it, and never the path of the References. An Assessment has one part in a document, at the first place that refers to it; every other place gives its id as a link to that part, and an Assessment that nothing shown refers to is not shown. Every number the panel prints is a link to the part of the record it comes from; when the Assessment of a line of a Decision's evidence is not among those the CLI lists, its numbers lead to that Decision's part. The texts the core supplies, such as wordings, messages, units and paths, are shown whole and hold no link.

Beside each output path that the part of an Assessment or a Comparison shows stands one control that opens that file: a button named after its label and described with the path, so that a person who reaches it with the keyboard is told which file it opens, inert while a call is in flight, as every control is, and active while a write with no answer is held, as Read again is. A ref that is null shows no path and no control. The message the control posts carries no path: it names the kind of the record's part, the place of that record in its listing of the object read and one of the refs of the table below. The extension finds the path in the object it holds and opens nothing when the message names nothing there, when the path is absolute or holds a .. segment, when the file's real path lies outside the real path of the Study's folder, or when the file does not exist; otherwise it shows the file in the editor and makes that editor read-only for the session. A file it does not open, or that the editor does not show, gives a document whose notice holds one fixed sentence. The part of an Assessment, a Comparison, a recorded Decision and a Declared deviation also gives the path of the record's own file, as the CLI names it in record_files, with one control beside it that opens that file the same way; a Decision's part also gives, each with its control, the own file of each Assessment its evidence names that the CLI lists. The extension finds that path in the entry of record_files of the record's kind and id, and composes none from an id; a record that record_files does not name has no such control. The Study's part and a Comparison's summary hold no control that opens. The References, anything of an Attempt and any path the client would compose itself are never opened, and the panel reads no content of the file: the editor shows it.

The panel's style, the guard of its layout and its own wording

Every colour the panel's style sets is a theme variable of VS Code, written var(--vscode-…), or one of the keywords transparent, currentColor and inherit, and the style sets the colour and the background of the body from theme variables, so that each keyword takes its colour from the theme. The buttons take the theme's button colours, including on hover and when disabled, and a border from the High Contrast border; no inert control or choice is drawn faded, so its text keeps its contrast; a disabled button's border is dashed, which the High Contrast themes draw, and the checked choice has an outline from the High Contrast active border; every focused control shows an outline in the theme's focus colour; the radio inputs take the theme's accent and are drawn in the scheme of the theme's kind. Each bar of a chart and each mark of a figure, a column, a whisker, its end, the box, the median, the delta's mark, a dot and the bar that joins the two dots of a row, takes its colour from a class whose rule names a theme variable, the dots of the Control and of the Candidate the classes of the first chart's two bars, and no element carries a colour, a fill or a style of its own. A figure is built as the charts are: in the extension, as text of the document, an svg of rect elements only, hidden from assistive technology and holding no text, a whisker drawn as a thin rect and a dot as a narrow one; its numbers and the ids of the dots' Items or Cases stand outside it, from the object of the second read. The style is written in TypeScript, in the document's one style element; the script sets no style, neither builds nor changes a chart or a figure, and its text holds none of the names that would set one.

A test of the client searches the values of that style for each of the forms of a literal colour of the table below, and the colours of a border, of an outline and of a shadow are searched as any other.

A second test measures the panel's document in headless Chrome, driven over its debugging port with Node's own WebSocket and no package: it sets the width of the table of the guard's bounds through device-metric emulation, checks the page's width before it measures, and fails when the wording of the first pending decision or the first evidence number stands farther from the top than its bound. The first evidence number is the delta's value of the first pending Comparison, or the delta's element when that delta is withheld; in the document the Comparison's delta follows the decision's wording, and the choices stand under the delta and its chart. The test runs with the client's other tests, with no step of its own in the workflow, and it is skipped with a named message where Chrome is absent or does not start. It is a regression guard only: the acceptance of the layout at that width, and of contrast and visible focus in the four themes, is the owner's check in VS Code. Other tests in headless Chrome, under approximations of the defaults of the four themes, check that every text of the documents of a write in flight and of a write with no answer is at the contrast of WCAG's AA, that the two equal bars of a chart are drawn equally long, that a radio input stands on the first line of its choice, that the checked choice is outlined and a disabled button drawn unlike an enabled one in the High Contrast themes, and that after a recorded write the view stays at the top with the notice focused.

Every label, heading and fixed sentence the panel prints is an entry of the label list of the table below, or one of the phrases of the tables above and of the bridge's tables, the phrases of whether a Decision applies included; each entry is in English, and a test finds in none a word that the glossary lists under Avoid, the headings on the warnings and limitations of a Comparison excepted under their names, since they name those keys of the record.

Deep links

A deep link is a vscode:// URI that the extension handles, of one of the two forms below. Its authority is the manifest's publisher and name, joined with a dot, and the manifest's activation events let a link start the extension. The query is the key and the path, which is the whole rest of the query: required, absolute, within the limit below, with no NUL character, and a Study that the walk above finds in the workspace. A valid link opens the panel on its Study, and on the Decision the second form names, as the section on recorded Decisions says. Anything else (another authority, a fragment, another path, a decision id that does not match the pattern) is refused with the one notification below, and opens nothing. A link never writes.

The two forms, the publisher and the name are a public contract of the client, which a link printed outside the repository would fix.

No state of its own

The client persists nothing and remembers no path: it has no setting, keeps nothing in VS Code's stores or in the webview's state, and writes no file. It reads what a Study holds only through the bridge, and may open in the editor, read-only, a file of the Study whose path a read names. The tests of tests/test_vscode_client.py list, over every tracked file of the client's sources, each name that starts a process, keeps state, writes a file, or reads or opens one, and compare the listing with their own, both ways: the one name that opens a file stands once, in the panel. The listing is bounded through two conventions: only the bridge imports Node's process module, through one named import of execFile, and vscode is imported only as a namespace. An escape the sources do not use and that only a planted case shows is a stated limit of that listing.

The Claude Code hook

A reviewer who records a Decision in the panel, then sends a prompt to Claude Code on the checkout, gets a first turn that knows it. The template of clients/claude-code/ does it with no kept value: a Python script that uses the standard library only, and a JSON settings fragment, settings-fragment.json, that registers the script under Claude Code's UserPromptSubmit event. It is a template a user copies, not a hook of this repository: this repository's .claude/settings.json does not register it, and the CLI has no command for it.

To install it, on a checkout installed as the first step of the install table says, copy the fragment into the project's .claude/settings.local.json (which git ignores) or .claude/settings.json, and write in its command the folder of the Study, relative to the checkout or absolute. One entry names one Study, and the script looks for no other: a checkout with two Studies gets two entries. Claude Code starts the script with python3 -I, which need not be the checkout's Python.

At each prompt the script starts one process, the CLI's read of the table below, in the folder Claude Code exports as CLAUDE_PROJECT_DIR, as the bridge starts the CLI. It starts nothing else, records no Decision and opens no file of the Study: what it prints comes from the CLI's answer. It prints, as plain text, the Study's folder and id, its Write sequence, each pending decision with what it asks and each choice's id and text, and each Decision with what it answered, the choice made, who made it and the origin it declares, how the person's own messages it holds reached its caller, or none, the ids it cites, whether it applies and the state of its evidence, the oldest first; the rule is the last line. No text of those messages is printed. An agent holds the Write sequence it read and passes it on its next write, as the rule says. Texts of the Study are printed as JSON strings, so that a quote or a line break in one stays on its line.

When the text would pass the limit of the table, Decisions are left out, the oldest first, until it fits, and the count line says how many. The Study, its Write sequence, the pending decisions and the rule are never left out: when the pending decisions alone pass the limit, the text is printed whole and Claude Code's own cap applies, which replaces the output with a file path and a preview. That is a stated limit of the template.

When the script cannot read the Study (no Study named, a Study the CLI refuses, a CLI that cannot be started or does not answer within the bound, an answer that is not one JSON object with ok true, or no project folder), it prints the failure line, which carries the rule. Every start ends with exit code zero and prints plain text, never a JSON object, so a prompt is never blocked. The fragment's time limit is above the bound, and once the bound passes the script stops the CLI's process with every process it started.

The script keeps nothing between prompts: it opens no file to write, so each prompt, in the same session or in a new one, gets the Study as it then is. The CLI's read writes nothing (ADR 0004); a cache that the package manager keeps for itself is the package manager's.

Claude Code adds the text as context alongside the prompt, with no transcript entry. The tests of tests/test_claude_code_hook.py start the script as Claude Code starts it, with no Claude Code binary and no model; whether the text reaches the model, the owner checks at the final review.

The Copilot tools

Copilot chat in VS Code reaches a Study through two language-model tools that the extension contributes and registers when it is activated: a read, with no side effect, and the write of a Decision. The table below gives, for each tool, its name, the name under which a user attaches it to a prompt, the activation event that starts the extension when Copilot first calls it, and each input with whether the manifest's schema requires it. Copilot gives no request id and no mode. The tools hold nothing between calls and call no model.

Each tool takes one Study. The write must name the folder of its Study on every call, even when the walk finds only one; the read may leave it out, and then takes the one Study the walk of the walk's table finds in the workspace. A folder a call names, resolved, must be one the walk finds, and a folder given as a path that is not absolute matches none. When the walk finds no Study, when the write names no folder, when the read names none and the walk finds several, or when the walk does not find the folder named, the tool turns the call down: its answer names the Studies found, and it starts nothing and opens no pick. As for the panel's links, a Study deeper than the walk goes is turned down even when named, and a folder reached through a symbolic link never matches.

The read starts one process, the bridge's first read, in the checkout root, and gives Copilot the object the CLI printed, whole and uncut. It starts nothing else: not the second read, not the write, and not the script of the Claude Code hook. When the CLI turns the read down, Copilot gets the CLI's error as printed, with the exit code; when the bridge gets no usable answer, its cause.

The write starts one process, the one write of the bridge's commands, through the bridge and with the arguments the bridge builds for the panel: the folder of the Study taken, the inputs Copilot gives, a new request id that the extension makes at each call, and the Write sequence Copilot read. The Decision is thus recorded through the same CLI command from Copilot chat, from the panel and from Claude Code. The kind of decider is passed as Copilot gives it: human when the user stated the choice in chat, proxy when Copilot answered with a stated rule. With proxy the tool asks for an origin that names the rule and, without one or with an empty one, starts nothing, though the CLI does not ask for it. An origin made only of white space counts as none, so a proxy Decision with such an origin is turned down too. The kind of decider that the panel passes is the panel's, and the tools do not read it. An input the bridge's own checks turn down starts nothing, and Copilot gets what was missing.

When the user states the choice in chat, Copilot can also pass the user's own messages that state it, each whole and as typed, with the ids of what the pending decision asks and of the choice made, and a label of who gave the messages. The tool then declares how they reached it itself, chat_relayed: it has no input for that, and an agent never declares panel, the Study panel's own way. The record keeps the messages as relayed, and nothing checks them against the chat. A paraphrase goes in the origin, never among the messages. The messages come only with human: with proxy the tool turns the call down and starts nothing, at the place where a proxy Decision with no origin is turned down, after the bridge's own checks and before the walk. The bridge turns down messages that are not a list of texts that are not empty, or whose texts pass the limit of the write's table in all, and names them; the CLI keeps no limit.

Before the write, VS Code asks the user to confirm it, unless the user chose "Always Allow" for the tool. The extension gives the confirmation as plain text, not Markdown: the Study folder the Decision goes to, the wording of the decision, the choice, the kind of decider with the one the record names as having made the choice (the user with human, Copilot applying a stated rule with proxy), the origin or that there is none, and each cited id, each text as a JSON string so that a quote or a line break stays on its line. When the user's messages are given, each follows on a line of its own, as a JSON string and in order, then the label when one is given, then one sentence: they are recorded as relayed through Copilot, and they are not checked against the chat. Without them the confirmation is what it was. The Write sequence read is not shown. The confirmation then says what each button does: Continue records the Decision in the Study, where it is not withdrawn, and it can still be turned down if the Study was written to since Copilot read it; Cancel records nothing. Preparing the confirmation runs the checks of the inputs and the walk, and nothing else: it starts no process and writes nothing. When an input fails the bridge's own checks, with proxy and no origin, or when the write names no folder or one the walk does not find, the tool turns the call down there, with the same answer, and no confirmation is asked. The write goes to the folder the call names, which is the one a confirmation shows. The invocation runs the same checks and the walk again, whether or not a confirmation came first, and a folder the walk no longer finds starts nothing.

A write the CLI turns down is reported to Copilot with the CLI's error as printed, and a write that gets no usable answer with the bridge's phrase for it and its cause: the Decision may have been recorded. The tool never sends a write again, so one call starts at most one process; a new call carries a new request id. Each answer that turns a call down, the tool's or the CLI's, names the next step: the inputs to correct, the Studies to choose from, the folder to open in the workspace, or a new read of the Study before any other write.

The tests start no VS Code and no Copilot: they give the extension's vscode stub a stand-in for the language-model API, put the recorder in the place of the process start, and call each tool as Copilot would. Whether Copilot calls the tools, and the confirmation as VS Code renders it, the owner checks at the final review.

The rule for Copilot

The two tools let Copilot read a Study and record a Decision; a template of Copilot's instructions file tells it when and how. It writes for Copilot the rule for agents of ADR 0004: the five requirements that the rule of the Claude Code hook states, in its own wording and in terms of the two tools. Copilot reads the Study's state at the start of each turn, with the read; it passes the Write sequence it read on every write; it records a Decision only through the write; it records an answer chosen with a stated rule as a proxy Decision, with an origin that names the rule; and, fifth, when the user states the choice, it records the user's own messages with the Decision, whole and unchanged, with the ids of what the pending decision asks and of the choice made, and puts its own wording in the origin. The hook's rule and the template both say that an agent never declares panel. The template also says that the kind of decider is human only when the user states the choice in chat, and proxy when Copilot answers with a stated rule. Like the hook, it is a template a user copies, written for a workspace that holds a Study and not for the development of this repository.

To install it, copy the template of the table below to the destination the table gives, in the workspace opened in VS Code. Copilot chat in VS Code then adds the file to its chat requests, as long as VS Code's setting github.copilot.chat.codeGeneration.useInstructionFiles keeps its default, true. Once there, the file applies to every chat of that workspace.

This repository's own .github/ holds no such file, so the chats that develop Hypotrail do not get the rule. Copilot also attaches the workspace-root AGENTS.md to them (VS Code's setting chat.useAgentsMdFile, true as its default), and that file is written for the agents that develop this repository, not for a reviewer of a Study. L2.7, listed in chadlis/hypotrail#103, installs the template for the demonstration.

No test starts VS Code, Copilot or a model. The tests of tests/test_handbook.py check that the template names each of the five requirements with the strings that name it, beside the hook's rule, and that each tool it names is one the extension contributes; they do not check its wording, so a weak paraphrase can pass. Whether Copilot reads the file and follows it, the owner checks at the final review.
