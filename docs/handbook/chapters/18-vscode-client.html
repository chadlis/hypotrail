The VS Code client is a TypeScript extension that talks to the CLI through one module, the bridge. It reads a Study and records a Decision only through the CLI, and holds no Decision, no record and no path of its own: the Study is the only decision authority (ADR 0004). It ships the bridge, the way to find a Study, and a panel that shows a Study's pending decisions with their evidence; the chat channels are later slices of chadlis/hypotrail#103.

The extension is installed from a checkout, in three steps, in this order. No packaged file is built, and no licence is chosen: the manifest carries no licence key. The first step is the README's own install; the second builds the extension in its folder; the third, in VS Code, picks that folder.

Where it lives, and its tooling

The choice of the client's location and tooling, which ADR 0004 leaves to L2.4, is recorded here. The extension is written in TypeScript, with the compiler as the only build step: no bundler, and the compiler's output folder is generated and not tracked. Its development dependencies are the compiler and the type definitions of VS Code and of Node; it has no runtime dependency. Its tests are TypeScript under its test/ folder and run under Node's own runner (node:test), with the vscode module replaced by a stub of that folder: no test runs inside VS Code. The second job of .github/workflows/tests.yml installs the locked development dependencies and runs them on every pull request; the job pytest runs the checks that read the client's files with no Node.

The literal lists the client uses (the CLI's program and arguments, the limits, the outcomes, the walk) are kept in the extension's contract.json, which the extension imports and the handbook's tests read: the tables of this chapter are compared with it.

The bridge

The bridge (src/bridge.ts) is the only part of the client that starts a process. It starts the CLI with execFile and a list of arguments, never through a command interpreter, from the checkout root: two folders above the extension's own folder. It has no setting. A Study path is given to the CLI joined to its flag by =, as one argument, so a path that holds spaces, quotation marks or a leading dash reaches the CLI unchanged. A second read starts the CLI again: the bridge keeps nothing between two calls.

Each call gives back one of the outcomes below. Two of them are what the CLI printed; the two others are the client's own account of a call. The bridge reads the CLI's exit code and its one JSON object on stdout, never stderr: a usage text or a warning may be printed there by a call that the exit code and the object settle otherwise. A failure to start, a call stopped by a limit, and an answer the bridge cannot read are told apart by the causes of the second table, read in the order of its rows, the first that holds winning.

Writing a Decision

The client starts two commands of the CLI, one to read and one to write, and no other: the bridge's list is closed, and a test compares it with the functions that start a process, both ways. The commands that write to a Study and are not in it keep no request id of their own (the dated line of 2026-11-23 in ADR 0004).

A caller gives the bridge a Decision to record and the Write sequence it read, which it takes from the object of its last read. Each flag goes to the CLI joined to its value by =, as one argument, so a text that begins with a dash or holds a quotation mark reaches the CLI unchanged. The bridge exports a function that makes a new request id, and never makes, changes or repeats one by itself: one call starts at most one process, whatever the outcome. A repeat is the caller's explicit second call with the same id, on whatever Write sequence it gives; the CLI finds it before the stale-sequence check and gives back the recorded Decision (chapter 17).

The bridge checks the inputs of a write before it starts anything. When one fails it starts no process and gives back the client's own outcome, which lists every failing input in the order of the table below and holds no code and no message. What the CLI refuses itself, such as an empty list of cited ids or a kind of decider it does not know, reaches the CLI and comes back as the CLI printed it. When a write gets no answer, its outcome holds the words of the table below, since the write may have happened: a killed writer has still advanced the Write sequence, and the next read shows what was written. A read with no answer does not hold them.

Finding the Study

A Study is a folder that holds a study.json. The client finds the Studies of the workspace by a walk, breadth first from each workspace folder, which follows no symbolic link and looks for the file's name without reading the file. It gives the Studies as absolute paths sorted by path. With one Study the client takes it; with several it asks with one pick; with none it shows the message below, opens no dialog and remembers nothing. The owner opens the checkout, or the Study's folder, as the workspace.

The panel and its content security policy

The extension contributes one command. It finds the Studies of the workspace as above and opens one webview panel on the Study found or picked; with no Study it creates no panel. A second run while the panel is open reveals that panel and creates none; once the panel is closed, the command creates one again. The panel holds what it was opened on in memory only, for as long as it is open. Its document shows what the Study holds, as the section below says.

The panel is created in one place, with the options below, and every document the client gives to a webview is built by one function. The document holds exactly one content security policy, in a meta element, whose directives are those below, in this order, joined by a semicolon and a space, with one nonce made for each document of letters and digits. It holds exactly one script and one style element, each with that nonce, no style attribute and no inline event handler. No element or attribute of the document holds a remote address, and a text of a Study is shown as text, whatever it holds. The colours come from VS Code's own theme variables; setting custom properties from a script is left to L2.5.

What the panel shows

The panel reads its Study through the bridge when it is opened, by the command or by a link, after each write the CLI answered, and when the reviewer presses Read again; it reads at no other time: no watcher, no timer, and no read when the panel is hidden or shown again. While a read is in flight the document says so, a press of Read again starts nothing, and an opening only reveals the panel. The extension builds each document whole from the object it read, and keeps in memory, besides the target, only that object, whether a call is in flight and, from a write with no usable answer to the answer of its repeat, that call's request id and arguments.

The document shows the Study's id whole and its Write sequence, then each pending decision in the order the CLI lists them: the core's wording of the decision and of each of its choices with its consequence; the Comparison it names, with its delta, its coverage and, where the delta record carries them, the Control's and the Candidate's values; the warnings and limitations the Comparison recorded; and the two Assessments it depends on, each under its role with every Metric. When nothing is pending, a fixed sentence stands where the first decision would. The recorded Decisions follow, as the next section says, then the Declared deviations, each with whether it is withdrawn. A number that is not an integer is written with six significant digits and an integer as held; a null number is written with a fixed word. The client computes nothing of its own: what is pending, the delta and the roles are those the object read holds, and a key it does not know is ignored.

A read that the CLI refuses shows the CLI's code and message unchanged; a read with no usable answer shows its cause after a fixed text. Either way nothing of an earlier read stays: the document holds the failure and Read again. Every word the panel prints is an entry of clients/vscode/contract.json.

What the panel shows of a recorded Decision

After the pending decisions, the panel shows each recorded Decision in the order the CLI lists them: its id, what was chosen, whole as recorded, who recorded it and each id it cites; whether it still applies, as the key and the value the CLI gives, with each reason and its id; and, when its evidence changed since, what happened to it: the state of the whole, with the reason revision_changed beside it when the Decision holds that reason, then each line with its state, its count of changed Items and, for each Metric, the cited value and the latest one. Each Comparison the Decision cites is shown as a pending one is, with the two Assessments that its roles name; a Comparison record without roles shows no Assessment under a role. The client computes none of this: whether a Decision applies, its reasons and the state of its evidence are those the object read holds, no difference of two values is written, and the delta shown is the Comparison's own.

A state is written with its phrase from the table of phrases, which equals the table of states of chapter 17.

A latest value that the latest Assessment does not hold is written with the word of a null value, and the cited value stays beside it.

A link of the second form shows the Decision it names in its place among the others, with a fixed line in its part, and the document's script scrolls to it. When the Study holds no Decision of that id, the document shows the Study with one line that names the id, and the link is not refused.

Recording a Decision from the panel

The reviewer records a Decision in two actions: selecting one of the choices of a pending decision, then pressing the control that records it, which stays inert until a choice is selected. The selected choice lives only in the document: the script sends the place of the pending decision and of the choice, and the extension finds both in the object it read. One write follows, through the bridge, with the wording of the decision and of the choice as that object holds them, the Comparison alone as the cited id, no origin, a new request id and the Write sequence of that object. Opening the panel, scrolling, following a link and Read again are not actions of a Decision.

While the write is in flight the document says so and the controls are inert. When the CLI answers, the panel reads the Study once and builds one document: a notice above the first pending decision, then what the read gives. A write the CLI accepted shows its Decision among the others, with whether it applies as the object read says; a write it turned down shows the CLI's code and message unchanged in the notice, and for a Study written to since the read this is the backstop of a stale Write sequence. If that read fails, the document shows the write's answer and the read's failure, both: after an accepted write the answer is a fixed sentence with the id of the recorded Decision, and nothing of an earlier read stays.

A write that gets no usable answer may still have happened, so the panel reads nothing by itself. The extension keeps that call's request id and arguments in memory; every document then says that the write's outcome is not known, in the words of the bridge's table above, and holds Repeat beside Read again, and the controls that record are inert. Repeat sends the same call again: the same id, the same values and the same Write sequence as the first. A read keeps the id; it is dropped on the answer to a repeat and when the panel closes, so the next write has a new one. While a write is in flight or an id is held, opening the panel, by the command or a link, only reveals it. A write the bridge itself turns down starts nothing: the notice names the missing inputs after a fixed text, no id is kept, and no read follows.

The script posts one of the messages of the table below, and the extension calls a handler only through one table keyed by their names.

The Decision is recorded with the kind of decider of the table below, no origin and the one Comparison cited, and a Decision is never rewritten, so a Decision recorded from the panel keeps these values.

Links inside the panel

A link of the panel moves the view to another part of the same document and does nothing else: it posts no message to the extension, starts no process, opens no file and writes nothing. Each record the document shows, the Study, a Comparison, an Assessment, a recorded Decision and a Declared deviation, stands in a part of its own with its id; the part of an Assessment or a Comparison also gives the path of each output that record names, as the CLI prints it, and never the path of the References. An Assessment has one part in a document, at the first place that refers to it; every other place gives its id as a link to that part, and an Assessment that nothing shown refers to is not shown. Every number the panel prints is a link to the part of the record it comes from; when the Assessment of a line of a Decision's evidence is not among those the CLI lists, its numbers lead to that Decision's part. The texts the core supplies, such as wordings, messages, units and paths, are shown whole and hold no link.

Each kind of number leads to the part of the table of the parts numbers lead to.

The panel shows each of the keys of the table of what is shown beside a value with the value the CLI gives, and computes none of them.

The document is built from the keys of the table of what the panel reads and from no other, so nothing of an Attempt is shown, and no output on the checked partition that no Assessment or Comparison recorded.

Deep links

A deep link is a vscode:// URI that the extension handles, of one of the two forms below. Its authority is the manifest's publisher and name, joined by a dot, and the manifest's activation events let a link start the extension. The query is the key and the path, which is the whole rest of the query: required, absolute, within the limit below, with no NUL character, and a Study that the walk above finds in the workspace. A valid link opens the panel on its Study, and on the Decision the second form names, as the section on recorded Decisions says. Anything else (another authority, a fragment, another path, a decision id that does not match the pattern) is refused with the one notification below, and opens nothing. A link never writes.

The two forms, the publisher and the name are a public contract of the client, which a link printed outside the repository would fix.

No state of its own

The client persists nothing and remembers no path: it has no setting, keeps nothing in VS Code's stores or in the webview's state, and writes no file. It reads what a Study holds only through the bridge. The tests of tests/test_vscode_client.py list, over every tracked file of the client's sources, each name that starts a process, keeps state or writes a file, and compare the listing with their own, both ways. The listing is bounded by two conventions: only the bridge imports Node's process module, by one named import of execFile, and vscode is imported only as a namespace. An escape the sources do not use and that only a planted case shows is a stated limit of that listing.
