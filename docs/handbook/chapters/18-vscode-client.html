The VS Code client is a TypeScript extension that talks to the CLI through one module, the bridge. It reads a Study and records a Decision only through the CLI, and holds no Decision, no record and no path of its own: the Study is the only decision authority (ADR 0004). It ships the bridge and the way to find a Study; the panel's content and the chat channels are later slices of chadlis/hypotrail#103.

Install

The extension is installed from a checkout, in three steps, in this order. No packaged file is built, and no licence is chosen: the manifest carries no licence key. The first step is the README's own install; the second builds the extension in its folder; the third, in VS Code, picks that folder.

Where it lives, and its tooling

The choice of the client's location and tooling, which ADR 0004 leaves to L2.4, is recorded here. The extension is written in TypeScript, with the compiler as the only build step: no bundler, and the compiler's output folder is generated and not tracked. Its development dependencies are the compiler and the type definitions of VS Code and of Node; it has no runtime dependency. Its tests are TypeScript under its test/ folder and run under Node's own runner (node:test), with the vscode module replaced by a stub of that folder: no test runs inside VS Code. The second job of .github/workflows/tests.yml installs the locked development dependencies and runs them on every pull request; the job pytest runs the checks that read the client's files with no Node.

The literal lists the client uses (the CLI's program and arguments, the limits, the outcomes, the walk) are kept in the extension's contract.json, which the extension imports and the handbook's tests read: the tables of this chapter are compared with it.

The bridge

The bridge (src/bridge.ts) is the only part of the client that starts a process. It starts the CLI with execFile and a list of arguments, never through a command interpreter, from the checkout root: two folders above the extension's own folder. It has no setting. A Study path is given to the CLI joined to its flag by =, as one argument, so a path that holds spaces, quotation marks or a leading dash reaches the CLI unchanged. A second read starts the CLI again: the bridge keeps nothing between two calls.

Each call gives back one of the outcomes below. Two of them are what the CLI printed; the two others are the client's own account of a call. The bridge reads the CLI's exit code and its one JSON object on stdout, never stderr: a usage text or a warning may be printed there by a call that the exit code and the object settle otherwise. A failure to start, a call stopped by a limit, and an answer the bridge cannot read are told apart by the causes of the second table, read in the order of its rows, the first that holds winning.

Writing a Decision

The client starts two commands of the CLI, one to read and one to write, and no other: the bridge's list is closed, and a test compares it with the functions that start a process, both ways. The commands that write to a Study and are not in it keep no request id of their own (the dated line of 2026-11-23 in ADR 0004).

A caller gives the bridge a Decision to record and the Write sequence it read, which it takes from the object of its last read. Each flag goes to the CLI joined to its value by =, as one argument, so a text that begins with a dash or holds a quotation mark reaches the CLI unchanged. The bridge exports a function that makes a new request id, and never makes, changes or repeats one by itself: one call starts at most one process, whatever the outcome. A repeat is the caller's explicit second call with the same id, on whatever Write sequence it gives; the CLI finds it before the stale-sequence check and gives back the recorded Decision (chapter 17).

The bridge checks the inputs of a write before it starts anything. When one fails it starts no process and gives back the client's own outcome, which lists every failing input in the order of the table below and holds no code and no message. What the CLI refuses itself, such as an empty list of cited ids or a kind of decider it does not know, reaches the CLI and comes back as the CLI printed it. When a write gets no answer, its outcome holds the words of the table below, since the write may have happened: a killed writer has still advanced the Write sequence, and the next read shows what was written. A read with no answer does not hold them.

Finding the Study

A Study is a folder that holds a study.json. The client finds the Studies of the workspace by a walk, breadth first from each workspace folder, which follows no symbolic link and looks for the file's name without reading the file. It gives the Studies as absolute paths sorted by path. With one Study the client takes it; with several it asks with one pick; with none it shows the message below, opens no dialog and remembers nothing. The owner opens the checkout, or the Study's folder, as the workspace.

The panel and its content security policy

The extension contributes one command. It finds the Studies of the workspace as above and opens one webview panel on the Study found or picked; with no Study it creates no panel. A second run while the panel is open reveals that panel and creates none; once the panel is closed, the command creates one again. The panel holds what it was opened on in memory only, for as long as it is open. Its document holds nothing of a Study yet: the panel's content is L2.5's.

The panel is created in one place, with the options below, and every document the client gives to a webview is built by one function. The document holds exactly one content security policy, in a meta element, whose directives are those below, in this order, joined by a semicolon and a space, with one nonce made for each document of letters and digits. It holds exactly one script and one style element, each with that nonce, no style attribute, no inline event handler and no remote address. The colours come from VS Code's own theme variables; setting custom properties from a script is left to L2.5.

Deep links

A deep link is a vscode:// URI that the extension handles, of one of the two forms below. Its authority is the manifest's publisher and name, joined by a dot, and the manifest's activation events let a link start the extension. The query is the key and the path, which is the whole rest of the query: required, absolute, within the limit below, with no NUL character, and a Study that the walk above finds in the workspace. A valid link opens the panel on its Study, and on the Decision the second form names; the panel's content renders it in L2.5. Anything else (another authority, a fragment, another path, a decision id that does not match the pattern) is refused with the one notification below, and opens nothing. A link never writes.

The two forms, the publisher and the name are a public contract of the client, which a link printed outside the repository would fix.

No state of its own

The client persists nothing and remembers no path: it has no setting, keeps nothing in VS Code's stores or in the webview's state, and writes no file. It reads what a Study holds only through the bridge. The tests of tests/test_vscode_client.py list, over every tracked file of the client's sources, each name that starts a process, keeps state or writes a file, and compare the listing with their own, both ways. The listing is bounded by two conventions: only the bridge imports Node's process module, by one named import of execFile, and vscode is imported only as a namespace. An escape the sources do not use and that only a planted case shows is a stated limit of that listing.
