The agentic Track asks a model Chinook questions and scores the answer it keeps. This chapter describes the part that exists: the Workload declaration and the task built from it, and the chinook_contract_v1 Scorer, which turns one Episode's raw final answer, its Reference and its projected trace into four Criteria, exact_table, format_valid, evidence_link_valid and contract_success, and keeps failures of the instrument apart from failures of the evaluated system. The spike chapter covers the runs and the log projection.

Where the Scorer lives

The Scorer is src/hypotrail/core/chinook_contract.py. It needs the standard library and jsonschema only; the core never imports Inspect (ADR 0001). Rescoring a kept log (agentic/rescore.py) projects the log, then applies this Scorer to each Episode. It calls neither the model nor a tool and never opens the Chinook file: the frozen References are enough. The output of every Episode records the Scorer's name, chinook_contract_v1, and its version, and two rescorings of one log give the same verdicts.

The Scorer takes the raw final answer unchanged and keeps it unchanged in its output, whether or not it respects the schema.

The Workload declaration

The Workload is declarative and holds no Python (ADR 0002). examples/chinook/workload.json is checked as a whole against one JSON Schema, src/hypotrail/agentic/workload.schema.json, by jsonschema. declaration.load_workload(directory) reads and checks it and returns a Workload; it imports neither Inspect nor any Reference, so a refusal comes before Inspect runs. The schema requires every key except scenarios, answer_schema and the Partitions under cases (cases must hold at least one); the table below says which entry point refuses each absent key (ADR 0002, clarification of 2026-11-04). Every object is closed, except configurations, whose keys are the Workload's own Configuration names; the Partition names under cases are closed to the Track's two roles.

Each refusal is an InvalidInputError (exit code 2 once a command line exists) with a code, a message, a stage and details. The stage is declaration, except for the scenarios file, whose refusals have the stage fixture. The details depend on the refusal. ANSWER_SCHEMA_NOT_DECLARED (stage declaration) and SCENARIOS_NOT_DECLARED (stage fixture) give only the path, answer_schema or scenarios. A schema refusal (DECLARATION_*, SCENARIOS_*) gives the key (null when the fault is the whole document) and the path, and DECLARATION_WRONG_TYPE and SCENARIOS_WRONG_TYPE also the expected type. A Configuration refusal gives the configuration and the path. PARTITIONS_NOT_DISJOINT gives the path, the case_ids and the partitions. PARTITION_NOT_DECLARED gives the partition and the path. An absent or non-JSON workload.json, answer schema or scenarios file gives the key, an empty path and the file. A Cases file refusal gives the file, plus the line when one line is at fault (not for an unreadable file, nor for CASE_ID_NOT_UNIQUE, which gives the case_id instead). The codes CONFIGURATION_NOT_DECLARED, CONFIGURATION_CYCLE, PARTITION_NOT_DECLARED and PARTITIONS_NOT_DISJOINT relate values to each other or to the declaration, which JSON Schema cannot express, so they stay in Track code (ADR 0002, clarification of 2026-11-04). CASE_ID_NOT_UNIQUE is raised by the Cases reader in Track code.

The two Configurations

  • plain carries the system text in full. It tells the model to answer with the available tools and not to guess, to answer in the requested schema table-answer/1, and to distinguish an answer, an ambiguity and unavailable information. It states the common format rules: one JSON object and nothing else, no Markdown fence, no extra prose, the six fields, the three statuses and their reason_codes (criterion_undefined for needs_clarification, field_not_available for not_answerable), with columns and rows empty and unit null for the last two.
  • verify is plain (extends) followed by a declared added_instruction and nothing else: check the scope, the joins, the units and the result before concluding. Its resolved text is exactly plain's text plus the instruction. No Reference value is in either text.

The task

runner.build_task(workload, configuration, cases=None, partition="dev") returns the Inspect task. runner.run_episodes(cases, workload=..., configuration=..., model=..., repeats=..., log_dir=...) runs it. The task replaces the spike's single prompt and its chinook_spike task.

  • Each Case is one sample. Its input is two messages: the Configuration's system text, and a user message rendered from the question, the requested columns and the unit only (prompt.render_user_message). A Case with no unit goes through the same rendering (Unit: none), so the system text is identical for every Case of a Configuration. The Case identifier, the group, the family, the Reference rows, the oracle SQL, the expected status and the tolerance never reach the model.
  • The model gets exactly two tools, describe_schema and query_readonly, both bound to the database path of the declaration. describe_schema takes no argument and returns the eleven tables with their columns, types and foreign-key relations, read from SQLite itself (PRAGMA); it holds no row, Reference or oracle SQL.
  • Both Configurations run with the same tools, limits and generation settings; only the system text differs.
  • The log header keeps the Configuration name and its exact system text (eval.metadata), and the live run record (run.json) repeats them.
  • The References are not an input of the builder: a task built from the declaration runs when the References file is absent.
Open pointThe builder can build a task on any declared group of Cases, public_check included. The builder does not refuse it; the counting and rescoring entry points do (see the scripted_fixture section), because they take no Study. Inside a Study, assess accepts public_check Episodes and records the Exposure (chapter 12).

The read-only SQL tool

The evaluated model reaches Chinook through two tools, describe_schema (see above) and query_readonly(sql) (agentic/sql_tool.py; the connection details are in the spike chapter). No SQL text is inspected: three native SQLite mechanisms decide what runs. The limit on attached databases is 0, execute takes a single statement, and an authorizer holds the allow-list.

  • Allowed: SELECT, reads of the tables the Chinook file itself declares, and the functions of the table below. AG-03 did not list like and glob; the owner added them by an explicit revision of AG-03 on 2026-11-07 (#51). SQLite reports the operators LIKE (also NOT LIKE and LIKE … ESCAPE) and GLOB to the authorizer under these two names; both only compare text, and the per-query caps still bound any pattern. LIKE keeps SQLite's default matching (case-insensitive for ASCII; GLOB is case-sensitive) because PRAGMA case_sensitive_like stays refused.
  • Tables read from the file: the table names are never written in the code, so a table the file does not declare is not readable, and the system tables such as sqlite_master stay refused.
  • Denied: writes and DDL, ATTACH, DETACH, PRAGMA, transactions, VACUUM (also INTO), extension loading, recursive queries and any other function. A statement that starts with WITH or SELECT but needs a denied action is refused.

A refused or failed statement sets error to a code, a type and a message; the code is what to rely on.

Four caps per query

Every call is also bounded by four caps (QueryCaps in agentic/sql_tool.py, AG-04). A cap that is reached is never turned into a complete result: it shows as truncated: true, or as an error that names the limit and comes with no rows.

CapDefaultWhen reached
Watched time1 s of wall clockError code TIME_LIMIT, no rows.
Instruction ceiling100,000,000 SQLite VM instructionsError code INSTRUCTION_LIMIT, no rows.
Rows200 returned, 201 fetchedThe first 200 rows in the query's order, truncated: true.
Serialized size64 KiB (the JSON of columns and rows)The longest prefix of rows that fits, truncated: true, and a row_count that matches the rows returned.

SQLite's progress handler, called every 1000 instructions, watches the first two caps. The fetch stops at 201 rows through fetchmany, so the extra row only tells that more exist. AG-04 gives no number for the instruction ceiling, so 100,000,000 is a declared default: the 1 s time stays the primary cap, and the ceiling is a machine-independent backstop set near it (about 0.7 s at the roughly 138 million instructions per second measured on the development machine). It is about 3,000 times the heaviest of the 16 oracle statements (about 32,000), so it does not refuse a read the time cap would allow on this machine. It changes only by a new value in the record. The two time mechanisms are witnessed apart: each test puts the other cap out of reach.

The query runs in a worker thread (anyio.to_thread), not on Inspect's event loop. A slow query therefore does not stop the Episode time limit from taking control: when that limit cancels the call, a stop flag read by the progress handler interrupts the statement. The four caps are recorded in the task metadata and read back with the Episode limits, under query_caps (read_back in agentic/limits.py).

Wrapped answers

The prompt asks for a single JSON object and nothing else, and a model sometimes puts a sentence before it or a Markdown fence around it. By owner decision of 2026-11-07 (#58, option E) the Scorer keeps the format as its own Criterion and stops letting the wrapping hide the content. The answer is scanned left to right; at each { the standard JSON decoder tries to read one value (NaN and the infinities are refused, and so is a number that decodes to a non-finite float), a read that gives an object is a candidate and the scan resumes after it, and a failed read (a stray brace in prose, a truncated object, a non-finite number) skips only its own {, so an object that decodes further on, even inside the text of a failed read, is still a candidate. find_embedded_object in core/answer_scoring.py returns the decoded candidate with its text only when there is exactly one, wherever it sits; the table below says what each outcome means. parse_answer is unchanged and still decides format_valid. The raw answer is never altered, and the record says what was scored in its top-level field answer_read_from. The Scorer's version was 2 when that decision was taken (#58), since the same raw answer then scored differently; its name stays chinook_contract_v1.

A number that decodes to a non-finite float, such as 1e999 or -1e999, is refused like NaN: the JSON value holding it is unreadable, so a bare answer holding one reads nothing (invalid_response_format), and in a wrapped answer it is a failed read that skips only its own {. Numbers that stay finite are read as they were (1e308, 5e-324, and an integer of any length up to the limit below, even one too large for a double), and the tokens NaN, Infinity and -Infinity stay refused. An integer of more than 4,300 digits, which Python refuses to read, leaves the answer unreadable in the same way, unless an object can still be read inside it. Since #61 the Scorer's version is 3, because the verdicts of those answers changed; the answer schema table-answer/1 is unchanged, as the rule is the Scorer's.

The evidence link and contract success

A successful tool call is one with no Inspect-level tool error and no structured error in its result body (the shape {code, type, message} that the read-only SQL tool returns, for example when its authorizer refuses a statement). The Scorer reads the Episode's projected steps, plain records, and never an Inspect object; the projection itself still reads the log only through Inspect's public log API. The link is a check that a cited ID points to a real, earlier, successful call. It is not a proof that every claim in the answer follows from the trace.

An exact table with no valid evidence is exact but not a success of the tool-based path: exact_table true, evidence_link_valid false, contract success false. Contract success is scored false as soon as one dependency is false, whatever the state of the others. Only when none is false and one is unscored or errored does it take that state and Reason: a well-formed answer with valid evidence and a missing Reference gives unscored with reference_missing. Without a trace, evidence_link_valid is unscored (trace_missing), and so is the contract success of an answered answer; for an answer whose evidence cannot be read (nothing is read from it, or the object read is not valid against the schema), evidence_link_valid is scored false with invalid_response_format, trace or not.

The tools are the real local tools on the Chinook file; the task (runner.run_episodes), the projection and the Scorer are the code a live run uses. Only the model differs. It needs no network and no provider key.

The banner as a report renders it is #10's.

Choices and limits worth knowing

Malformed means not exact, unless it only wears a wrapper

What the other two Criteria read is set out in the table of wrapped answers; a failure to read is the system's failure, not the instrument's.

Failed and missing Episodes

Every expected Episode has a state for every Criterion, with a Reason for each non-score (rescore.rescore_episodes). An Episode failed by an execution error has every Criterion unscored with execution_failed; an Episode absent from the log is missing, every Criterion unscored with observation_missing. Neither is scored false, and neither has an empty list. An Episode stopped by one of our limits is failed too (see the scripted_fixture section), with Criteria that depend on who stopped it.

The schema is an input

The Scorer is given the Workload's table-answer/1 schema; it does not read it from disk, so rescoring opens no Workload file.

Not built

An Inspect @scorer adapter (ADR 0001's parity test applies if one is built), and the report. An Inspect log is imported into a Study since #69: see chapter 09. Answers imported as JSONL without a trace, the Assessment contract with its counters and shares, and the closed Scorer registry that holds this Scorer exist since #68: see chapter 08.

The live command

spike live runs one declared Configuration of the Chinook task against a real Anthropic model. It is opt-in, paid and bounded by the limits of the table above, among them the output-token budget metered by Inspect's TokenLimit(type="output"), and it is never part of the tests or CI. It writes only under --out and records nothing in a Study; run agent --mode llm_live (chapter 13) is the command that records a native Attempt of the live Mode in a Study, with its own bounds (a Partition's Cases times three Repeats at most), while spike live keeps its two Episodes on dev. Each output directory must be empty. With no --case, the spike live execution takes the two dev join Cases, D03 and D05, one Repeat each, so two Episodes; the record names them. The command refuses, before the key is read and before Inspect is imported, a Configuration the Workload does not declare, a model that is not an explicit anthropic/<model> (there is no default), a Case outside dev, and more than two Episodes. With no key it exits 5 and sends nothing. The output is scanned for the key before the execution reports.

Reasoning is disabled, identically for plain and verify, and the output cap per model call is kept (owner decision 1 on #8). A reasoning level would draw its thinking from the same per-call cap as the answer, so an answer could be cut by our own setting; disabled leaves the whole cap to the answer. A test captures the request bodies of both Configurations at the fake endpoint and checks that each carries the same thinking field and the same max_tokens, the cap of the table above. Which thinking value a model gets is Inspect's to decide: {"type": "disabled"}, or {"type": "between_tools"} for Sonnet 5.5, which rejects disabled. Inspect's source describes between_tools as no up-front thinking and the model's lowest setting; it does not say whether thinking may still happen between tool calls, so that is not claimed here. Before any provider call, the execution asks Inspect's own request building (completion_config, no network) what the request would carry; if it would not state the reasoning setting (for example Opus 5.5 cannot disable thinking, and models before 4.7 get no thinking field), the execution is refused with REASONING_NOT_EXPLICIT and nothing is sent. The record keeps the field as it was sent, with this note.

The projection records why each model call stopped. A live Episode whose final call stopped on the output cap is failed with the Reason output_cap, never produced; one stopped by the turn, token or time limit carries turn_limit, token_limit or time_limit. How they are scored is described above; live Episodes are still not scored against References here.

run.json holds: the Mode llm_live and the provider; the requested and served model; the Configuration name and its exact system text; the reasoning setting (requested and as sent) and the output cap (requested and as sent); the engine version, Python and hardware (where each field comes from); the requested limits (requested_limits) and the effective limits (effective_limits), with the token budget under the key of the table above and token_budget_metering beside it. The effective limits are read back from the log and include the per-query caps. request_source says where the requested limits come from (see its table); a request read from a kept log goes through the same header fields as the effective limits, so they agree wherever the log records the limit, with tool_calls null because no log holds it, and output_cap's requested value follows the same source; the statements that Inspect has no tool-call limit and how many provider calls the turn limit allows; the Cases of the execution; the SHA-256 of the Chinook file before and after the execution; and, per Episode, the number of model calls, the latency, the cost when the log gives one, and five token figures under Inspect's own field names: input_tokens, output_tokens, input_tokens_cache_write, input_tokens_cache_read and total_tokens; token_budget (the budget Inspect recorded on the sample, under the same key and with the same token_budget_metering as above, and metered_usage, so a budget stop shows what it counted next to the Episode's output_tokens); and uses_tool_result with uses_tool_result_reason. The token figures are Inspect's model_usage for the sample, read through the public log API and summed over the models of the sample as ModelUsage adds them; the sample's model_usage is also kept per model, keyed by model name, as the log gives it. They include the provider's cache reads and writes: input_tokens alone is only the input charged at full rate, and total_tokens counts the cached input tokens too, so it is the figure an all-token limit is checked against. The record copies what the log gives. A field Inspect leaves None (the cache fields, when a provider reports none) is null, and an Episode absent from the log has every figure null; but Inspect itself writes 0 for input_tokens, output_tokens and total_tokens when a provider omits them, so a 0 there may not be the provider's count. These are token counts, not a cost. uses_tool_result is true when every row of a readable final answer is a row the tool returned, and false when a row is not; its Reason is then null. A readable answer is exactly one JSON object, as parse_answer decides. In every other case the value is null, never false, and uses_tool_result_reason names the cause. The cause is one of:

ReasonWhen
no_final_answerThe Episode has no final answer.
no_tool_resultThere is a final answer but no tool result to compare it with.
answer_unreadableThe final answer is not exactly one JSON object, for example prose before the JSON object, a JSON value that is not an object, or an object holding a number that decodes to a non-finite float such as 1e999.
