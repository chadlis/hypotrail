compare on two Assessments of a Chinook Study works as it does on the bike (chapter 07), with what an agent adds: the Items are Episodes, aligned by Case and Repeat; the two sides must share their planned Repeats, tools, model and budgets, except for the factor the request declares as intentional; each side keeps its Case × Repeat matrix; and, when every Episode is scored on both sides, each Criterion is aggregated per Case first and every Case weighs the same. The main delta is that of the primary Criterion, contract_success. With one Episode missing, the Comparison shows the coverage and gives no main delta. A Chinook side is an Import (chapter 08, chapter 09) or a native llm_live Attempt recorded by run agent (chapter 13). A Comparison with an Import on either side is descriptive; the strict path is two native llm_live Attempts, witnessed offline by two Attempts recorded with Inspect's mock model in place of the provider, which only a test can do. An Attempt of the scripted_fixture Mode is never assessed, so it is never compared.

The command

The command is the one of chapter 07, with one more flag. The work is in src/hypotrail/core/agent_comparison.py, a core module (ADR 0001): it imports no Track, no scikit-learn, no NumPy and no Inspect, and hypotrail.core.comparison loads it for an Assessment of an agentic Observation set. --factor names the factor that is intentionally different between the two sides; it defaults to configuration, the factor of plain against verify (the verify Configuration adds one explicit instruction to plain and changes nothing else). On a Study of another Track it is refused with UNSUPPORTED_CAPABILITY (exit 2). The command holds the Study's writer lock for the whole command and follows the --json rules of chapter 04.

# the Chinook Study of chapter 08: two imports, each assessed with chinook_contract_v1
uv run python -m hypotrail compare --study runs/chinook --control ASSESSMENT_ID_OF_PLAIN --candidate ASSESSMENT_ID_OF_VERIFY --json
# the two sides differ by their model on purpose
uv run python -m hypotrail compare --study runs/chinook --control ASSESSMENT_ID_A --candidate ASSESSMENT_ID_B --factor model

What is checked, in order

The checks run in this order, and the first one that fails refuses the Comparison with its own code and exit 3; nothing is written. A Partition other than dev and public_check is refused right after the population (COMPARISON_PARTITION_NOT_DEV, exit 2), as in chapter 07; a public_check Comparison is journaled once every check has passed (chapter 12). The population of an agent Comparison is the Partition and the Cases; the Repeats have their own check, so that a difference in Repeats can be declared. The References, Scorer and unit checks are those of chapter 07, with the same codes. The refusal's details carry the check, its Reason, the values of both sides and the checks evaluated so far.

For tools, model and budgets, each side establishes what it can: a native Attempt's manifest records them; an Import declares its model and tools in the lines of its file, and its budgets in the header of an Inspect log, or leaves them unknown (chapter 06). A check compares what both sides establish. When a side does not establish it, the check is recorded as failed with the Reason not_established, nothing is refused, and the Comparison is descriptive. An Import is never strict.

Strict against descriptive

A Comparison is compatible (strict) only when every check passed and both sides were produced by Hypotrail. It is descriptive_only when a side is an Import, whatever the origin of the fields the Import declares, when a native side does not record a factor, or when a native side establishes no Case content (its digests leave out a Case of the population, or it records none and the two sides do not record the same Cases file). The first case carries the warning COMPARISON_DESCRIPTIVE_IMPORT of chapter 07; the second, COMPARISON_FACTOR_NOT_ESTABLISHED, naming the factors; the third, COMPARISON_CASES_NOT_ESTABLISHED, since cases is not a factor. All are in warnings and limitations, and the command prints them on stderr. As in chapter 07, the record compares the code environments of the two Attempts: when they differ it says so and never calls the executions identical, and when they are the same it still does not claim they were identical.

Two native Attempts of which one finished before the other started, by the started_at and finished_at of their manifests and nothing else, ran in separate time blocks: run agent runs one Configuration per invocation (chapter 13), so the two sides were not alternated, and the delta may include a time effect. Such a Comparison holds COMPARISON_ORDER_NOT_ALTERNATED in warnings and limitations, whatever the declared factor, and its message names the side that ran first. The warning leaves the status as the checks and Imports compute it: a pair whose checks all pass stays compatible. compare prints the warning on stderr and names its code beside the status on its stdout line, and the report names it beside the status in the row Comparability (chapter 14). The Limits below say which pairs get no derived warning.

Episodes, the matrix and the Case weight

Episodes are aligned by (case_id, repeat), never by position. The Comparison takes the union of the two sides' Episodes and drops none: an Episode on one side only (possible only when repeats is declared) and an Episode not scored for the primary Criterion on a side both show in coverage, as counts and as rates of the expected Episodes. matrix.json keeps each side's Cases × Repeats matrix: for each Case and Repeat, the execution status and, for each of the four Criteria, the state, the score and the Reason.

With full coverage, every Episode scored for the primary Criterion on both sides, the Criterion is aggregated per Case first: a Case's share is the share of its Repeats scored true. The value of a side is the mean of the shares of its Cases, so every Case has the same weight and the three Repeats of a Case are never counted as three Cases (they are not independent). The delta is the value of the Candidate minus the value of the Control; a positive value means the Candidate is better, since the Criterion is higher-is-better. paired_deltas.csv holds one row per Case. The main delta, delta, is that of the primary Criterion (contract_success, declared by the Workload and frozen by the Study); secondary_deltas holds the other three Criteria, each with its own coverage rule.

Without full coverage, delta.value is null and delta.reason is coverage_incomplete; paired_deltas_ref is null, so no per-Case table hides the gap. No binomial or other interval is computed over Episodes, and the limitations say so. A correct answer without a trace leaves contract_success unscored (trace_missing, chapter 05), so an import without traces gives no main delta unless every answer is wrong or needs no tool call.

The interval over Cases

With full coverage, the Comparison's interval resamples the Cases: the per-Case delta_share values of paired_deltas.csv are drawn with replacement, as many as there are, 2,000 times, and the bounds are the 2.5% and 97.5% quantiles of the means, every Case weighing the same. The Repeats of a Case are not resampled, and no interval is computed over Episodes. The Chinook Workload declares {"unit": "case", "seed": 240}; the record holds unit case, units (the number of Cases), the seed and variant and block_length null. With an interval, the first limitation names the unit and says what it does not cover: no binomial interval over Episodes and no significance claim. A withheld delta (coverage_incomplete) gets null bounds with delta_withheld; a Study whose current revision declares no resampling gets resampling_not_declared, and its first limitation stays the earlier sentence. The line of compare gives the bounds, the level and "over N Cases" after the delta.

An oracle test compares the interval with Inspect's clustered bootstrap, ci(method="bootstrap", cluster=...), on synthetic sets with equal Repeats per Case: the two agree within the resampling error, and cannot be equal, since they draw from two generators. The interval over groups

A Workload whose Cases are paraphrases of one question may declare {"unit": "group", "seed": N}; chinook_prose declares {"unit": "group", "seed": 291}. Every Case then declares its group, or init and init --new-revision refuse it with CASE_GROUP_MISSING before anything is written, and the Study's memberships.csv holds the group of each Case in a third column, group, which enters the Protocol with the file. A Workload whose Cases declare no group keeps its two columns and its bytes.

The interval then draws whole groups: as many groups as there are, with replacement, taken in the sorted order of their ids, and each resample's mean is the mean of the per-Case delta_share values of the drawn groups, so every Case weighs the same and a group weighs its number of Cases. compare reads the groups from the memberships of the Study's current revision. The record holds unit group, units the number of groups and cases the number of Cases; cases is null under the other units. Fewer than two groups give too_few_units. The level, the count of resamples and the method are those of the Case interval. With bounds, the first limitation says that the Cases of a group are drawn together and the Repeats are not resampled. The line of compare and the report give "over N groups". A follow-up Case whose history quotes a Case of another group leaves a dependence between the two groups, which the interval does not take into account; chinook_prose states it as a limitation.

An oracle test compares the group interval with Inspect's ci(method="bootstrap", cluster="group") at 10 groups of 3 Cases with one and three Repeats and at 40 groups of 3, within the tolerance of the Case oracle. At those sets the Case interval would agree too; on sets whose group effect dominates the noise of an Episode, a second oracle test finds the group interval within the tolerance of Inspect's and the Case interval on the same deltas narrower by more than twice that tolerance. The simulation gives each group a Control rate uniform on [0.35, 0.45] and an effect uniform on [-0.35, 0.55] that its Cases share, so the true delta is 0.1 and the Cases of a group are not independent; each data set gets both the group interval and the Case interval, with the same resampling seed. The rates, and what is only described

rates repeats, for each side, the two named rates of its Assessment with the unknowns beside them: quality_among_scored (correct among scored) and confirmed_share_of_expected (correct among expected), the Episodes unscored or errored and their Reasons, and the failed and missing Episodes. A rate whose denominator is zero is null with a Reason, never 0. descriptive reports, for each side, latency, the numbers of model and tool calls, tokens and cost. These are descriptive only: no Criterion and no delta rests on them, and no cost is compared. Calls are counted from the kept traces and are null unless every Episode that ran has one; latency, tokens and cost are the sums of the usage each Episode's normalized entry keeps, from an Inspect log (chapter 09, which states no cost) or from a JSONL line (chapter 08), and each is null unless every Episode that ran has it, so a JSONL import without usage, a partial log, or a line whose model's cost_usd is null gives null. None of them is ever filled with 0.

Declared settings

An Import declares its settings as a flat map on each line of a JSONL file, and its Observation set records the map only when every line holds the same one; otherwise, and for an Inspect log import, it records them unknown (chapter 08). A native Attempt declares none. When at least one side declares settings, the Comparison holds settings: control and candidate, each declared or unknown, and keys, one entry per key either side declares, sorted, with the value of each side as declared (null where that side declares none) and its state. The key is absent when neither side declares settings, as on every Bike Comparison and every Comparison written before it. No check, status, warning or refusal reads settings: two Comparisons whose Imports differ only by their settings have the same comparability, warnings and limitations. The line of compare ends with "settings: N equal, M different, K unknown" when the key is present, and the report shows one row per key (chapter 14).

StateWhen
equalBoth sides declare the key with the same canonical JSON bytes; 1 and true are not the same bytes.
differentBoth sides declare the key, with values whose canonical JSON bytes differ.
unknownOne side declares the key and the other does not: its map leaves the key out, or its settings are unknown.

Limits

Native Attempts

The keys a native Attempt records for this chapter (configuration, model, tools, limits, repeats) are written by run agent. The strict path, the repeats and model refusals are witnessed on two recorded llm_live Attempts; the tools and budgets refusals, which no flag of run agent can produce, are witnessed on native manifests built by hand. The model compared is the requested one; the model the log reports is kept beside it as served_model.

Exposure

A Comparison of public_check Episodes is an Exposure and has its journal entry (chapter 12).

Primary Criterion

The primary Criterion is the one of the Control's Assessment. Two Assessments scored under two primary Criteria are not told apart by a check; the Protocol of a Study freezes one.

Latency and cost

Latency and tokens come from an Inspect log, imported or recorded by run agent, or from a JSONL line's usage, which also gives cost; each is null for an Episode that gives none. None of them is compared.

Compatible with a warning

A compatible Comparison can hold a warning, as two native Attempts run one after the other hold COMPARISON_ORDER_NOT_ALTERNATED and a side that a Declared deviation covers holds COMPARISON_DEVIATION_DECLARED (chapter 17), so compatible does not mean that warnings is empty (the warning codes are in chapter 07).

Overlapping Attempts

Two native Attempts whose intervals overlap, neither finished before the other started, get no derived COMPARISON_ORDER_NOT_ALTERNATED: the warning is derived only for intervals that are disjoint.

An Import side

A Comparison with an Import side gets no COMPARISON_ORDER_NOT_ALTERNATED: an Import's manifest records its import time, not when its outputs were produced, so its order is not established, and the Comparison is already descriptive.
