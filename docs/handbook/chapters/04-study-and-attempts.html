A Study is a folder that holds one Protocol and the Attempts run under it. init creates the Study of the bike Workload; run ml runs one Configuration on one Partition and records it as an Attempt: a manifest, an Observation set and the predictions, every artifact referenced by its digest and published atomically before the terminal manifest. A repeated --request-id returns the recorded Attempt or is refused. A Study admits one writer at a time (init, run ml, import ml, recover, assess and compare take its lock); status shows its local state and recover records an Attempt left behind by a dead writer as interrupted. This chapter describes what exists; importing outputs produced elsewhere is chapter 06; scoring an Attempt is chapter 05; comparing two Assessments is chapter 07.

Commands

The four commands are in src/hypotrail/cli.py. With --json, stdout holds exactly one JSON object ({"ok": true, ...} or {"ok": false, "error": {"code", "message", "stage", "details"}}) and the human diagnostic goes to stderr; no error carries a secret (an unexpected exception and an OS error are each reported by their type only, and a failed Attempt's Reason names them the same way). Without --json, stdout holds one line.

  • init verifies the Workload's data and creates a StudySpec (study.json) and Study artifacts. For temporal regression it verifies the data lock. For an agent Study it keeps the database, Case memberships, References and answer schema. The primary metric is the Workload's Criterion (chapter 08). For ranking it verifies a private build and binds the Study to a single Partition. A Study folder with an existing study.json is refused. init --study DIR --new-revision adds a revision to an ordinary Study when its Protocol changes, such as after a correction to References or Case text (chapter 10). It takes no --workload.
  • run ml runs one declared Configuration (seasonal_7, ridge_v1) on one declared Partition and records one Attempt. --request-id is required. Its output is {"ok": true, "replayed": false, "attempt": MANIFEST, "observation_set_id": ID}; replayed is true when the request was already recorded and nothing was computed. observation_set_id is the ID of the Observation set the Attempt recorded, the one assess --observations takes, and is null when its manifest names none (a failed or interrupted Attempt returned for a request sent again); without --json, the line ends with ; Observation set ID or ; no Observation set. It needs the ml extra only to run ridge_v1.
  • status only reads. It lists every Attempt of the Study with its technical_status and the artifacts found in its folder, the partial ones of an Attempt that never reached its terminal manifest included, and the Study's Write sequence (see The Write sequence below). It takes no lock and writes nothing.
  • recover is the explicit command that writes. It records as interrupted, with finished_at and a Reason, an Attempt that is running while no writer is alive, and keeps its artifacts. It resubmits nothing.

The Workload stays where it is declared (examples/<name> of a checkout, or the folder given by --examples-dir: see below): a Configuration can change after the Study exists, and an Attempt records the Configuration it ran. The Study freezes the Protocol, not the Configurations.

A ranking Study defaults to dev. Only the declared evaluator can create a separate ranking Study for held_out, outside a Git worktree. It calls hypotrail --evaluator init --partition held_out and verifies the build while holding the Study lock. Hypotrail requires GITHUB_ACTIONS=true and a GITHUB_WORKFLOW_REF matching GITHUB_REPOSITORY and .github/workflows/evaluator.yml@refs/heads/main. The kit and GitHub control admission to the protected job. Ordinary CLI and client entry points refuse the protected Study before reading its records.

The records

Every record is canonical JSON (core/canonical.py): UTF-8, keys sorted, separators , and :, no whitespace, strict types. NaN and Infinity are refused, never written (NON_CANONICAL_VALUE), and an integer and a float of the same value stay distinct. A configuration declared with its keys in another order has the same digest; the source files are hashed on their bytes, separately. Each record is validated against the contract schema (src/hypotrail/core/contracts.schema.json, by jsonschema) before it is written and after it is read; a fault is CONTRACT_VIOLATION.

The schema is derived from the kit's contracts.schema.json and owned here; the kit's copy is not changed. It keeps every field of the kit's envelopes, names the Criterion states scored / unscored / errored and their counters unscored / errored, and defines the fields and the two further record kinds (freeze, exposure) that the next tickets of the slice name. Only the records below are written today.

Attempt manifest. attempt_id is a UUID, never a hash of the inputs: two requests of identical inputs under two request_ids are two Attempts with the same effective_config_digest. effective_config holds the Command, the Workload, the Mode, the Partition, the Configuration (its id and its declared content), the Protocol (id and digest), the input digests (dataset, population, References), the effective parameters (null while running), and the applicable bounds. code_environment holds the Python version, the dependency lock (uv.lock, by digest) and the code revision: the commit, whether the code is dirty and, when it is, a fingerprint of the local code. "The code" is src/, pyproject.toml and uv.lock. No provider secret is written: the process environment is never read into a record. A manifest that is running has no finished_at; a completed one has it, the counts of its Items by execution status (item_counts) and its output_refs.

Observation set. One per Attempt. Its Items are exactly the Items of the Partition (read from the Study's memberships), each produced, failed or missing. population_ref is the memberships artifact, raw_refs the library's own files, normalized_ref observations.csv.

Artifacts and integrity

An ArtifactRef is {path, sha256, size_bytes, media_type, role}: the path is relative to the Study and the digest is of the bytes. A path that leaves the Study (.., an absolute path) or goes through a symlink pointing outside it is refused (ARTIFACT_PATH_OUTSIDE_STUDY), for writing and for reading; a symlink that stays inside is not a traversal.

Publication is atomic (core/artifacts.py): the bytes go to a temporary file in the destination's folder, inside the Study, are flushed and fsynced, then renamed onto the final path; nothing appears under the final path before the rename. A published artifact is immutable: other bytes under the same path are refused (ARTIFACT_IMMUTABLE). When a referenced artifact's bytes no longer match its digest, or the file is gone, reading it back is an integrity refusal (ARTIFACT_INTEGRITY, ARTIFACT_MISSING; exit 3), raised before any computation: run ml reads back the dataset, the memberships and the References of the Study before it computes, and an Attempt it replays.

The canonical JSON and the atomic write were copied from hypotrail/hypotrail at commit 4ef4925 (framework/mlkit/study/understanding/canonical.py, framework/mlkit/study/store.py) and are owned here; nothing is imported from that project.

The Protocol

The StudySpec's protocol_digest is the canonical digest of what binds every Attempt: the Partitions and their ranges, the population and the References by their bytes, the data file by its bytes, the columns, the rules on when information is available (period_k, the forbidden and the allowed target features) and the primary metric. It changes when a Partition range or the References change. It does not change when a Configuration changes, nor with the key order of the declaration. run ml recomputes it from the Workload for a new request and refuses a Workload whose Protocol is no longer the Study's (PROTOCOL_CHANGED, exit 3); a Protocol that changed on purpose is a new revision of the Study (chapter 10).

The question, the objective and the limitations of the StudySpec are declared by the Workload (question, objective, limitations in workload.json, read by init only). The primary metric is mae, lower_is_better, in the unit the Workload declares. study_id is a UUID; revision is the digest of the StudySpec without its study_id and itself. An artifact ID is its kind and the first 16 hex digits of its digest (references-<digest>), so a corrected References set has another ID.

Request identity

--request-id is required for run, for import (chapter 06) and for decide (chapter 17), and must not be empty. A request is identified by the elements below, read from the Attempt manifest itself. The same request_id with the same request returns the recorded Attempt, whatever its status, after reading its artifacts back against their digests: no fit and no prediction happens, and nothing is written. With any element different it is REQUEST_CONFLICT (exit 6), naming the elements that differ, and nothing is written. A wanted rerun uses a new request_id and --retry-of ATTEMPT_ID; the earlier Attempt and its artifacts keep their digests.

A Study has one request_id namespace, for its Attempts, its Decisions and its Declared deviations. A request_id that names a record of another kind is REQUEST_CONFLICT: a Decision or a Declared deviation for run and import, an Attempt or a Declared deviation for decide, an Attempt or a Decision for deviation. In each, differs is ["command"] and details carry attempt_id, decision_id and declared_deviation_id, those that do not apply set to null. Two Decisions under one request_id that differ name, in differs, the fields of the Decision record that differ (chapter 17).

Changing ridge.alpha from 1.0 to 10.0 under the name ridge_v1, or changing the dataset, or running another commit, is therefore a conflict under the same request_id; under a new one it is a new Attempt (a changed dataset is then refused as a Protocol change). A different dirty state or fingerprint of the local code with the same commit is a conflict too.

One writer, interruption and retry

The lock. Every command that writes to a Study (report only when its page records an Exposure) holds an exclusive, non-blocking lock on writer.lock (core/lock.py) for the whole command. The steps that all writers share, in the order each writer keeps (the argument check, the lock, the write journal, the replay of a request identity, the stale-sequence check), are written once, in core/study_write.py. A second writer does not wait: it is refused at once with STUDY_LOCKED, exit 6, and writes nothing. The operating system drops the lock when its holder ends, killed or not, so a dead writer never blocks the Study. status takes no lock; it probes whether one is held. The lock needs fcntl (Linux, macOS); elsewhere the writers are refused with LOCKING_UNAVAILABLE (exit 5). The lock mechanism was adapted from framework/mlkit/study/lock.py of hypotrail/hypotrail at commit 4ef4925 and is owned here.

What an interruption leaves. The manifest is written running before anything else, each artifact is published before the terminal manifest, and the terminal manifest replaces the running one atomically, last. A process killed in between leaves the artifacts it had published, no artifact under a final path it had not reached, and a manifest that is still running, without finished_at. No complete state is invented. An error that is raised inside a live process instead leaves the Attempt failed, with a Reason and finished_at, its artifacts kept, and the command exits 4.

Looking and recovering. status shows such an Attempt as it is: running, with recoverable: true when no writer is alive. recover --attempt ID records it as interrupted. It refuses an Attempt that is already terminal (ATTEMPT_TERMINAL, exit 3) and, while a writer is alive, the whole command (STUDY_LOCKED). An Attempt whose Mode calls a provider (llm_live) is recorded with outcome_unknown: true: a lock that is gone is never read as the cancellation of a remote call.

Retry. A retry is never implicit and nothing is resubmitted. The same request_id with the same request returns the recorded Attempt, whether it is running, interrupted or failed, with neither a fit nor a prediction. To run it again, use a new --request-id and --retry-of ATTEMPT_ID: it is a new Attempt, and the earlier one and its artifacts keep their digests.

Immutability. Once an Attempt is no longer running, a write that would change its manifest or its outputs, or add a file to its folder, is refused with ATTEMPT_TERMINAL.

The Write sequence

A Study keeps a Write sequence: a value that every write to the Study advances and that nothing else changes. It is the number of entries of an append-only journal, write_journal/SEQ.json (core/write_journal.py, opened and appended to by core/study_write.py); an entry is never rewritten. status --json shows it as the top-level key write_sequence, and no other command's output shows it, but the details of the two refusals of --read-sequence (below). It is not a revision of the Study (chapter 10): a revision changes the Protocol, a write only advances the sequence.

Two entries per writing command. A command that writes appends a begin entry just before its first write and an end entry after its last. A writer killed between its first write and its last has still written: it leaves its begin entry only (a run ml killed after its running manifest leaves the sequence one higher), and the recover that follows adds two. A command that writes and then stops appends its end entry too: a run ml that leaves a failed Attempt, and a compare refused for its coverage after it appended its Exposure entry (chapter 12).

What a command that writes nothing leaves. status, a replay (the same request_id with the same request), a refusal before the first write and a report whose page shows dev Items only leave the sequence as it was, and append no entry.

What an entry says. request_id is null for a command without one (init, assess, compare, recover, report). The outcome of an end entry is completed (the command wrote what it set out to write), failed or refused. For run and import, any error after the running manifest is failed, whatever its exit code, since it leaves a failed Attempt. For a command with no Attempt, an error after its first write is failed when it exits 4 and refused when it is a coded error with another exit. outcome may gain values: a reader does not treat that list as closed.

Reading the sequence before a write: --read-sequence N. A command that writes to a Study takes, as an option, the Write sequence its author read (the write_sequence of status --json); the command table below says which do, and whether it is required. A command for which the table makes the option optional, given none, behaves as it did before the option existed; it appends its journal entries all the same. Given and equal to the Study's, the command does what it does without the option. The table of refusals below gives what any other value gets. report compares the value only when its page records an Exposure; a page of dev Items only is written as without the option.

The value is compared under the writer lock, so a write made by another process between the author's read and the command is caught. The refusals come in this order: the arguments (the read sequence value is the library's first argument check); the Study; the lock; the request identity (a replay of the same request_id with the same request returns the recorded Attempt, or the recorded Decision for decide, and writes nothing, whatever value was read; another request is a conflict); the comparison of the value; then the command's other refusals. The table of checks before the lock below lists the checks that come before the lock beyond this general order, those that read more than the arguments. Such a check comes before the comparison of the value, as before this version; compare --factor and report --out are among them. An older value given with one of them failing gets that refusal, not the one for the value. In run ml, import ml and import agent the refusals that guard the reads the identity needs keep their place before the identity; in run agent, whose identity reads its input bytes directly, only the data check and the artifact checks come after the comparison (the table of refusals below gives their codes, and chapter 13 the order of that command); the others keep their place, before the lock or before the identity. An older value with corrupt data is therefore refused for the value in run agent and for its data in run ml; neither writes anything.

A Study written before this version holds no journal and shows write_sequence 0 until its first write. Its files are never rewritten.

Reading status --json. The table below lists the top-level keys of the object. A later version may add keys to it, or to an entry of a list it holds, so a client should ignore a key it does not know rather than refuse the object. status --since N gives what was written since a Write sequence: a client that read the Study at Write sequence N asks what was written after it. The value is judged as the value of --read-sequence is, before the Study is read; one above the Study's is refused as a write's is (the table of refusals below), and 0 is answered. The answer is the whole object of status --json with one key more, the last row of the table below, whose entries have the shape of the detail that names them in the refusal of a write made on an older Write sequence, a killed writer's begin entry included. The entries and the write_sequence of one answer come from one listing of the journal, so a writer that appends while it reads cannot make them disagree. It stays a read: it takes no lock, writes nothing and records no Exposure. How to run it

# from the repository root; the ml extra is needed for ridge_v1
uv run python -m hypotrail init --workload bike_day --study runs/bike
uv run python -m hypotrail run ml --study runs/bike --config seasonal_7 --partition dev --request-id ml-dev-a
uv run python -m hypotrail run ml --study runs/bike --config ridge_v1 --partition dev --request-id ml-dev-b --json
# the same request_id and request again: the recorded Attempt, nothing recomputed
uv run python -m hypotrail run ml --study runs/bike --config ridge_v1 --partition dev --request-id ml-dev-b --json
# after a writer was killed: look, record the Attempt as interrupted, then repeat it on purpose
uv run python -m hypotrail status --study runs/bike --json
uv run python -m hypotrail recover --study runs/bike --attempt ATTEMPT_ID
uv run python -m hypotrail run ml --study runs/bike --config ridge_v1 --partition dev --request-id ml-dev-c --retry-of ATTEMPT_ID

The tests are tests/test_canonical_json.py, test_artifacts.py, test_contracts.py, test_study_init.py, test_run_ml.py and test_study_lock.py (the lock, the killed writer, status, recover, the retry); like the rest of the suite they run offline and call no model. run ml may be run on any declared Partition, public_check included: there is no freeze record or Exposure journal yet.

Limits

No resume engine, POSIX locking

An interrupted or failed Attempt is never continued: a retry is a new Attempt (a generic resume engine is out of scope). The lock needs fcntl; on Windows the writers are refused. A status probe holds a shared lock for an instant, so a writer that starts at that very moment is refused (it writes nothing) and can simply be run again. recover leaves the unpublished scratch files of a dead writer in .scratch/.

No scoring, no Comparison

run ml does not score: assess does, in a separate step (chapter 05), and compare compares two Assessments in another (chapter 07). An import is a separate command (chapter 06).

No freeze at run time

A run ml on public_check is recorded like any other and is not an Exposure: it scores nothing, so it writes no freeze record and no journal entry. The Exposure is the Assessment or the Comparison (chapter 12). After the Study's first Exposure, a run ml of a Configuration the freeze record does not hold is not refused: its Attempt is marked check_informed.

Two Tracks, one native each

run ml serves the temporal regression Track only. A Chinook Study (init) takes answers produced elsewhere with import agent (chapter 08) and records its own native Attempts with run agent (chapter 13), which follows the order, the request identity, the lock and the manifest described here.
