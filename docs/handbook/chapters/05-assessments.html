assess applies one registered Scorer version to one kept Observation set and one References set of a Study, and writes a new Assessment. It fits nothing, computes no Configuration's prediction and calls no model or tool: it reads files the Study already keeps, and computes from the Study's copy of the dataset the forecast of each lag feature the Configuration declares, used alone (the single-feature check, below). Every expected Item gets a Criterion state, with a Reason for every non-score, and rescoring never changes an earlier Assessment: it writes another one. This chapter describes what exists (the temporal regression Track, on dev); the agent Scorer chinook_contract_v1 is in the registry too, and chapter 08 describes what it writes; the report is later work (see Limits).

The command

assess is in src/hypotrail/cli.py; the work is in src/hypotrail/ml/assess.py and the registry in src/hypotrail/core/scorers.py. It follows the rules of chapter 04: with --json, stdout holds one JSON object, {"ok": true, "assessment": RECORD} or {"ok": false, "error": {"code", "message", "stage", "details"}}, and the diagnostic goes to stderr; without it, stdout holds one line. The three ids are the ones the Study keeps: the observation_set_id of an Observation set record (run ml prints it in attempts/ATTEMPT_ID/observation_set.json), a Scorer id from the registry, and the artifact_id of the References set in study.json (references- and 16 hex digits).

The Scorer registry

For a ranking Study, use ranking_recall_at_top_v1. The Metric is mean recall among the top tenth of the Items of each development date. Equal scores are ordered by Item ID. The Assessment records counted and omitted dates in ranking_dates. Its verified per-Item artifact has the Item, entity, as-of date, score and frozen label of the development population.

The registry is a static, closed table in the code. A --scorer value is a key of that table and nothing else: it is never imported, evaluated or looked up by name, so a string such as package.module:function loads no Python and is refused as a Scorer that is not registered. A Scorer belongs to one Track (its domain); one applied to an Observation set of another Track is refused. chinook_contract_v1 is the Scorer of the agent Track (version 3); it has four Criteria and no Metric of its own, and its Assessment is described in chapter 08.

Both Scorers have the same Criterion, the absolute error of the day, and differ in the Metric they aggregate from it: mae, the mean of the absolute errors, and rmse, the square root of the mean of their squares. The Metric's unit is the one the StudySpec declares for the primary metric; its direction is lower_is_better. The config_digest is the digest of the Scorer's configuration (the Criterion, the Metric and the direction): another Metric is another digest.

What is checked, in order

  1. The Study exists; the Scorer is in the registry.
  2. The Observation set and the References set exist in the Study (the References set of the current revision: an earlier revision's set is refused with REFERENCES_NOT_FOUND), and the Scorer belongs to the Observation set's Track.
  3. Every artifact read is read back against its digest: the Observation set record, the normalized outputs, the raw predictions it was made from, the population and the References, and, only when the Attempt's Configuration declares a lag feature, the copy of workload.json the Attempt keeps and the Study's copy of the dataset. One that is gone or no longer matches is an integrity refusal (chapter 04, ARTIFACT_MISSING or ARTIFACT_INTEGRITY, exit 3) and nothing is written, on public_check no Exposure either.
  4. The Partition of the Items is dev or public_check; any other Partition (train) is refused. An Assessment on public_check is an Exposure: the Study's freeze record is written if the revision has none and one journal entry is appended before any Item is scored (chapter 12). Running predictions on public_check with run ml is not an Exposure.
  5. The Items of the Observation set must be Items of that Partition, each once.
  6. Each expected Item (for a native Attempt, every Item of the Study's memberships in the Partition; for an Import, every Item of the population file it was given, which may list fewer; whatever the outputs hold) gets its Criterion; the Metric is aggregated from the scored ones. per_item.csv is published, then assessment.json, last.

Criterion states

A Criterion is scored (a number), unscored (the Scorer ran and had no usable reading) or errored (the scoring machinery broke). Neither of the last two is held against the evaluated system, and a null value is never zero: it is left out of the Metric and counted. The execution status of the Item (produced, failed, missing) stays separate, in its own column. An expected Item that the outputs do not hold at all is missing.

The Assessment record

assessments/ASSESSMENT_ID/assessment.json is canonical JSON, validated against the contract schema before it is written and when it is read. assessment_id is a UUID, new each time. counts holds one counter per key of the schema, named for the key (the specification's N_expected is expected). attempted is the Items that were produced or failed (a missing Item was never attempted). For a numeric loss, correct and incorrect are null: an absolute error is not a binary verdict; the other counters are filled. scored + unscored + errored = expected. The Metric has the number of scored Items as its denominator; with none, its value is null with the Reason no_scored_item.

The single-feature check

A regression Assessment of a native Attempt also scores each lag feature its Configuration declares, used alone as the forecast: the forecast of an Item is the feature's value at the Item's date, computed from the Study's copy of the dataset with the date and target columns of the workload.json the Attempt keeps, never from the Workload under --examples-dir. Nothing is fitted. Only the declared features that the kept declaration allows and whose kind is a value of the target (lag, mean_previous) are computed: a calendar column never is, and neither is an allowed feature the Configuration does not declare. Each feature is scored by the Assessment's Scorer over the Items the Assessment scored, and beating lists every one whose Metric is strictly lower than the Assessment's, best first. It is a flag, never a refusal: the Metric, the counts and per_item.csv are those the Assessment has without it, and compare names the flag in a warning (chapter 07).

single_feature_check has three states. A Configuration that declares no lag feature, such as seasonal_7, gets it with both lists empty: checked, nothing to compare. An Import declares no Configuration and gets no field: not checked. Neither does an Assessment one of whose features needs a date the series does not hold for some scored Item (LAG_SOURCE_MISSING): no feature is compared on fewer Items than the Assessment scored, so the field is left out, the command still exits 0, and one line on stderr names the cause. The dataset copy is read back against its digest before an Exposure is recorded and parsed only after it, and the series it gives keeps only the dates before the last scored Item's, so an Assessment of dev reads no value of public_check.

Limits

One writer

assess holds the Study's writer lock for the whole command, as init, run ml, import ml, recover and compare do: while another writer holds it, assess is refused at once with STUDY_LOCKED (exit 6) and writes nothing (chapter 04).

Summarised by the report

Two Assessments are compared by compare (chapter 07), and report sets Assessments and Comparisons of a Study out on one page (chapter 14). The record's rescoring field says which earlier Assessment of the same Observation set the new one differs from and why (chapter 10).

Dev, and public_check with a journal

Items of public_check can be assessed because the Study journals the Exposure (chapter 12); Items of train never can. PROTOCOL_CHANGED (exit 3) refuses an Assessment of public_check Items when the Workload's Protocol is no longer the revision's.

Two Scorers' shapes

The two regression Scorers aggregate one Criterion into a Metric and leave correct and incorrect null. chinook_contract_v1 scores four Criteria per Episode and counts them: its Assessment is the subject of chapter 08.
