import ml adopts a complete CSV of daily predictions, written by a program that never imports Hypotrail, as an Import Attempt of the Study that already holds the native Attempts. The original file, the mapping and a validation report are kept. Everything the import cannot establish about how the file was made is unknown; what the mapping claims is declared, never verified. assess then scores the Import like any Observation set (chapter 05). This chapter describes what exists: the temporal regression Track (the bike Workload), complete files only.

A ranking Study also uses import ml. Its mapping joins item_id to score, and dataset_sha256 names the frozen digest of items.csv. The Import accepts a population of mature development Items. Producer settings from the ranking mapping remain declared, and the original score file is kept with the Attempt.

The stand-in exporter

examples/external/bike_trailing_mean.py stands in for someone else's program (ADR 0002 makes examples/external/ the one place for Python that never imports hypotrail). It uses the standard library only. It reads the daily file, predicts every day of a window with the mean of the 28 days before the window, writes a CSV with its own column names (day_key, forecast_rentals, forecast_unrounded) and prints the sha256 of the data file it read. A test runs it in a subprocess where hypotrail cannot be imported.

The command

import ml is in src/hypotrail/cli.py; the work is in src/hypotrail/ml/imports.py. It follows the rules of chapter 04: --request-id is required, with --json stdout holds one object ({"ok": true, "replayed": BOOL, "attempt": MANIFEST, "observation_set_id": ID}, with the Observation set ID of chapter 04, or {"ok": false, "error": {"code", "message", "stage", "details"}}) and the diagnostic goes to stderr, and the command holds the Study's writer lock for its whole execution. It imports neither scikit-learn, NumPy nor Inspect, and reads no network: import ml and assess of the Import run where none of them is installed.

# a program that never imports hypotrail writes its predictions; it prints the digest of the data it read
python examples/external/bike_trailing_mean.py --data examples/bike_day/data/day.csv --first 2012-01-01 --last 2012-06-30 --id-prefix bike-day --out predictions.csv
# mapping.json: {"row_id": "day_key", "y_pred": "forecast_rentals", "dataset_sha256": "<that digest>"}
# population.json: {"item_ids": ["bike-day:2012-01-01", "bike-day:2012-01-02", "..."]}
uv run python -m hypotrail import ml --study runs/bike --source predictions.csv --mapping mapping.json --population population.json --request-id import-a
uv run python -m hypotrail assess --study runs/bike --observations OBSERVATION_SET_ID --scorer regression_mae_v1 --references references-0123456789abcdef

The mapping and the population

The mapping is a JSON object of strings. A key that is not in the table is refused, and so is a missing required key. The values of the three column keys must name columns of the source file; a value that names a callable or a module (os.system, pickle:loads, f(x), a path) is refused, and a column whose name looks like a dotted name cannot be mapped. The claim keys are free text, kept as data and never read as code. The population is {"item_ids": [...]}: the Items the file must hold, all of one Partition of the Study's Protocol. The expected population comes from this file checked against the Protocol, never from the source file or its name; the source cannot add an Item to it.

What is checked, in order

  1. The Study exists and the writer lock is free; the Workload's data is verified against its lock and the Study's artifacts are read back against their digests (chapter 04).
  2. The three files are read and their sha256 taken. The request is identified (below). The same request_id with the same request ends here with the recorded Import: the source is not validated again, and nothing is written or scored.
  3. The Protocol of the Workload is still the Study's (PROTOCOL_CHANGED, chapter 04).
  4. The mapping, then the source file (data and not a serialized object, valid UTF-8, a readable CSV that holds the mapped columns), then the population are checked. The dataset digest of the mapping is compared with the lock's.
  5. Every row of the source is joined to the population by ID: no empty ID, no repeated ID, no ID outside the population, a finite number in y_pred; every Item of the population must be present. A population smaller than its Partition is allowed: assess counts the Items of the Partition that the file does not hold as missing.
  6. Only then is anything written: the running manifest, the original files, the validation report, the normalized Observations and the Observation set, and the terminal manifest last. A refusal at steps 4 or 5 writes nothing at all. An error inside the process after the manifest is written leaves a failed Attempt with a Reason, as in chapter 04.

Nothing in an import is executed or deserialised as code. A source with the extension of a pickle, joblib or array dump, or whose first byte is the pickle marker, is refused as SOURCE_SERIALIZED before it is read as text.

What the Import keeps

The Import is an Attempt of the same Study as the native ones: its manifest has operation: import and Mode external_unknown, and its Observation set has origin: imported. The original source is copied under its own file name and referenced with its digest (role import_source), and it is the only raw output of the Observation set. The manifest's started_at and finished_at are import times; effective_config.import_time says so, and the time of generation is a separate field of effective_config.producer. The normalized Observations (observations.csv) are written in the same form as a native Attempt's, one line per Item of the population in ID order, every Item produced, so a permuted source gives the same bytes and the same measures. The Observation set's population_ref is the population file, so assess expects exactly those Items.

What is known about the producer

Each producer field is {"value": ..., "origin": ...} in effective_config.producer and in the Observation set's provenance. The origin is declared when the mapping says it and unknown when it does not; no field is verified, because a claim in an external file is not checked by importing it. unknown_fields of the Observation set lists the fields whose origin is unknown. Whether the producer saw public_check values is always unknown: no mapping key can declare it. No record states that the producer worked independently. An Import whose fields are all unknown is scored like any other (descriptively); a later Comparison against it is descriptive with a warning.

The request

The identity of an import holds every element of chapter 04's list, each with the import's value or unknown when the import does not establish it: the command (import ml), the Workload, the Configuration (unknown), the Partition of the population, the Mode (external_unknown), the model (the declared one, or unknown), the repeats (unknown), the digests of the dataset, the source, the mapping and the population, and the code revision (commit, dirty state, fingerprint of the local code). The same request_id with the same request returns the recorded Import: the digests are recomputed to compare the requests, and nothing is validated again, written or scored. With any element different, including a request id that names a native Attempt, it is REQUEST_CONFLICT (exit 6).

Limits

Complete ML files only

An incomplete file is refused, never imported with the gaps marked missing. An agent import of JSONL answers is chapter 08; an import of an Inspect log is chapter 09; the migration of old Studies is another ticket. A Comparison that involves an Import is descriptive, with a warning on its scope (chapter 07); the report and the Exposure journal come later in issue #9.

Claims are not checked

The digest of the dataset is checked against the lock; the model, the date, the protocol and the tool use are only what the mapping says. A column whose name looks like a dotted name (pred.v1) cannot be mapped, because the same shape names a module.

The tests are tests/test_import_ml.py (every criterion of the ticket) and tests/test_handbook.py (the tables of this chapter against the code). They run offline and call no model.
