The demonstration script

The script runs the steps of section 18 of the teaching page, pages/de-zero-a-la-demo.html in chadlis/hypotrail-learning (in French; read at commit 164aa3a), that need no person, from a Study that does not exist to its final state, with no live model call and no network. It takes one work folder, outside the checkout and new or empty; any other folder is refused with exit code 2 and one line on stderr, and nothing is written. The work folder receives everything the demonstration writes: the Studies, the report pages and the population file of the Import. No file of the checkout changes, its examples/ included.

The demonstration has four Studies, in this order: a first Bike Study, a second Bike Study on a Workload copy, a Chinook Study, then a copy of the Study the Chinook Campaign kept in the repository (chapter 20). The script runs all four; the steps of the second come between L1.7 and L1.8, and the last step, which section 18 does not have, copies the kept Study into the work folder and writes in the copy alone, so the kept folder keeps its bytes. The second Bike Study is made from a copy of examples/ in the work folder, given with --examples-dir to each command that reads the Workload, and the two edits of task 6 are made in that copy. The first table lists the steps it runs, each by its id in section 18 (C5-check is its check C5, run from the terminal) or by a name of its own for a step section 18 does not have, with its title and the folder of its Study in the work folder.

For each step the script prints what it shows and why, starts each command as a process of its own, as a person would, and prints the values each command gave. It then checks each value the step expects: an exit code, the code and stage of a refusal, or the value at a named key of the command's --json object, a float being compared to 12 significant digits. It stops at the first that does not hold, after a line that names the step, the key, the value expected and the value found, and exits with code 1; when every step gives what it expects, its last line counts them and it exits with code 0. Each id a command takes is printed by an earlier command of the same demonstration, so no step looks one up. Each process is started without the live key in its environment. The tests run the same step list in process, under the suite's network guard, and check the records each command leaves in its Study.

The panel on the kept states

The client's tests walk the panel through the kept states, in clients/vscode/test/panel-demonstration.test.ts. At each one they build the document the panel shows once its two reads answer, and read it against them: the question, the delta, the options with their consequences, each Decision with whether it applies, and the state of its evidence. They record the Decision of task 3 twice: in headless Chrome with the keyboard alone, from the top of the document to the message it posts, and through the panel's bridge, where that message starts the decide the demonstration ran. They also send the write that the Study refuses at S1, and read the refusal and the question asked again. The same reads go through the client's other checks of a read, the drawings of clients/vscode/test/panel-screen.test.ts in the four themes at 420 and 900 px, the contact sheet of verify-panel, and the two Copilot tools in clients/vscode/test/tools-demonstration.test.ts.

Blocker 11 is fixed (chadlis/hypotrail#226): one assertion checks that every file name and every number the panel shows leads to its record, and it holds on every kept state. Two parts of the drawings are expected to fail until the panel is redesigned: Record in the first screen at 420 px, and the latest of two Decisions in it. Each is marked, so that npm test passes while it fails, and an unmarked test fails on the day it holds, until the mark is removed.

The edits of task 6

Task 6 shows a recorded Decision become outdated when its evidence changes. Its evidence is changed by editing a Reference twice, first one outside the assessed Partition, then one inside it, each time in a copy of the Workload passed with --examples-dir, never in the checkout's examples/. A Bike Reference is not a file of its own: it is a cell of the target column of the copy's data file, and the CLI checks two things before it writes anything. The target must equal the sum of its two parts, so an edit changes one part and the target by the same amount; and the file must match the copy's lock, so an edit also rewrites the file's sha256 and size_bytes there. One edit is therefore three values in two files, one of them a SHA-256.

The script below makes one edit with one command and rewrites the lock's entry for the file. It prints the day, the old and new value of each column it changes, and the old and new SHA-256 of the file. It takes the Workload copy, the folder passed as --examples-dir, and which of the two edits to make. It uses the standard library only, imports nothing of Hypotrail, and is not a command of the CLI.

It refuses a folder inside the checkout it is in: it exits with code 2, names the reason on stderr and writes nothing. "Inside" is judged on the resolved path, so a path through .. or a symbolic link into the checkout is refused too; another clone of the repository elsewhere on the machine is not recognised as the checkout. This is its only refusal: an edit made a second time is made again, and adds the amount once more. A copy without data/day.csv or its lock gets one line on stderr naming the missing file, a non-zero exit, and nothing written. To return to a clean state, remove the Workload copy and the Study and make them again.

After each edit, check the copy, start a new revision of the Study from it, and assess each of the Study's two Observation sets against the new References ID, as below. The last column of the table is what each edit is expected to give in the panel and in status --json: the Decision recorded on the Comparison no longer applies, and the state of its evidence is the label of the table.

What stays out of commits

The demonstration opens this checkout in VS Code and leaves two kinds of file in it. The README's commands write the Study under runs/, which .gitignore ignores, so a Study there does not show as untracked. The owner installs the Copilot template, clients/vscode/copilot-instructions.md, as .github/copilot-instructions.md (chapter 18), which .gitignore also ignores: this repository's own .github/ holds no instructions file, and the installed copy stays uncommitted. The Claude Code hook is installed in .claude/settings.local.json, which was already ignored.

Where the ids of assess come from

assess takes an Observation set ID and a References ID, and the commands before it print both. run ml, import ml, run agent and import agent end their line with the Observation set ID they recorded, as in Attempt ATTEMPT_ID completed (N Items produced, N failed, N missing); Observation set OBSERVATION_SET_ID, and their --json object holds it under observation_set_id. init and init --new-revision end their line with the References ID of the revision they made, as in Study runs/bike is at revision 2: Workload bike_day, protocol PROTOCOL..., study_id STUDY_ID, references_id REFERENCES_ID, and their --json object holds it under references_id. After init --new-revision, the References ID is the one it printed; the Observation set IDs stay those the two run ml printed.
