The first milestone is accepted test by test. SPEC §10 lists 24 acceptance tests, T01 to T24. This chapter has one row per test with what it does, the result it expects, and either the proof that it holds or an explicit not run with its reason. Three statuses are kept apart, each with its own value and its own evidence, and none derived from another: OFFLINE_ACCEPTED, LIVE_ACCEPTED (pending) and USABILITY_REVIEW_PENDING (open).

The three statuses

OFFLINE_ACCEPTED rests on T01 to T19 and T21 to T24 and is computed from the rows of the grid below: it is reached only if each of those rows has a passing proof, and otherwise it is pending and names the rows that hold it back. A row marked not run holds it back. LIVE_ACCEPTED rests on T20 and on the model report of the spike, and it is pending. USABILITY_REVIEW_PENDING stays open until another person has read the README path.

The value LIVE_NOT_VALIDATED of SPEC §0 is for the case where no usable real model exists. That does not hold here: a real model was used (the spike and one paid run agent Attempt, kept in docs/handbook/traces/), so LIVE_ACCEPTED is pending, not LIVE_NOT_VALIDATED.

The grid

Each row's English text renders the row of SPEC §10; whether it renders it faithfully is checked by the review of record, not by a test. A pytest proof names test nodes, and each node declares the row (T05 in its name or its docstring): a collected test that is about another row fails the grid. Whether the content of a test matches what §10 asks of the row is not checked by that declaration; it stays with the review of record. A pytest proof passes if its nodes pass in the same suite as the test that reads this table. The T24 row passes when the walk record exists, passes the test that checks it against the README, and holds what T24 expects: the walker identified, a failure and a limit found, the difficulties recorded. A recorded difficulty does not fail it; a difficulty that kept the walker from finding the failure or the limit does.

The live Campaign, for after the owner's review

The Campaign is 12 Cases x 3 Repeats x 2 Configurations = 72 Episodes on public_check. run agent runs one Configuration per invocation, so it is two invocations, one with --config plain and one with --config verify, with the same model and limits for both, the response cache off and retries at zero (the limits of the Track, chapter 03). Each Attempt is then assessed, the two Assessments are compared with plain as the Control and verify as the Candidate, and the Study is reported. The placeholders are filled from the output of the step before and from status --json (chapter 04). Running on public_check is an Exposure (chapter 12).

StepCommand
1. plain invocationuv run python -m hypotrail run agent --study DIR --mode llm_live --config plain --partition public_check --repeats 3 --model anthropic/claude-sonnet-5-5 --request-id REQUEST_ID_PLAIN
2. verify invocationuv run python -m hypotrail run agent --study DIR --mode llm_live --config verify --partition public_check --repeats 3 --model anthropic/claude-sonnet-5-5 --request-id REQUEST_ID_VERIFY

4. assess verifyuv run python -m hypotrail assess --study DIR --observations OBSERVATION_SET_ID_VERIFY --scorer chinook_contract_v1 --references REFERENCES_ID
5. compareuv run python -m hypotrail compare --study DIR --control ASSESSMENT_ID_PLAIN --candidate ASSESSMENT_ID_VERIFY
6. reportuv run python -m hypotrail report --study DIR --out FILE

Every line parses with the CLI's parser once its placeholders are filled, so it carries the flags the parser requires: --study and --request-id for run agent (with --mode and --config), --study, --observations, --scorer and --references for assess, --study, --control and --candidate for compare, and --study and --out for report. verify is plain plus one instruction (chapter 03), which is why plain is the Control. The two invocations use two --request-ids.

The conditions under which it runs:

  • only after the owner's review of the References (of E07 and of E01-E10);
  • Inspect logs and Observation sets kept whole;
  • no further paid invocation except after a technical failure;
  • within the USD 30 budget and five paid live invocations per slice.

No command of this grid was run against a real model when the grid was written. A later correction of a Reference is rescored from the kept outputs under a new Study revision, without a new model call (chapter 10).

Open pointThe order of the Configurations is not alternated Episode by Episode. AG-12 asks to alternate the order of baseline and verify by the parity of case_index + repeat_index, which needs both Configurations interleaved; run agent runs one Configuration per invocation, and the Campaign is two invocations. A single-Episode invocation per Episode would be 72 invocations, more than five paid live invocations per slice. Whether a later change to run agent provides the alternation, or the Campaign records it as a limit, is not settled; it is for the owner-decision gate.
